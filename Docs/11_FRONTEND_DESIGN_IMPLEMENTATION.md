# FRONTEND_DESIGN_IMPLEMENTATION — 2026-07-10 프론트 디자인 반영 기록

## 1. 작업 목적

이 문서는 2026-07-10에 진행한 프론트 영역 디자인 수정 내용을 기록한다.

작업 방향은 다음과 같다.

1. 첨부된 한국도박문제예방치유원 홈페이지 이미지는 디자인 요소 참고용으로만 사용한다.
2. 홈페이지의 네비게이션 바, 햄버거 메뉴, 마이페이지 사이드바를 그대로 복제하지 않는다.
3. 배정 교육 정보처럼 현재 기능에 필요하지 않은 섹션은 제거한다.
4. 실제 기능에 필요한 업로드, 검수, 저장 목록, 다운로드 섹션만 남긴다.
5. 미적으로 과한 화면보다 낮은 리소스 사용과 업무 흐름의 명료성을 우선한다.

## 2. 디자인 방향

### 2.1 제거한 방향

| 제거 대상 | 사유 |
|---|---|
| 다크 배경 | 기관 홈페이지와 시각적으로 다름 |
| 글래스모피즘 패널 | 공공기관 업무 UI에 비해 장식성이 큼 |
| 큰 그라디언트와 글로우 | 리소스와 시각적 피로가 큼 |
| 이모지 중심 액션 표현 | 공식 업무 도구 톤과 맞지 않음 |
| 홈페이지 네비게이션 바 복제 | 이 앱의 기능과 직접 관련 없음 |
| 마이페이지 사이드바 복제 | 이 앱의 기능과 직접 관련 없음 |
| 배정 교육 정보 섹션 | 현재 자동작성 기능에 불필요 |

### 2.2 적용한 방향

| 적용 방향 | 설명 |
|---|---|
| 백색 캔버스 | 기관 홈페이지와 유사한 밝은 배경 |
| 보라색 브랜드 축 | `#6855A0` 중심의 주요 버튼, 포커스, 상태 표시 |
| 얇은 회색 경계선 | 패널과 표를 1px 선으로 구분 |
| 회색 표 헤더 | 저장 학생 목록을 행정 문서처럼 표시 |
| 기능 중심 첫 화면 | 앱 제목, 짧은 설명, 업로드 방식 선택만 표시 |
| 낮은 장식성 | 그림자, 블러, 그라디언트 사용 최소화 |

## 3. 현재 화면 구조

현재 첫 화면 구조는 다음 순서를 따른다.

```text
앱 제목 및 짧은 설명
→ 응답지 업로드 방식 선택
→ 응답지 업로드
→ 인식 결과 검수
→ 작성 완료 학생 목록
→ CAGI / 만족도 엑셀 다운로드
```

작업 시작 전:

```text
응답지 엑셀 자동작성
→ 개별/순차 촬영 선택
→ 일괄 스캔 업로드 선택
```

작업 시작 후:

```text
업로드 패널
→ 오류 요약
→ 인식 중 상태
→ 검수 화면
→ 저장 완료 학생 목록
→ 다운로드 버튼
```

## 4. 업로드 흐름 반영

### 4.1 개별/순차 촬영

사용 흐름:

```text
선별검사지 업로드
→ 만족도조사 업로드
→ 두 이미지가 모두 있으면 인식 요청
→ 인식 결과 검수
→ 엑셀 반영
```

화면 요구:

- 선별검사지와 만족도조사를 나란히 배치한다.
- 각 박스는 파일 선택, 업로드 완료 장수, 다시 업로드 상태를 표시한다.
- 만족도 이미지에서는 문항1~10만 읽고 기본정보는 선별검사지 값을 사용한다.

### 4.2 일괄 스캔 업로드

사용 흐름:

```text
선별검사지 묶음 업로드
→ 만족도조사 묶음 업로드
→ 장수 일치 확인
→ 일괄 인식 시작
→ 학생별 검수
→ 순차 엑셀 반영
```

화면 요구:

- 앞면 묶음과 뒷면 묶음을 분리해서 업로드한다.
- 각 묶음의 장수를 표시한다.
- 장수가 다르면 오류 박스를 표시하고 분석 버튼을 비활성화한다.
- 파일 순서가 학생 순서와 일치해야 한다는 주의 문구를 항상 노출한다.

## 6. 업로드 타입 보정

기존 문제:

```text
프론트는 업로드 칸의 type(cagi/satisfaction)을 알고 있음
→ 서버 업로드 API에는 type을 보내지 않음
→ 서버 저장 파일명은 img_타임스탬프.ext
→ classifyForm은 파일명으로 cagi/satisfaction을 분류
→ 실제 업로드 파일은 unknown으로 분류될 가능성이 큼
```

수정 후:

```text
ImageUploadPanel에서 FormData에 type 추가
→ /api/upload가 type을 검증
→ 저장 파일명은 cagi_타임스탬프.ext 또는 satisfaction_타임스탬프.ext
→ recognize 단계의 파일명 기반 분류가 실제 업로드 흐름에서도 최소 동작
```

주의:

- 이 보정은 실제 OCR/Form Recognition을 완성한 것이 아니다.
- 현재 분류는 여전히 파일명 기반 경량 분류이다.
- 향후 문서 제목 OCR 또는 양식 레이아웃 기반 분류로 교체해야 한다.

## 8. 남은 작업

### 8.1 디자인

- 모바일 화면에서 업로드 카드와 검수 폼의 줄바꿈 재점검
- 실제 기관 홈페이지와 버튼 높이, 표 행 높이, 폰트 굵기 추가 대조
- 기능과 무관한 기관 홈페이지 구조가 다시 들어가지 않도록 유지

### 8.2 기능

- 일괄 업로드 초기화 시 서버 업로드 파일도 함께 정리
- 순차 업로드에서 재업로드 시 이전 파일이 인식 대상에 남지 않도록 처리
- `recognize` API에서 실제 세션 존재 여부 확인
- 파일명 기반 양식 분류를 실제 OCR/Form Recognition 기반 분류로 교체
- PDF 변환을 CDN 전역 객체 의존에서 안정적인 번들 또는 서버 처리로 전환

### 8.3 테스트

- 실제 `/api/upload`를 거친 뒤 `/api/recognize`까지 이어지는 통합 테스트 추가
- 재업로드/초기화 후 이전 파일이 섞이지 않는지 검증하는 테스트 추가
- 모바일 폭 시각 QA 추가
