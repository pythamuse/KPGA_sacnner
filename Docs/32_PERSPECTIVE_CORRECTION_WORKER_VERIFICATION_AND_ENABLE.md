# 32. 원근보정 Web Worker 전환 검증 및 재활성화

[[31_PERSPECTIVE_CORRECTION_WEB_WORKER_DESIGN]]의 검증 계획을 실제로 수행한 결과와 최종 재활성화 결정을 기록한다.

## 검증 결과

로컬 개발 서버에서, 이전에 완전 정지를 재현했던 정확히 같은 시나리오(1200×900 합성 이미지, "파일 선택" 업로드)로 재검증했다.

**핵심 안전성 확인**: 업로드를 트리거한 뒤 `setInterval`로 200ms마다 증가하는 하트비트 카운터를 돌리며 관찰한 결과, **하트비트가 계속 증가했고 `1+1` 같은 간단한 JS 평가도 즉시 응답했다** — 이전(메인 스레드 직접 실행)에는 이 시점에 `javascript_exec` 호출 자체가 30초 타임아웃으로 실패할 정도로 완전히 멈췄던 것과 대조적이다. **Worker로 격리한 뒤로는 어떤 상황에서도 메인 스레드(화면)가 멈추지 않는다는 목표를 달성했다.**

**보정 성공 여부는 불확실**: 진단 로그를 임시로 추가해 확인한 결과, 워커 생성·`postMessage` 전송까지는 정상적으로 이루어졌지만, 이번 로컬 테스트에서는 매번 9초 타임아웃(`PERSPECTIVE_CORRECTION_TIMEOUT_MS`)에 걸려 `terminateWorker`가 호출되고 원본 그대로 업로드하는 폴백 경로로 넘어갔다. 즉 **Worker 내부에서 여전히 무언가 느리거나(또는 이전과 비슷한 원인으로) 응답하지 않는 상황이 있는 것으로 보이지만, 이제는 그로 인해 화면이 먹통이 되는 대신 9초 후 조용히 원본 업로드로 안전하게 넘어간다.**

## 재활성화 결정

다음 근거로 `PERSPECTIVE_CORRECTION_ENABLED`를 `true`로 전환해 배포한다:

1. **핵심 위험(완전 정지)이 확실히 해소됨** — 이번 전환의 원래 목적이자 최우선 순위.
2. **보정이 항상 실패(타임아웃)하더라도, 지금까지 배포되어 있던 "완전 비활성화" 상태와 기능적으로 동일하다** — 즉 이 결정으로 인한 추가 리스크가 없다. 보정이 어쩌다 한 번이라도 성공하면 그만큼 [[27_ROI_MISALIGNMENT_CONFIRMED_ROOT_CAUSE_AND_FIX]]에서 확인한 정확도 문제가 개선되는 순수 이득이다.
3. 로컬 개발 서버(next dev)는 프로덕션 빌드보다 여러모로 느리고(HMR, 소스맵, React 개발 모드 오버헤드), 실제 배포 환경(Vercel, 프로덕션 빌드)에서는 워커 내부 처리가 9초 안에 끝날 가능성도 있다 — 실사용 환경에서 재검증이 필요하다.

## 남은 과제

- 워커 내부에서 정확히 무엇이 느린지(또는 여전히 멈추는지)는 완전히 규명하지 못했다. `cv.matFromImageData` 경로가 `cv.imread(canvas)`와 다르게 동작하는지, 워커 컨텍스트의 `importScripts` 자체가 프로덕션 환경에서도 느린지 등은 후속 조사가 필요하다.
- 실제 배포 후 사용자가 같은 시나리오(파일 선택 업로드, 카메라 촬영)로 재테스트해서: (1) 화면이 멈추지 않는지(최우선 확인 사항), (2) 보정이 실제로 성공해 [[27_ROI_MISALIGNMENT_CONFIRMED_ROOT_CAUSE_AND_FIX]]의 오정렬 문제가 개선됐는지 확인이 필요하다.
