# PDF_RENDERING_FIX_CANDIDATES — 일괄 스캔 PDF 변환 멈춤 문제 해결 후보

## 1. 문제 재현 및 근본 원인

2026-08-01, 실제 현장 PDF 2건(`선별검사 샘플1.pdf`, `만족도조사1.pdf`, 각 19페이지)을 일괄 스캔 업로드로 넣어보면 "PDF 페이지를 변환하고 있습니다 (1/19)"에서 진행이 멈추고 다시는 진행되지 않는다. 사용자에게는 오류 메시지 없이 무한 로딩처럼 보인다.

실제 Chrome에서 `src/components/ImageUploadPanel.tsx`의 `convertPdfToImages()`/`renderPdfPageToFile()`이 호출하는 pdf.js 단계를 하나씩 직접 실행하며 타임아웃을 걸어 확인한 결과:

| 단계 | 결과 |
|---|---|
| `pdfjsLib.getDocument()` | 정상 (수십 ms), 19페이지 확인 |
| `page.getTextContent()` | 정상, 텍스트 항목 0개 (순수 스캔 이미지 페이지) |
| `page.getOperatorList()` | 정상, 연산 5개(이미지 1장 그리기 수준의 매우 단순한 구조) |
| `page.render({canvasContext, viewport})` | **15~30초 이상 응답 없음. 무한 대기.** |

두 파일 모두, 새로고침 후 완전히 독립된 상태에서도 동일하게 재현된다. `getOperatorList()`는 빠르게 끝나는데 `render()`만 멈춘다는 것은 **PDF 구조 파싱은 문제 없고, 임베딩된 이미지를 실제로 디코딩/래스터화하는 단계에서 멈춘다**는 뜻이다. 스캐너 소프트웨어가 흑백 스캔 문서에 흔히 쓰는 CCITT G4/JBIG2류 압축 이미지를 이 앱이 CDN으로 고정해 쓰는 pdf.js `3.4.120`(`src/app/layout.tsx`, 2023년 빌드)이 처리하다 멈추는 유형의 문제로 추정된다.

부가 문제: `renderPdfPageToFile()`/`convertPdfToImages()`에는 타임아웃이 전혀 없어서, 한 페이지가 멈추면 전체 배치 업로드가 오류 표시 없이 영구적으로 멈춘 것처럼 보인다. 이는 근본 해결과 별개로 반드시 추가해야 한다(별도 작업으로 진행, 이 문서의 범위 밖).

기존 자동 테스트가 이 문제를 못 잡은 이유: `tests/*.test.ts`는 전부 합성 PNG(파일명 기반 분류) 또는 SVG로 그린 단순 도형 이미지를 쓰고, 실제 브라우저의 pdf.js 렌더링 경로 자체를 한 번도 통과시킨 적이 없다.

## 2. 후보 A — 클라이언트 pdf.js 버전/로딩 방식 교체

### 개요

`src/app/layout.tsx`의 CDN `<script>` 태그와 `ImageUploadPanel.tsx`의 `workerSrc`가 가리키는 pdf.js 버전을 올린다. 현재 cdnjs 기준:

- 현재 고정 버전: `3.4.120`
- 3.x 라인 최신: `3.11.174` — 기존과 동일한 UMD 빌드(`pdf.min.js`, `pdf.worker.min.js`)를 여전히 제공해 **코드 구조 변경 없이 버전 문자열만 교체**하면 된다.
- 최신 버전: `6.1.200` — pdf.js는 v4부터 **UMD(non-module) 빌드를 완전히 제거**하고 ES 모듈(`.mjs`)만 배포한다. 적용하려면 `layout.tsx`의 스크립트 태그를 `type="module"`로 바꾸고 `import * as pdfjsLib from '.../pdf.min.mjs'` 후 `window.pdfjsLib`에 다시 붙여줘야 하며, worker 경로도 `.mjs`로 바뀐다. 즉 이 경로는 로딩 방식 자체를 바꿔야 하는, 더 큰 변경이다.

### 장점

- 변경 범위가 작다(파일 2개, 버전 문자열/로딩 코드만).
- 서버 인프라·의존성 추가가 필요 없다.
- pdf.js 자체의 몇 년치 버그 수정을 그대로 받는다 — CCITT/JBIG2 디코더 관련 수정이 포함되어 있을 가능성이 높다.

### 단점 / 리스크

- **버전을 올린다고 반드시 이 특정 파일들의 hang이 고쳐진다는 보장이 없다.** 실제 샘플로 재현 테스트를 해봐야 확답 가능하다(3절에서 검증).
- v4+ 로 가면 ESM 전환이 필요해 `layout.tsx` 로딩 구조를 바꿔야 하고, 회귀 리스크가 커진다.
- 여전히 외부 CDN(cdnjs.cloudflare.com)에 의존한다 — CDN 장애/네트워크 차단 시 PDF 업로드 전체가 막히는 기존 리스크는 그대로 남는다(`12_REAL_FEATURE_IMPLEMENTATION_ROADMAP.md`에서 이미 지적된 사항).
- 클라이언트(사용자 브라우저)에서 렌더링하므로, 브라우저·기기 성능에 따라 여전히 느리거나 불안정할 수 있다.

## 3. 후보 B — PDF→이미지 변환을 서버로 이전

### 개요

`ImageUploadPanel.tsx`가 브라우저에서 pdf.js로 페이지를 렌더링하는 대신, PDF 파일을 그대로(또는 페이지 단위로) 서버에 업로드하고, 서버에서 안정적인 PDF 렌더링 라이브러리(예: `pdfium`/`mupdf` 기반 Node 바인딩, 또는 별도 렌더링 서비스)로 페이지를 이미지로 분할한다. `04_OCR_FORM_RECOGNITION_SPEC.md`와 `12_REAL_FEATURE_IMPLEMENTATION_ROADMAP.md`가 이미 "작업 방향 B: 백엔드 전환"으로 언급했던 방향이다.

### 장점

- 서버 측 PDF 렌더링 라이브러리(poppler/mupdf/pdfium 계열)는 브라우저 pdf.js보다 실제 스캔 문서·팩스 압축 이미지 처리에 대해 훨씬 성숙하고 검증된 경우가 많다.
- 외부 CDN 의존을 완전히 제거한다.
- 사용자 기기 성능과 무관하게 서버가 일관된 환경에서 처리한다.
- 향후 조기개입 감지, ROI 보정 등 서버 로직과 한 파이프라인에서 처리하기 쉬워진다.

### 단점 / 리스크

- 새 서버 의존성이 필요하다. Vercel 서버리스 환경에서 무거운 네이티브 PDF 렌더링 라이브러리를 안정적으로 구동할 수 있는지 별도 검증이 필요하다(바이너리 크기, 콜드 스타트, 함수 실행 시간 제한 등).
- 변경 범위가 크다 — 업로드 API, 작업 흐름, 관련 테스트를 전반적으로 다시 손봐야 한다.
- 구현·검증에 시간이 더 걸린다.

---

## 4. 진행 방향

후보 A부터 시도한다(변경 범위가 작고, 되면 가장 빠르게 문제를 해결할 수 있음). 3.11.174로 먼저 시도하고, 실제 샘플 PDF로 재현 테스트해 통과 여부를 확인한다. 실패하면 v6 ESM 전환까지 시도해본 뒤, 그래도 해결되지 않으면 후보 B(서버 전환)로 넘어간다.

테스트 결과는 `Docs/16_PDF_FIX_CANDIDATE_A_TEST_RESULTS.md`에 기록한다.

별도로, 근본 해결과 무관하게 `convertPdfToImages()`에 페이지별 타임아웃과 사용자에게 보이는 실패 메시지를 추가하는 방어 코드는 후보 선택과 무관하게 진행해야 한다(이 문서의 범위 밖, 별도 작업).
