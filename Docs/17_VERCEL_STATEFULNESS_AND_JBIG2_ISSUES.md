# VERCEL_STATEFULNESS_AND_JBIG2_ISSUES — 2026-08-02 배포본 재현 테스트에서 확인된 문제 2건

`fix/pdf-batch-render-hang` PR #3의 실제 Vercel 프리뷰에서 사용자가 직접 재현한 화면을 바탕으로 조사한 결과, **서로 다른 두 가지 문제**가 확인됐다. 하나는 이번 PR이 고치려던 문제와 무관한 기존 아키텍처 문제(세션/파일 저장), 다른 하나는 이번 PR의 pdf.js 업그레이드가 완전히 고치지 못한 잔존 버그(JBIG2 디코딩)다.

## 1. [확인됨] Vercel 서버리스 인스턴스 간 로컬 파일 미공유 — 저장 버튼까지 영향

### 증상
- crop 미리보기 이미지 클릭 시 `{"error":"작업 세션이 존재하지 않습니다."}` (404)
- 브라우저 콘솔에 `/api/uploads/crop`, **`/api/students`(검수 완료 및 엑셀 반영 버튼)** 모두 404 다수 발생

### 원인
`src/lib/storage/jobStore.ts`와 `src/lib/excel/templateManager.ts`가 작업 세션·업로드 이미지·작업용 엑셀 사본을 전부 `os.tmpdir()` (로컬 디스크)에만 저장한다. Vercel 서버리스 함수는 요청마다 다른 인스턴스로 처리될 수 있고, 각 인스턴스의 `/tmp`는 서로 공유되지 않는다. 작업을 만든 인스턴스가 아닌 다른 인스턴스가 이후 요청(crop 미리보기, 저장, 다운로드)을 받으면 그 인스턴스엔 파일이 아예 없어 404가 난다.

이 문제는 이미 `Docs/14_PREVIEW_DEPLOYMENT_QA_2026-08-01.md`에서 "다운로드 실패" 사례로 문서화했었는데, 이번에 **핵심 저장 버튼(`/api/students`)까지 동일하게 영향받는다는 게 재확인**됐다. 즉 단순 미리보기 문제가 아니라 앱의 핵심 기능이 Vercel 배포본에서 비결정적으로 완전히 막힐 수 있는 치명적 문제다.

### 개선 방향 (택 1)

**방향 A. 클라이언트를 진실의 원천으로 삼는 무상태(stateless) 재설계 (권장)**

- 확정된 학생 목록은 이미 클라이언트(`page.tsx`의 `students` state)가 들고 있다. 서버가 `session.students`를 별도로 누적 관리하지 않고, **저장/다운로드 요청마다 클라이언트가 확정된 학생 전체 목록을 함께 보내면, 서버는 매번 원본 템플릿(레포에 내장되어 모든 인스턴스에 항상 존재)에서 시작해 전체 목록을 다시 써서 반환**한다.
- 업로드 이미지의 crop/원본 미리보기도 서버에 남은 파일에 의존하지 말고, **클라이언트가 이미 갖고 있는 File 객체를 이용해 브라우저에서 직접 미리보기·crop을 그린다**(서버 재조회 자체가 불필요해짐).
- 장점: 새 유료/설정 필요한 외부 저장소가 전혀 필요 없다. 각 요청이 독립적이라 지금 `withJobLock`으로 막고 있는 행 번호 경쟁 문제도 구조적으로 사라진다. 지금 규모(강사 1명, 학생 수십 명)에 적합하다.
- 단점: `/api/students`, `/api/download`, crop/이미지 미리보기, 클라이언트 상태 관리 로직을 함께 손봐야 하는 중간 규모 리팩터링이다. 새로고침 시 진행 중 작업이 사라지는 건 기존과 동일(원래도 서버 세션 기반이라 다르지 않음).

**방향 B. Vercel Blob Storage 등 외부 공유 저장소 도입**

- 업로드 이미지·작업용 엑셀 사본·세션 메타데이터를 인스턴스 간 공유되는 외부 저장소(Vercel Blob 등)로 옮긴다.
- 장점: 현재 아키텍처(서버가 세션을 계속 들고 있는 모델)를 크게 바꾸지 않고 저장 위치만 바꾸는 것이라 개념적으로 단순하다.
- 단점: **Vercel 대시보드에서 Blob Store를 만들고 프로젝트에 연결하는 수동 설정이 필요**하다(이 환경에는 `vercel` CLI가 없어 코드만으로는 자동 프로비저닝이 불가능함을 확인함). 로컬 개발 환경과 배포 환경의 저장 방식이 갈라져(로컬은 파일시스템 폴백 필요) 코드가 더 복잡해진다.

### 권장
방향 A(무상태 재설계)를 권장한다. 새 인프라 없이 근본 원인을 없애고, 지금 앱의 실제 사용 규모에 더 잘 맞는다.

## 2. [신규 확인] pdf.js 6.1.200도 일부 실제 스캔 페이지에서 JBIG2 디코딩에 멈춤 — 이전 수정이 불완전했음

### 증상
브라우저 콘솔에 다음이 반복 출력됨:
```
Warning: Unable to decode image "img_p6_1": "JBig2Error: JBig2 failed to initialize".
Warning: Dependent image isn't ready yet
... (img_p7_1 ~ img_p18_1까지 반복)
```

### 재현 (직접 확인)
PR #3에서 "38페이지 전부 13ms 내외로 렌더링 성공"이라고 확인했던 건 **1페이지만 반복 테스트**한 결과였다. 이번에 같은 파일(`선별검사 샘플1.pdf`)의 **6페이지를 단독으로 렌더링**해보니:

```
page.render() 호출 → 50초 이상 응답 없음 (완전히 멈춤, 타임아웃 아님)
```

즉 **pdf.js 6.1.200으로 올린 것으로 "PDF 렌더링 멈춤" 문제가 전부 해결된 게 아니라, 우연히 1페이지가 JBIG2 압축 이미지를 안 쓰는 페이지라 통과했을 뿐**이고, 6페이지처럼 JBIG2로 인코딩된 이미지가 포함된 페이지는 여전히 멈춘다. `Docs/16_PDF_FIX_CANDIDATE_A_TEST_RESULTS.md`의 "38페이지 전부 성공" 결론은 이번 재검증으로 **정정이 필요**하다.

### 이게 왜 "낮은 신뢰도" 문제와도 연결될 수 있는가
지금까지 실제 촬영/스캔 샘플에서 인식 신뢰도가 거의 다 "낮음"으로 나오는 걸 "ROI 좌표가 실제 샘플 기준으로 안 맞아서"로만 설명해왔다. 그런데 JBIG2 디코딩이 실패하면 pdf.js는 해당 이미지를 제대로 못 그리고(빈 화면이거나 깨진 이미지) 넘어갈 수 있다 — 이 경우 서버로 올라가는 JPEG 자체가 처음부터 내용이 없거나 손상된 상태일 수 있고, ROI 인식이 낮게 나오는 게 순수 좌표 튜닝 문제가 아니라 **애초에 원본 이미지 변환 자체가 실패한 결과**일 가능성이 있다. (다만 타임아웃으로 막힌 페이지는애초에 서버로 전송조차 안 됐을 것이므로, 정확히는 "타임아웃에 걸리지 않고 조용히 빈 이미지로 넘어간 페이지들"에 한해 해당하는 가설이다.)

### 개선 방향
pdf.js는 순수 JS로 구현된 자체 JBIG2 디코더를 쓰는데, 이번에 문제가 된 이미지처럼 특정 스캐너가 만드는 JBIG2 인코딩 방식에서 알려진 취약점이 있는 것으로 보인다. CDN 버전을 더 올리는 걸로 해결될지는 추가 확인이 필요하며, **더 근본적인 해결은 애초에 문서에 후보 B로 적어뒀던 "PDF→이미지 변환을 서버 쪽의 더 성숙한 라이브러리로 이전"** 이다(poppler/mupdf/pdfium 계열은 JBIG2를 포함한 스캔 이미지 코덱을 훨씬 안정적으로 지원하는 경우가 많다). 이건 새 라이브러리 조사·검증이 필요한 별도 작업 규모라, 이번 저장소 문제 수정과 분리해서 다음 작업으로 남겨둔다.

이번 타임아웃 방어 코드(`src/lib/pdf/withTimeout.ts`)는 여전히 유효하다 — 최소한 "영원히 멈춘 것처럼 보이는" 상황은 20초 후 명확한 오류로 바뀐다. 다만 이건 증상 완화이지 근본 해결은 아니라는 점을 다시 확인한 것이다.
