# 26. 항목 인식 방식 재설계 검토

## 배경

지금까지 확인된 인식 정확도 문제(CAGI04·문항7 등 "높음" 배지인데 실제론 틀림)의 근본 원인은 아직 픽셀 단위로 확정하지 못했지만(사용자의 ROI 확인 스크린샷 대기 중), 현재 방식의 구조적 한계는 명확하다:

- `src/lib/recognition/roiTemplates.ts`에 **고정된 정규화 좌표**(0~1 비율)로 각 문항·보기의 위치를 하드코딩해두고,
- `src/lib/recognition/markDensity.ts`의 `detectContentBounds`/`detectFrameBounds`로 종이 경계를 추정한 뒤 그 좌표를 적용해,
- 해당 작은 영역의 "어두운 픽셀 비율"만으로 체크 여부를 판정한다.

이 방식은 (1) 종이 경계 추정이 틀리면 좌표 전체가 밀려서 엉뚱한 곳을 찍고, (2) 경계가 맞아도 인쇄된 원문자(⓪①②③) 위에 옅게 겹쳐 그린 체크 표시처럼 신호가 약한 필기 스타일에서는 후보 간 점수 차이가 거의 없어진다는 두 가지 실패 지점이 있다. 사용자가 제안한 방향은 이 구조 자체를 바꾸는 것이다: **고정 좌표 대신, 이미지 자체에서 표/문항 영역을 검출해 계층적으로 작게 쪼갠 뒤 개별적으로 인식**하는 방식.

## 검토한 방식

### A. 고전 CV 기반 동적 구조 검출 (사용자 제안과 가장 가까운, 외부 의존성 없는 버전)

OpenCV(이미 원근보정에 도입됨, Docs/21)의 선/윤곽선 검출 기능으로 각 이미지에서 **실제 표 격자선을 직접 찾아** 행·열 경계를 계산하고, 그 경계를 기준으로 각 문항·보기 셀을 크롭한다. 고정 비율 좌표에 의존하지 않으므로 종이 위치·스케일이 조금 달라도 강건하다. 셀 하나하나를 잘라낸 뒤에는 지금과 비슷한 방식(어두운 픽셀 비율 비교)으로 판정하거나, 더 나아가 작은 이미지 분류기를 둘 수도 있다.

- 장점: 서버·클라이언트 어디서든 자체 처리 가능, 외부 API 비용 없음, **학생 개인정보(도박문제 선별검사 응답 포함)가 외부로 전혀 나가지 않음** — 지금 PRD의 개인정보 요구사항([[00_PRD]] 10장: "이미지 임시 저장 후 삭제", "원본 이미지 다운로드 제한")과 정합성 유지.
- 단점: "표 격자선을 안정적으로 찾는" 것 자체가 여전히 고전 CV의 난제이고(사진마다 선명도·대비가 다름), "인쇄 글자 vs 옅은 체크 표시" 신호 약함 문제는 셀을 정확히 잘라내도 그대로 남을 수 있다. 구현·튜닝에 반복적인 실제 데이터 검증이 많이 필요하다.

### B. 비전 언어 모델(예: Claude/GPT 계열 비전 API) 활용

각 학생의 선별검사지·만족도조사 이미지(또는 문항별로 크롭한 이미지)를 비전 모델에 보내 "몇 번에 체크되어 있는가"를 직접 물어보고 구조화된 응답을 받는다.

- 장점: 픽셀 밀도가 아니라 실제 시각적 이해를 사용하므로 체크·동그라미·X 등 필기 스타일 편차, 약한 신호, 기울어짐에 훨씬 강건할 가능성이 높다. 구현 자체는 API 호출 + 프롬프트 설계로 비교적 단순.
- **단점(중요, 정책 판단 필요)**: 이 서식에는 만14세 미만 포함 가능한 아동·청소년의 **도박문제 선별검사 응답, 성별·나이·학교 정보**가 담겨 있고, 실물 동의서에도 "개인정보의 수집 및 이용목적"이 명시되어 있다. 이 이미지를 외부 상업 API로 전송하는 것은 지금 PRD 10장이 전제하는 "자체 처리 후 삭제" 모델을 벗어나는 **새로운 데이터 흐름**이다. 법적 근거(개인정보보호법)나 기관 내부 정책상 허용되는지는 내가 판단할 수 없는 영역이라, 이 방향은 반드시 사용자/기관의 결정이 필요하다.
- 추가 고려사항: 건당 비용 발생(트래픽에 따라 누적), 네트워크 호출로 인한 지연 증가, 외부 서비스 장애 시 인식 기능 자체가 막힘.

### C. A+B 하이브리드

기본은 A(자체 처리)로 가되, 신뢰도가 낮게 나온 항목에 한해서만(예: 저신뢰 8개 이하일 때) 사용자 동의 하에 B를 보조적으로 쓰는 방식도 이론적으로는 가능하다. 다만 "일부만 외부로 보낸다"도 정책적으로는 "외부로 보낸다"와 동일한 결정이 필요해서, B의 정책 이슈가 그대로 남는다.

## 권장

**A(자체 처리, 동적 구조 검출)를 우선 방향으로 권장한다.** 이유:
1. 지금 이 프로젝트의 모든 처리(엑셀 생성, 이미지 크롭, 양식 판정)가 외부 API 없이 자체 완결적으로 설계되어 있고, PRD의 개인정보 요구사항도 그 전제 위에 쓰여 있다.
2. 아동·청소년의 민감한 검사 응답 데이터를 다루는 서비스라 외부 전송 도입은 기술적 판단이 아니라 기관의 정책 결정 사항이다.

**B(비전 API)는 정확도 개선 잠재력이 가장 크지만, 위 개인정보 이슈에 대한 명확한 답 없이는 구현에 착수하지 않는다.**

## 다음 단계

- A 방향으로 진행할지, B(또는 하이브리드)를 실제로 검토할지 사용자 확인 필요.
- A로 진행 시: 먼저 실제 문제 이미지의 ROI 확인 스크린샷으로 정확한 실패 지점(좌표 오정렬 vs 신호 약함)을 확인한 뒤, 그에 맞는 동적 구조 검출 설계를 구체화한다(지금 바로 설계를 확정하기보다, 실패 원인을 알아야 어떤 구조 검출이 필요한지 정확히 설계할 수 있음).
