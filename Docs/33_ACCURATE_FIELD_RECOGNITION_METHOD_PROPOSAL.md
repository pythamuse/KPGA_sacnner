# 33. 정확한 항목 인식을 위한 보정 방법 제안

## 배경 정리

지금까지 확인된 사실들을 종합한다:

1. **확정된 근본 원인** ([[27_ROI_MISALIGNMENT_CONFIRMED_ROOT_CAUSE_AND_FIX]]): 오인식은 "체크 표시 신호가 약해서"가 아니라, 페이지 경계 추정(`markDensity.ts`의 `detectContentBounds`/`detectFrameBounds`)이 틀려서 고정 비율 좌표가 완전히 엉뚱한 행(예: 4번 문항이 8~9번 문항 라벨을 찍음)이나 섹션(예: 7~9번 문항이 페이지 맨 아래 동의서 텍스트를 찍음)을 가리키는 것이었다.
2. **클라이언트 원근보정(OpenCV.js + Web Worker)**은 만들었고 화면 멈춤 문제는 해결했지만([[29]]~[[32]]), 실제로 보정이 성공하는지는 아직 확인 못했다 — 로컬 테스트에서는 매번 타임아웃으로 폴백됐다. 이 경로는 브라우저 WASM/Worker 특성상 원인 규명도, 디버깅도 어려웠다(이번 세션에서 두 번의 심각한 배포 사고를 겪음).
3. **정책 결정** ([[26_RECOGNITION_ARCHITECTURE_REDESIGN_OPTIONS]]): 외부 비전 API는 학생 개인정보(도박 선별검사 응답) 유출 문제로 배제, 자체 처리(A안)로 확정했다.

## 제안: 서버 사이드 동적 표 구조 검출로 전환/보강

### 핵심 아이디어

지금 좌표 시스템은 "페이지 경계를 한 번 추정하고, 그 안에서 고정 비율(%) 좌표로 각 문항 위치를 계산"하는 방식이다. 이 방식은 페이지 경계 추정 하나가 틀리면 그 아래 모든 좌표가 연쇄적으로 틀린다 — 실제로 확인된 실패 패턴과 정확히 일치한다.

대신 **각 이미지에서 실제 표 구분선(가로줄)을 직접 찾아서, 그 검출된 선의 실제 위치를 문항 좌표로 사용**하도록 바꾼다. 페이지 전체의 "추정된 경계" 하나에 모든 걸 의존하지 않고, 표 자체의 구조를 그 이미지 안에서 직접 읽어내는 방식이다.

### 왜 이 방법인가 (다른 후보와 비교)

| 방법 | 개인정보 외부 유출 | 구현/디버깅 난이도 | 근본 원인과의 직접 연관성 |
|---|---|---|---|
| **A. 서버 사이드 표 구조 동적 검출 (제안)** | 없음 | 낮음 — Node.js + `sharp`만 사용, 이미 `markDensity.ts`에 있는 것과 같은 방식의 픽셀 분석을 확장하는 수준 | 높음 — 확정된 원인(페이지 경계 오추정)을 직접 해결 |
| B. 클라이언트 OpenCV.js 원근보정 계속 붙잡기 | 없음 | 높음 — WASM/Worker 특성상 원인 불명 버그를 이번에 두 번 만남, 계속 디버깅 리스크 있음 | 간접적 — 페이지 "전체 기울기"는 바로잡지만 표 내부 좌표 오정렬은 별개 문제일 수 있음(실제 실패 사례는 원근보정 없이도 발생) |
| C. 외부 비전 API | **있음 (배제됨)** | 낮음 | 높음 |

**A안을 우선 제안한다.** 이유:
- 확정된 원인을 가장 직접적으로 겨냥한다.
- 이번 세션에서 브라우저/WASM/Worker 쪽 작업이 두 번의 심각한 배포 사고(완전 화면 정지)를 냈고, 원인 규명에 시간이 많이 들었다. 반면 서버 사이드 픽셀 분석은 순수 Node.js 로직이라 **브라우저 자동화 없이 직접 스크립트로 실제 샘플 이미지에 돌려보면서 빠르게 반복 검증**할 수 있다 — 이번 세션에서 계속 확인됐듯, 실제 데이터로 직접 검증할 수 있는 방법이 신뢰도가 훨씬 높다.
- 기존에 만든 클라이언트 원근보정(Worker 격리, 이제 안전함)은 **폐기하지 않고 1차 보정 단계로 그대로 둔다** — 전체적인 기울기·원근 왜곡을 줄여주는 역할은 여전히 유효하다. 이번 제안은 그 위에 "표 내부 정밀 위치 찾기"라는 2차 보정을 추가하는 것이지, 대체하는 게 아니다.

### 구체적 접근 (개략)

1. **가로 투영 프로파일(horizontal projection profile)**: 이미지의 각 행(row)마다 어두운 픽셀 비율을 계산한다. 표의 구분선(각 문항 사이 가로줄)은 이 프로파일에서 뚜렷한 피크로 나타난다. 지금 `detectFrameBounds`도 같은 원리를 쓰지만, "가장 위/가장 아래 선만" 찾아 하나의 사각형 경계로 쓰는 데 그친다 — 이걸 **모든 가로줄을 찾아 그 사이 간격들을 각 문항 행의 실제 경계로 사용**하도록 확장한다.
2. 검출된 선의 개수·간격 패턴을 `roiTemplates.ts`에 이미 정의된 문항 구조(CAGI 9문항 = 7문항 + 2문항 서로 다른 보기 그룹, 만족도 3개 하위 표)와 매칭해서, "이 선이 몇 번 문항의 경계다"를 판별한다.
3. 판별된 실제 픽셀 위치를 각 문항의 크롭 좌표로 사용해 지금과 동일한 어두운 픽셀 밀도 비교를 수행한다(이 부분 로직 자체는 안 바꾼다 — 오직 "어디를 크롭할지 결정하는 방식"만 바꾼다).

### 검증 계획

사용자가 이미 제공한 실제 두 장(CAGI, 만족도)을 기준으로, Node 스크립트로 직접 돌려서 각 문항 크롭이 실제로 맞는 위치를 찍는지 확인한 뒤 서버에 반영한다. 브라우저 테스트 없이도 정확도를 먼저 검증할 수 있다는 게 이 방법의 실질적 장점이다.
