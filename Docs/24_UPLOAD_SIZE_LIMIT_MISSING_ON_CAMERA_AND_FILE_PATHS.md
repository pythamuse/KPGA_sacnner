# 24. 카메라/파일 업로드 경로에 용량 초과 방어 로직 누락

## 증상

컴퓨터 웹 환경에서 실제 촬영된 사진(약 5MB, JPG)을 "파일 선택"으로 직접 업로드했을 때 다음 에러가 떴다:

> 파일 업로드 실패: 업로드 파일 용량이 너무 큽니다. PDF를 더 낮은 해상도로 변환한 뒤 다시 시도해주세요.

업로드한 파일은 PDF가 아니라 일반 이미지 파일인데도 메시지가 PDF를 가정하고 있어 혼란을 준다.

## 원인

**(1) 413의 실제 원인**: `src/app/api/upload/route.ts`에는 자체 용량 체크 로직이 없다. 413은 Vercel 서버리스 함수(Node.js 런타임)의 **요청 본문 크기 제한(기본 4.5MB)** 에 걸려 Next.js 라우트 코드가 실행되기도 전에 플랫폼에서 반환하는 응답이다.

**(2) 방어 로직이 한쪽에만 있음**: `src/components/ImageUploadPanel.tsx`를 보면, PDF를 이미지로 변환하는 경로(`convertPdfToImages` → `renderPdfPageToFile`)에만 용량 안전장치가 있다 — `MAX_UPLOAD_IMAGE_BYTES`(3.8MB)를 넘으면 `PDF_RENDER_OPTIONS` 배열(스케일·품질 3단계)로 순차 재시도해 용량을 줄인다. 그런데 다음 두 경로에는 이 안전장치가 전혀 없다:

- **"파일 선택"으로 이미지 직접 업로드** (`handleSequentialFileChange`, `handleBatchFileChange`) — 선택한 원본 파일을 그대로 업로드한다. 요즘 스마트폰 카메라 원본 사진은 수 MB~십수 MB가 흔하다.
- **카메라로 직접 촬영** (`captureCurrentFrame` → `uploadCapturedCanvas`) — `canvas.toBlob(resolve, 'image/jpeg', 0.92)`로 **품질 0.92 고정**, 용량이 크면 낮추는 로직이 없다. `getUserMedia`가 최대 1600×1200을 요청하고, OpenCV 보정 성공 시엔 그보다 더 큰 1422×1968(474×3, 656×3)까지 나올 수 있어(Docs/21, 22), 촬영 내용에 따라 이 경로에서도 같은 413이 재현될 수 있다.

즉 지금 컴퓨터에서 겪은 문제는 우연이 아니라, **PDF 경로만 용량을 관리하고 나머지 두 경로(카메라 촬영, 이미지 직접 업로드)는 관리하지 않는 설계 공백**이다.

## 수정 방향 (코덱스에 위임할 작업)

1. 재사용 가능한 헬퍼 함수를 추가한다: `File`을 받아 `MAX_UPLOAD_IMAGE_BYTES`보다 크면 캔버스에 다시 그려 품질/해상도를 낮춰가며 재인코딩하고, 이미 그 이하 크기면 원본을 그대로 반환한다. `renderPdfPageToFile`의 `PDF_RENDER_OPTIONS` 재시도 패턴과 동일한 방식을 재사용한다.
2. 이 헬퍼를 **모든 업로드 경로의 공통 지점인 `uploadSingleFile`** 맨 앞에 적용해서, PDF·카메라·파일선택 세 경로 전부가 같은 안전장치를 거치도록 한다(PDF 경로는 이미 자체적으로 줄여서 오므로 헬퍼를 통과해도 그대로 통과됨, 중복이어도 무해함).
3. `uploadSingleFile`의 413 에러 메시지(`'업로드 파일 용량이 너무 큽니다. PDF를 더 낮은 해상도로 변환한 뒤 다시 시도해주세요.'`)를 PDF를 가정하지 않는 일반적인 문구로 바꾼다.
