# 35. 표 행(row) 탐지 기능 구현 검토 및 검증 결과

## 배경

[Docs/34](34_TABLE_ROW_DETECTION_WORK_ORDER.md)의 작업지시서에 따라 Codex가
`src/lib/recognition/tableRowDetection.ts`(신규), `markDensity.ts`,
`detectCheckmarks.ts`, `roiTemplates.ts` 변경과
`tests/table-row-detection.test.ts`(신규, 6개 테스트)를 구현했다. Codex 자체
보고 기준 `npm test`(당시 기준 전체) 및 `npm run build` 통과.

이 문서는 그 결과물에 대한 내 자체 코드 리뷰와, 리뷰 중 발견한 설계 리스크에
대한 실증적 검증(synthetic 이미지 기반) 결과를 기록한다.

## 코드 리뷰 결과

전반적으로 작업지시서의 요구사항을 충실히 따랐다:

- CAGI/satisfaction의 예상 간격 패턴이 `roiTemplates.ts`의 기존
  `cagiQuestionYs`/`cagiLateQuestionYs`/`satisfactionBinaryYs`/`satisfactionScaleYs`
  배열에서 직접 계산되며, 별도로 하드코딩된 배열이 없다 (하드코딩 시 발생할
  수 있는 데이터 drift 방지 요구사항 충족).
- `calculateDarkPixelDensity`의 `yOverride`는 Y축에만 영향을 주고, X축
  (`left`/`right`)은 기존 `contentBounds` 기반 계산에서 전혀 변경되지 않았다.
- 매칭 실패/비신뢰 시 항상 빈 객체 `{}`를 반환하여 기존 동작으로 안전하게
  폴백한다 (`satisfaction.q01`은 애초에 매칭 대상에서 제외).
- 순수 Node.js/TypeScript 로직으로, 브라우저 API나 OpenCV/Worker에 전혀
  의존하지 않는다.

## 리뷰 중 발견한 설계 리스크

`buildCagiRowOverrides`/`buildSatisfactionGroupOverrides`는 이미지에서 감지한
가로선들을 `roiTemplates.ts`의 문항 Y 좌표(각 문항 응답 칸의 **행 중심**
위치)에서 유도한 간격 패턴과 매칭한다. 그런데 실제 촬영된 설문지에서
안정적으로 감지 가능한 가로선은 대개 표의 **행 경계(구분선)** 이지, 행
중심이 아닐 가능성이 높다. 이 경우 감지된 선들의 간격 패턴이 템플릿의
행-중심 간격 패턴과 체계적으로 다르게 나타날 수 있다.

## 검증 방법

실제 촬영 이미지를 파일로 확보할 수 없어(채팅에 붙여넣은 스크린샷만 존재),
synthetic 이미지로 두 가지를 검증했다:

1. **완전 경계선 케이스**: 9개 문항의 행 경계(연속된 두 문항 중심의 정확한
   중점)에 가로선을 그리고, 각 문항 중심에는 표시(마킹)를 그린 이미지를
   생성하여 `buildCagiRowOverrides`를 실행.
2. **민감도 스캔**: 가로선을 행 중심에서 다음 행 쪽으로 0%~50%까지 5%
   간격으로 이동시키며 `matchRowPattern`이 매칭에 성공하는 임계값을 측정.

## 결과

- **완전 경계선 케이스**: `buildCagiRowOverrides`가 빈 객체 `{}`를 반환했다
  (매칭 실패 → 오버라이드 없음 → 기존 동작 그대로 사용). 오답 오버라이드가
  적용되는 일은 없었다 — 안전 요구사항(Docs/34 3번)이 실제로 지켜짐을 확인.
- **민감도 스캔**: offset 0~20%(행 간격 대비)까지는 매칭 성공, 25% 이상부터는
  매칭 실패(폴백)로 전환됨을 확인. 즉 이 알고리즘은 감지된 선이 템플릿
  행-중심 위치에서 최대 약 20% 이내로 근접할 때만 오버라이드를 적용하고,
  그 이상 벗어나면(완전한 행-경계선 포함) 항상 안전하게 아무 것도 하지
  않는다.

## 조치

위 리스크에 대한 방어적 완화로 `buildOverridesFromRowCenters`의 크롭 여백
배수를 `interval * 0.3` → `interval * 0.45`로 넓혔다 (매칭이 성공한 경우,
중심에서 다소 벗어난 실제 마크 위치까지 크롭 범위가 포함되도록). 이에 따라
`tests/table-row-detection.test.ts`의 하드코딩된 기대값 3개
(`cagi.q01`/`q08`/`q09`)를 재계산된 실제 값으로 갱신했다.

`matchRowPattern`의 `toleranceRatio`(0.35)는 의도적으로 건드리지 않았다.
이를 완화하면 20~50% 범위의 오프셋에서도 매칭이 "성공"하게 만들 수는
있지만, 이는 실제로 심각하게 잘못 정렬된 사진(이번 세션 앞부분에서 확인된
진짜 오작동 사례들)에서도 거짓 매칭을 유발할 위험이 있어, Docs/34가 명시한
"애매하면 무조건 아무 것도 하지 않는다" 원칙에 반한다.

## 결론 및 남은 리스크

- **안전성**: 실증적으로 확인됨. 매칭이 불확실한 경우 항상 폴백하며, 잘못된
  오버라이드가 적용되는 사례를 재현하지 못했다.
- **효과(실제 정확도 개선 여부)**: 미검증. 실제 설문지 사진에서 안정적으로
  감지되는 가로선이 문항 행 중심에서 20% 이내에 위치하는지는 실제 이미지
  없이는 확인할 수 없다. 만약 실제 양식의 구분선이 행 경계에 가깝다면, 이
  기능은 (안전하게) 거의 활성화되지 않고 기존의 미해결 오정렬 문제가 여전히
  남을 수 있다.
- **다음 단계**: 배포 후 실제 사용자의 촬영/업로드 이미지로 재검증 필요.
  가능하다면 실패했던 실제 ROI 사례(Docs/27의 스크린샷 근거 이미지)로
  `buildCagiRowOverrides`가 오버라이드를 실제로 생성하는지, 생성한다면
  올바른 위치인지 직접 확인하는 것이 가장 확실한 검증 방법이다.
