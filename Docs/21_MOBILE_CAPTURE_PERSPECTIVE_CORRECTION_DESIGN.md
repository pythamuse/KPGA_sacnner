# 21. 모바일 촬영 원근 보정 설계

## 1. 문제 재정의

인식/양식판정 파이프라인(`classifyForm`, `recognizeStudentForms`)은 텍스트를 전혀 읽지 않는다. CAGI/만족도 각 양식마다 체크박스가 있어야 할 위치를 **정규화 좌표(0~1 비율)** 로 하드코딩해두고, 감지한 종이 경계(`contentBounds`) 안에서 그 좌표의 어두운 픽셀 비율만 측정한다 ([Docs/20](20_MOBILE_PHOTO_FORM_MISCLASSIFICATION_FIX.md)에서 확인). 이 방식은 스캐너·PDF처럼 원근 왜곡이 없고 종이가 프레임 전체를 채우는 이미지에서만 신뢰할 수 있다.

그런데 "개별/순차 촬영" 모드의 카메라 캡처(`src/components/ImageUploadPanel.tsx`의 `captureCurrentFrame`)는:

- 화면의 점선 가이드가 **순수 시각적 안내일 뿐**이고 실제로는 `drawImage(video, 0, 0, width, height)`로 비디오 프레임 전체(배경 포함)를 그대로 캡처한다.
- 사람이 손으로 든 카메라로는 원근 왜곡 없이, 종이 네 변에 정확히 맞춰 촬영하는 것이 현실적으로 불가능하다.
- 종이 경계 감지(`detectFrameBounds`)는 "길게 이어지는 어두운 픽셀 행/열"을 찾는 단순 휴리스틱이라, 배경 물체·표 안쪽의 격자선 등을 오탐지할 수 있다. 이 경우 확신을 갖고 잘못된 좌표를 계산한다.

결론: **좌표 기반 인식 자체는 그대로 두더라도, 그 좌표가 적용되는 입력 이미지를 "촬영 시점에" 왜곡 보정된 정면 이미지로 만들어주지 않는 한 근본적으로 불안정하다.** 이번 설계는 입력 이미지를 보정하는 새 단계를 추가하는 것을 다룬다.

## 2. 검토한 방식

### A. 자체 구현 엣지/코너 검출 + 투영 변환
Sobel/Canny류 엣지 검출과 Hough 변환으로 종이의 네 꼭짓점을 직접 찾고, 호모그래피 행렬을 계산해 보정한다.
- 장점: 외부 의존성 없음.
- 단점: 이 자체가 OpenCV가 이미 잘 풀어놓은 문제를 처음부터 다시 구현하는 것과 같다. 정확도·엣지케이스 대응이 검증된 라이브러리보다 훨씬 떨어질 위험이 크고, 디버깅 비용이 큼. **비권장.**

### B. OpenCV.js(WASM)로 클라이언트에서 보정 — 촬영 직후
`cv.Canny` → `cv.findContours` → 최대 사각형 컨투어 근사(`cv.approxPolyDP`) → `cv.getPerspectiveTransform` + `cv.warpPerspective`로 촬영 직후 브라우저에서 바로 보정.
- 장점: 문서 스캐너 앱들이 공통으로 쓰는 검증된 고전 CV 파이프라인. 촬영 직후 보정 결과를 사용자에게 바로 보여주고 확인/재촬영을 받을 수 있어 UX 안전장치가 자연스럽게 들어감. Vercel 서버리스에 새로운 네이티브 의존성을 추가하지 않음(이번 세션에서 Windows 샌드박스, PDF 워커, `/tmp` 무상태성 등 Vercel 관련 이슈를 여러 번 겪었기 때문에 서버 쪽에 새 WASM/네이티브 의존성을 얹는 것은 리스크가 큼).
- 단점: opencv.js 번들이 크다(수 MB). 카메라 촬영을 실제로 시작할 때만 지연 로드하면 완화 가능.
- **권장.**

### C. OpenCV.js로 서버(API 라우트)에서 보정
업로드 직후 서버에서 동일한 파이프라인을 실행.
- 장점: 카메라 캡처·파일 업로드 두 경로 모두 동일하게 처리 가능.
- 단점: Vercel 서버리스 Node 런타임에서 WASM 모듈을 브라우저 밖 환경으로 구동해야 하고(콜드스타트 비용, 메모리/시간 제한), 이번 세션에서 이미 Vercel 특유의 예상 밖 이슈를 여러 차례 겪은 만큼 검증되지 않은 새 실패 지점을 서버에 추가하는 리스크가 있음. 또한 사용자가 보정 결과를 확인/재촬영할 기회가 없어 실패를 조용히 삼킬 위험.
- **1차 범위에서는 비권장** (후속 과제로 남김 — 파일 업로드 경로까지 넓히고 싶다면 재검토).

### D. ML 기반 문서 감지(예: TensorFlow.js 코너 검출 모델)
- 장점: 조명·배경이 복잡해도 강건할 수 있음.
- 단점: "책상 위 사각형 종이"라는 문제에 비해 과한 접근이고, 모델 크기·추론 비용·학습/파인튜닝 부담이 큼. 고전 CV(윤곽선 검출)로 충분히 풀리는 문제.
- **비권장.**

## 3. 채택안: B (클라이언트, 촬영 직후 OpenCV.js 보정 + 확인 단계)

### 3.1 파이프라인
1. 기존과 동일하게 `captureCurrentFrame`이 비디오 프레임을 캔버스에 그린다.
2. opencv.js를 지연 로드한다(카메라 흐름을 시작할 때 1회, `startCameraFlow`에서 트리거).
3. 캡처된 캔버스를 `cv.Mat`으로 변환 → 그레이스케일 → 블러 → `Canny` 엣지 검출 → `findContours` → 넓이가 가장 큰 사각형(4개 꼭짓점으로 근사되는 컨벡스 컨투어) 탐색.
4. 유효한 사각형을 찾으면: 네 꼭짓점을 좌상/우상/우하/좌하 순으로 정렬 → `getPerspectiveTransform` + `warpPerspective`로 `cagiTemplate`/`satisfactionTemplate`의 `baseSize` 비율(474:656)에 맞는 정면 사각형 이미지로 보정.
5. 보정 결과를 **미리보기로 사용자에게 보여주고 "이대로 사용" / "다시 촬영" 선택을 받는다** — 자동 감지가 항상 완벽할 수 없으므로, 다른 문서 스캐너 앱들처럼 확인 단계를 필수로 둔다.
6. 유효한 사각형을 찾지 못하면: 보정을 건너뛰고 **원본 프레임을 그대로 업로드**한다(현재 동작과 동일 — 새 기능이 실패해도 기존 대비 기능 저하가 없도록 항상 폴백).
7. 최종적으로 업로드되는 이미지(보정본 또는 원본 폴백)는 이후 서버 파이프라인(`classifyForm`, `recognizeStudentForms`)에 지금과 동일하게 들어간다 — **서버 쪽 코드는 변경하지 않는다.** 입력 이미지 품질을 촬영 단계에서 개선하는 것으로 문제를 해결한다.

### 3.2 적용 범위 (1차)
- **카메라 캡처 흐름만** 대상으로 한다(`captureCurrentFrame`). 이번에 실제로 문제가 보고된 경로이고, 스캐너/PDF 업로드 경로는 이미 원근 왜곡이 없어 대상이 아니다.
- "파일 선택"으로 이미 찍어둔 사진을 올리는 경로는 1차 범위에서 제외한다(후속 과제로 명시). 필요해지면 같은 보정 모듈을 파일 선택 direct-upload 흐름에도 재사용할 수 있도록 모듈을 독립적으로 설계한다.

### 3.3 실패 시 처리 원칙
- 보정 모듈 로드 실패, 사각형 미검출, 처리 시간 초과 등 어떤 이유로든 실패하면 **항상 원본 프레임 업로드로 자연스럽게 폴백**한다. 사용자를 막지 않는다.
- opencv.js 로드 자체가 오래 걸리는 저사양 기기 대비, 로딩 중에는 "화질 보정 준비 중" 같은 짧은 대기 상태만 보여주고, 일정 시간(예: 5초) 안에 준비되지 않으면 보정 없이 진행할 수 있게 한다.

### 3.4 구현 파일 계획
- `src/lib/documentScanner/loadOpenCv.ts`: opencv.js를 CDN에서 지연 로드하고 `window.cv` 준비를 기다리는 헬퍼(`<script>` 동적 삽입 + `cv['onRuntimeInitialized']` 대기, pdf.js처럼 `layout.tsx`에 정적으로 넣지 않고 카메라 흐름 시작 시점에만 로드).
- `src/lib/documentScanner/perspectiveCorrect.ts`: `detectDocumentQuad(canvas): Point[] | null`, `warpToRectangle(canvas, corners, outputWidth, outputHeight): HTMLCanvasElement` 등 opencv.js를 감싸는 순수 함수들.
- `src/components/ImageUploadPanel.tsx`: `captureCurrentFrame` 이후 보정을 시도하고, 보정 성공 시 확인/재촬영 미리보기 상태를 추가.

### 3.5 테스트 계획
- 단위 테스트로는 실제 카메라·opencv.js WASM 동작을 검증할 수 없다(jsdom/vitest 환경 한계). `detectDocumentQuad`/`warpToRectangle`의 순수 로직(예: 꼭짓점 정렬 함수)만 분리해 단위 테스트 가능하면 테스트를 추가한다.
- `npm test`, `npm run build`로 회귀 없는지 확인.
- **실기기 테스트가 필수**다 — 실제 조명·손떨림·각도 조건에서 보정이 실제로 오판정을 줄이는지는 사용자가 모바일에서 직접 재테스트해야 확인 가능하다.
