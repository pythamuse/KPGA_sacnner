# 문서 촬영 및 왜곡 보정 전략 검토

작성일: 2026-08-05  
검토 대상: `만족도조사.jpg`, `선별검사지.jpg` 및 인식 결과 화면  
목적: 현재 원근 보정만으로 해결되지 않는 촬영 왜곡에 대해 자동 촬영(A)과 외부 문서스캔 사례 기반 보정(B)의 적용 방향을 결정한다.

## 1. 결론

두 방식 중 하나만 선택하지 않고 **B를 기본 처리 파이프라인으로 강화한 뒤, A를 카메라 촬영 경로의 보조 기능으로 추가하는 혼합안**을 채택한다.

우선순위는 다음과 같다.

1. 파일 선택, 카메라, PDF 변환에 공통으로 적용되는 문서 경계 검출·보정·품질 검증을 안정화한다.
2. 카메라 미리보기에서는 낮은 해상도의 실시간 검출로 문서가 안정된 상태인지 판단한다.
3. 안정 상태가 일정 프레임 동안 유지될 때만 자동 촬영하고, 사용자가 수동 촬영할 수 있는 fallback을 유지한다.
4. 보정 신뢰도가 낮으면 잘못된 결과를 자동 업로드하지 않고, 원본과 네 모서리 수동 조정 화면을 제공한다.

**B만 적용하면 파일 업로드와 PDF까지 보호할 수 있지만 심하게 기울거나 흐린 원본을 사후에 복구하는 데 한계가 있다. A만 적용하면 카메라 입력의 품질은 좋아지지만 이미 저장된 사진과 PDF에는 적용되지 않고, 종이 휨과 경계 검출 실패를 해결하지 못한다.** 따라서 운영 입력 전체를 덮는 B와 촬영 품질을 높이는 A를 함께 사용해야 한다.

## 2. 샘플에서 확인된 문제

### 2.1 원본 이미지의 상태

- 두 원본 모두 문서 전체가 대체로 프레임 안에 들어오지만, 카메라가 문서 정면이 아니다.
- 종이의 좌우·상하 경계가 화면과 평행하지 않고, 가장자리의 명암이 배경과 충분히 분리되지 않는 부분이 있다.
- 만족도조사 이미지에는 하단 그림자와 종이의 미세한 휨이 있다.
- 선별검사지 이미지에는 큰 사각형 테이블과 문서 외곽선이 동시에 존재해, 단순히 가장 큰 사각형을 선택하는 방식이 내부 표 영역을 선택할 가능성이 있다.
- 손글씨, 체크 표시, 굵은 표 선, 지워진 흔적은 외곽선 검출을 방해할 수 있다.

### 2.2 결과 화면에서 확인된 증상

결과 화면에는 원본 이미지가 보존되어 있으나, 기본정보 일부가 비어 있거나 잘못 선택되고 CAGI 문항 crop이 실제 문항 행과 일치하지 않는 증상이 보인다. 이는 체크 표시를 조금 잘못 읽은 문제가 아니라, 문서 좌표계가 실제 종이 좌표계와 맞지 않은 상태에서 고정 ROI를 적용한 문제로 분류한다.

따라서 인식 단계의 임계값만 조정해서는 충분하지 않다. 먼저 문서 사각형과 좌표 변환의 신뢰도를 검증해야 한다.

## 3. 현재 코드의 처리 방식과 한계

현재 파일 선택 경로와 카메라 경로는 다음과 같이 동작한다.

```text
원본 이미지 또는 카메라 프레임
  -> 긴 변 최대 1600px 감지용 캔버스
  -> Web Worker의 OpenCV.js
  -> 그레이스케일, Gaussian blur, Canny, contour 검출
  -> 면적이 가장 큰 convex 4점 사각형 선택
  -> 고정 크기 캔버스로 homography warp
  -> 사용자 확인 후 업로드
```

관련 구현은 다음과 같다.

- `src/components/ImageUploadPanel.tsx`
  - `processSelectedFile()`과 `captureCurrentFrame()`에서 같은 보정 요청을 사용한다.
  - `PERSPECTIVE_CORRECTION_ENABLED`가 `true`이다.
  - 보정 결과가 있으면 확인 미리보기를 띄우고, 사용자가 `이대로 사용`을 눌러야 업로드한다.
- `src/lib/documentScanner/perspectiveCorrect.worker.ts`
  - OpenCV.js를 Worker에서 로드한다.
  - Canny와 contour에서 가장 큰 convex quadrilateral을 선택한다.
  - 선택된 네 점을 `474 * 3` x `656 * 3` 크기의 템플릿으로 투영한다.
- `src/lib/documentScanner/perspectiveCorrect.ts`
  - `orderQuadPoints()`가 점의 합과 차이를 이용해 네 모서리를 정렬한다.

현재 방식의 구조적 한계는 다음과 같다.

1. **가장 큰 사각형이 문서 외곽이라는 보장이 없다.** 문서 내부의 큰 표, 박스, 테이블 선이 더 선명하면 내부 사각형이 선택될 수 있다.
2. **단일 `epsilon`과 Canny 임계값에 의존한다.** 그림자, 반사, 낮은 대비, 손글씨, 지워진 선에 민감하다.
3. **검출 결과에 충분한 품질 점수가 없다.** convex 4점이 하나만 나오면 각도, 종횡비, 가장자리 연속성, 템플릿과의 일치 여부가 부족해도 보정 결과로 사용된다.
4. **homography는 평면의 투영 왜곡을 보정하는 수학이다.** 종이가 휘거나 접힌 비평면 왜곡, 렌즈의 방사 왜곡, 가려진 모서리를 복원하지 못한다.
5. **촬영 전 안정성 검사가 없다.** 현재 카메라는 사용자가 버튼을 누른 순간의 한 프레임만 분석한다. 문서가 흔들리는지, 네 모서리가 모두 보이는지, 화면 안에서 충분히 큰지 미리 확인하지 않는다.
6. **보정 실패 시 원본으로 폴백한다.** 기능 중단을 막는 데는 안전하지만, 원본 좌표가 신뢰할 수 없는 상태로 인식 단계에 넘어갈 수 있다. 폴백은 자동 확정이 아니라 재촬영 또는 수동 crop으로 연결되어야 한다.

## 4. 방식 A 검토: 안정 상태 자동 촬영

### 기대 효과

- 문서가 화면 밖으로 잘린 순간, 심하게 흔들리는 순간, 기울기가 큰 순간을 촬영하지 않을 수 있다.
- 촬영 직전부터 문서 외곽선을 보여주면 사용자가 문서를 프레임 안에 맞추기 쉽다.
- 최종 보정에 필요한 네 모서리의 관측 품질이 좋아져 B의 성공률도 함께 높아진다.

### 필요한 구현

실시간 영상 전체 해상도에 OpenCV를 매 프레임 적용하면 모바일 브라우저가 느려질 수 있으므로, 다음 구조가 필요하다.

1. 비디오에서 긴 변 320~640px 수준의 감지 프레임을 만든다.
2. 초당 5~10회 이하로 직렬 검출한다. 이전 검출이 끝나기 전에 다음 검출을 시작하지 않는다.
3. 사각형 후보가 다음 조건을 만족하는지 계산한다.
   - 네 점이 모두 검출됨
   - convex quadrilateral임
   - 화면 안에서 충분한 면적을 차지함
   - 문서 템플릿의 세로형 종횡비와 크게 다르지 않음
   - 네 변의 길이와 각도가 비정상적으로 찌그러지지 않음
   - 밝기와 blur가 인식 가능한 범위임
4. 후보가 3~5개 연속 프레임에서 일정 거리 이하로 유지되면 `촬영 가능` 상태로 표시한다.
5. 짧은 debounce 후 고해상도 비디오 프레임을 한 번 캡처한다.
6. 최종 고해상도 프레임은 다시 B 파이프라인을 거친다.

### 한계와 위험

- A는 카메라 경로에만 적용된다. 갤러리 파일과 PDF에는 영향을 주지 않는다.
- 자동 촬영이 너무 민감하면 사용자가 의도하지 않은 촬영이 발생한다.
- 경계가 잘 보이는 내부 표를 문서로 오인할 수 있으므로 실시간 검출도 품질 점수가 필요하다.
- 종이의 휨과 렌즈 왜곡은 문서가 안정적으로 보이는 상태에서도 남는다.
- 브라우저별 카메라 해상도, 권한, 배터리, 성능 차이를 고려해야 한다.

## 5. 방식 B 검토: 문서스캔 사례 기반 보정 강화

### 사례에서 확인한 공통 구조

- CamScanner 공식 개발자 문서는 문서 경계 자동 검출, 자동 crop, 이미지 향상, 수동 세부 조정을 함께 제공한다고 설명한다. 또한 API 지원 대상은 Android/iOS 앱이며, 앱 설치가 필요하다고 안내한다.
- Google ML Kit Document Scanner는 자동 문서 감지 기반 자동 촬영, 정확한 edge detection, 자동 회전, 필터·그림자·오염 제거 및 편집 흐름을 제공한다. 이 API는 Android용이고, 전체 흐름은 기기에서 처리된다.
- OpenCV의 homography 예제는 네 점으로 평면 사이의 투영 관계를 계산한 뒤 `warpPerspective`로 perspective correction을 수행한다. 이는 현재 프로젝트의 기본 보정 원리와 같다.
- 웹용 OpenCV.js 문서스캐너 예제도 자동 polygon 검출, crop, 실시간 스캔 연결, 사용자의 사각형 수동 수정이라는 조합을 사용한다. 다만 외부 프로젝트 코드를 그대로 가져오는 것이 아니라, 라이선스와 API의 안정성을 따로 확인해야 한다.

### 우리 프로젝트에 맞춘 B의 개선안

현재의 `largest convex quad` 한 단계 검출을 다음 다단계 파이프라인으로 바꾼다.

```text
감지용 저해상도 이미지
  -> 방향/밝기/대비 정규화
  -> Canny 후보 + adaptive threshold 후보 생성
  -> contour/선분 후보에서 여러 quadrilateral 생성
  -> 문서 템플릿 점수화
       면적, 세로 종횡비, convexity, 각도, 변의 연속성,
       화면 여백, 내부 표와의 구분, 모서리 신뢰도
  -> 상위 후보의 모서리 보정
  -> homography warp
  -> 결과 품질 검사
  -> 통과: 보정본 미리보기 / 실패: 원본 자동 확정 금지
```

필수 품질 검사는 다음과 같다.

- 문서 외곽선 후보가 실제 페이지에 해당하는지 확인한다.
- 출력 이미지의 네 모서리가 비정상적으로 늘어나지 않았는지 확인한다.
- 템플릿의 제목, 표 영역, 하단 동의 영역이 예상 순서에 있는지 확인한다.
- 문서가 너무 작거나 일부가 잘렸으면 `재촬영 권장`으로 표시한다.
- 사각형 신뢰도가 낮으면 네 모서리를 사용자가 직접 조정할 수 있게 한다.
- 보정 결과가 원본보다 나빠지는 경우 원본과 보정본을 나란히 보여주고 자동 저장하지 않는다.

### B의 한계

문서가 평면이라는 가정이 깨지는 경우에는 단순 homography를 계속 강화해도 해결되지 않는다. 종이 휨까지 펴려면 line-based dewarping 또는 학습 기반 문서 rectification이 필요하다. 하지만 이 프로젝트의 문서는 체크 표시 위치 보존이 가장 중요하므로, 검증되지 않은 강한 dewarping을 먼저 적용하면 체크 위치가 새롭게 이동할 위험이 있다.

## 6. A/B 비교

| 평가 항목 | A. 안정 상태 자동 촬영 | B. 보정 시스템 강화 |
|---|---|---|
| 카메라 입력 품질 | 높음 | 중간 이상 |
| 기존 파일 업로드 | 적용 불가 | 적용 가능 |
| PDF 입력 | 적용 불가 | 적용 가능 |
| 심한 기울기 | 촬영 전 예방 | 촬영 후 복구 시도 |
| 종이 휨 | 해결하지 못함 | homography만으로는 해결하지 못함 |
| 모바일 브라우저 구현량 | 큼 | 중간에서 큼 |
| 사용자 오작동 방지 | 높음 | 수동 확인이 필요 |
| 현재 프로젝트와의 호환성 | 카메라 경로에 한정 | 모든 입력 경로에 공통 적용 가능 |
| 단독 채택 판단 | 보조 기능으로 적합 | 기본 기능으로 필요 |

## 7. 권장 설계

### 1단계: B를 먼저 안전하게 만든다

- Worker 경계와 9초 강제 종료 구조는 유지한다.
- `largest convex quad` 단일 결과를 바로 사용하지 말고 후보 점수와 신뢰도 결과를 반환한다.
- 문서 템플릿 종횡비와 내부 표 영역을 활용해 내부 사각형을 제외한다.
- 검출 성공과 보정 성공을 분리한다. 보정 결과가 생성됐다는 이유만으로 유효한 문서라고 판단하지 않는다.
- 검출 실패·저신뢰 결과는 원본 자동 업로드 대신 수동 네 모서리 조정 또는 재촬영으로 보낸다.
- 보정 결과와 원본 모두를 검수 화면에서 확인할 수 있게 한다.

### 2단계: A를 카메라 보조 기능으로 추가한다

- 카메라 화면에 문서 경계 overlay와 상태를 표시한다.
- `문서를 화면 안에 맞추세요`, `흔들림을 줄이세요`, `촬영 가능` 상태를 구분한다.
- 3~5개 안정 프레임을 확인한 뒤 자동 촬영한다.
- 자동 촬영 버튼을 끌 수 있는 수동 촬영 fallback을 제공한다.
- 자동 촬영된 고해상도 프레임도 반드시 1단계 B 검증을 통과시킨다.

### 3단계: 품질 목표 미달 시 선택

현재 Next.js/Vercel 웹 프로젝트에는 Android 전용 Google ML Kit Document Scanner나 Android/iOS 앱 설치가 필요한 CamScanner API를 직접 붙일 수 없다. 따라서 먼저 웹에서 B+A 혼합안을 검증한다. 그래도 실사용 정확도가 목표에 못 미치면 다음 중 하나를 별도 검토한다.

- 모바일 앱 또는 Capacitor/React Native wrapper에서 Google ML Kit 또는 상용 문서스캔 SDK를 사용한다.
- 서버 처리용 전문 문서 rectification 모델을 도입한다. 이 경우 개인정보 처리, 비용, 지연, Vercel Serverless 적합성을 별도로 검토한다.

## 8-1. 다수 페이지 일괄 스캔 시 보정 전략

### 현재 코드 상태

현재 `handleBatchFileChange()`는 PDF를 페이지별 JPEG로 변환하거나 여러 이미지 파일을 수집한 뒤, 각 파일을 `uploadSingleFile()`에 순서대로 전달한다. `processSelectedFile()`에서 호출하는 `correctImageInWorker()`는 이 경로에 연결되어 있지 않다.

따라서 현재 배치 경로는 다음과 같다.

```text
PDF/다중 이미지
  -> 페이지별 이미지 변환
  -> 용량 축소
  -> 페이지별 업로드
  -> 서버 인식 시 rotate/grayscale/content bounds 추정
```

페이지별 원근 보정 또는 deskew는 아직 수행하지 않는다. 페이지마다 미세한 회전·기울기가 다르면 한 페이지에 맞춘 좌표 보정값을 다른 페이지에 재사용할 수 없으며, 현재처럼 각 페이지가 서버의 경계 추정에만 의존하면 confidence 저하와 ROI 행 어긋남이 반복될 수 있다.

### 배치에 적합한 기술

OpenCV.js의 contour·선분 검출과 perspective/affine 변환은 각 페이지를 독립적으로 처리하는 방식에 적합하다. 스캐너에서 발생하는 작은 회전만 있으면 전체 사각형 warp보다 먼저 지배적인 가로선의 각도를 추정해 빠른 deskew를 적용한다. 네 모서리의 비대칭이 일정 수준을 넘을 때만 full quadrilateral homography를 적용한다.

Dynamsoft Document Normalizer/Document Viewer 사례처럼 페이지마다 경계 검출 결과와 상태를 반환하고, 검출 결과를 페이지 단위로 정규화하는 구조를 참고한다. 자동 촬영용 기능보다 배치에서 중요한 부분은 `page -> detect -> normalize -> quality gate`가 독립적으로 반복된다는 점이다.

PaddleOCR의 UVDoc 같은 비평면 문서 unwarping 모델은 종이가 휘거나 구겨진 페이지에 대한 후속 후보가 될 수 있다. 그러나 모든 페이지에 기본 적용하면 모델 로드·추론 비용이 누적되므로, 1차 보정의 품질 게이트를 통과하지 못한 페이지에만 선택적으로 적용하는 것이 적절하다.

### 배치 처리 구현 원칙

1. 모든 페이지에 동일한 보정값을 적용하지 않고 페이지마다 독립적으로 검출한다.
2. 감지용 이미지는 저해상도로 축소하고, 최종 warp만 필요한 출력 크기로 수행한다.
3. OpenCV Worker는 페이지마다 새로 만들지 않고 재사용해 OpenCV 초기화 비용을 한 번만 부담한다.
4. 한 Worker에 처리 요청을 직렬로 보내되, 페이지 순서와 파일명 매핑을 유지한다.
5. 전체 작업을 무제한 병렬화하지 않는다. 브라우저 메모리와 Vercel 업로드 요청이 동시에 증가할 수 있으므로 제한된 동시성 또는 페이지 단위 순차 처리를 사용한다.
6. 한 페이지의 검출 실패는 전체 배치를 중단하지 않고 해당 페이지를 `재검토 필요` 상태로 기록한다.
7. `detect`, `normalize`, `quality gate`, `upload` 시간을 페이지별로 기록해 병목과 실패 페이지를 식별한다.
8. 보정 실패 페이지를 원본 그대로 조용히 자동 확정하지 않는다. 원본 대조, 수동 crop, 재스캔 중 하나를 선택하게 한다.

### 빠른 보정 모드

다수의 스캐너 페이지에는 다음과 같은 3단계 모드를 적용한다.

| 단계 | 조건 | 처리 |
|---|---|---|
| 1 | 회전·deskew만 필요 | 선분 각도 기반 affine 회전. 가장 빠른 경로 |
| 2 | 네 모서리 위치가 비대칭 | 문서 quadrilateral 검출 후 homography |
| 3 | 종이 휨·주름 또는 낮은 confidence | 원본 자동 확정 금지. 수동 조정 또는 선택적 UVDoc 실험 |

이 구조는 정면 스캔 페이지에 불필요한 무거운 원근 보정을 반복하지 않으면서, 페이지별 차이를 보정할 수 있다.

### 배치 적합성 결론

- **OpenCV.js와 Dynamsoft 방식**: 페이지별 독립 보정에 적합하다.
- **Google ML Kit·Apple Vision**: 실시간 카메라 검출의 참고 사례로는 좋지만, 현재 Next.js 웹의 PDF 일괄 처리 엔진으로 직접 사용할 수 없다.
- **CamScanner**: 제품 UX와 자동 보정 흐름 참고용이며 현재 웹 배치 엔진으로 직접 연결하기 어렵다.
- **PaddleOCR UVDoc**: 비평면 왜곡이 실제로 남는 일부 페이지의 후속 보정 후보로 적합하다.

따라서 배치 스캔에서는 **A 자동 촬영보다 B의 페이지별 빠른 정규화가 우선**이다. 카메라로 직접 촬영하는 경우에만 A를 앞단에 추가하고, PDF·스캐너 일괄 입력은 B의 `deskew -> 필요 시 homography -> quality gate` 파이프라인으로 처리한다.

## 9. 완료 기준

- 현재 두 원본을 포함한 회귀 샘플에서 문서 경계 후보가 실제 페이지 외곽을 선택한다.
- 저신뢰 경계에서는 값이 자동 확정되지 않고 원본 대조 또는 수동 조정이 표시된다.
- A를 사용하는 경우 문서가 안정되지 않은 상태에서 자동 촬영되지 않는다.
- 자동 촬영을 사용하지 않아도 수동 촬영과 파일 선택 업로드가 동작한다.
- PDF 일괄 업로드 경로에는 실시간 카메라 검출 코드가 개입하지 않는다.
- OpenCV 워커가 실패하거나 시간 초과되어도 웹페이지가 멈추지 않는다.
- 최종 저장 전 사용자가 원본 또는 보정 결과를 확인할 수 있다.
