# 검수 속도 개선 (2026-08-20~)

자동 입력률이 `CORRECT 108/135`에서 정체돼 있고, 남은 12칸 중 10칸을 풀어야 PRD 목표(118)에 닿는다. 정확도 작업은 계속하되, **채우지 못한 칸을 사람이 얼마나 빨리 처리하는가**는 별개의 지렛대다.

상위 문서: [Docs/00_PRD.md §10-1](../Docs/00_PRD.md) — A3(학생당 수기 3칸 이하)은 이미 만족한다. 이 스레드는 A3의 "3칸"을 **얼마나 빨리 끝내는가**를 다룬다.
관련 스레드: [[MARK_EVIDENCE_WEAK_SIGNAL_2026-08-20]] (정확도 축)

## 1. 사이클 1 — 검수 화면의 실제 마찰 진단

코드를 읽어 확인한 것. 추정이 아니라 `RecognitionReview.tsx`에 그렇게 쓰여 있다.

### 1.1 ★ 확인 필요 개수가 절대 줄지 않는다

`attentionFields`는 **신뢰도**로만 정해진다.

```ts
const attentionFields = reviewKeys.filter((key) => confidenceRank[getConfidenceLevel(key)] > 0);
```

그런데 `handleBasicChange` 계열은 `recognitionValueSource[field] = 'manual'`만 설정하고 **`confidence`는 건드리지 않는다.** 신뢰도는 사람이 보기 **전에** 인식기가 생각한 값이고 그 뒤로 바뀌지 않는다.

결과: 검수자가 방금 고친 항목이 계속 강조되고 계속 세어진다. **"확인 필요 4개"가 일을 아무리 해도 4개다.** 남은 것을 머릿속으로 추적해야 하고, 그것을 학생 19명에 대해 반복한다.

### 1.2 강조된 항목까지 가는 길이 없다

배너는 개수만 말하고 항목으로 이동하는 수단이 없다. 23개 필드 중 4~5개를 **테두리 색만 보고 스크롤로 찾는다.**

### 1.3 이미 맞는 값을 승인할 방법이 없다

낮은 신뢰도 항목은 값이 이미 맞는 경우가 많다 — 인식기가 확신을 못 했을 뿐이고 검수자가 크롭을 보고 동의하면 끝이다. 그런데 `select`에서 **같은 항목을 다시 고르면 change 이벤트가 발생하지 않는다.** "이게 맞다"고 말할 방법이 없으므로 그 항목은 영원히 미처리로 남는다.

### 1.4 기술 진단이 화면을 덮고 있다

`renderDecisionTrace`와 `renderCoordinateDiagnostics`가 **항상** 렌더된다. 정확도 조사를 위해 내가 넣은 것들이고, 지금은 이런 문자열이 필드마다 11px로 깔린다.

```
[match=1 win=12x12 #1 ref=22x20 off=-0.3,-0.4 ink=0.2,0.1 ext=0,0,0,0 core=0 dark=62 fix=0 sig=0 #2 ...]
```

**검수자가 4개를 찾기 위해 읽고 지나쳐야 하는 벽이다.** 조사에는 값졌지만 실무 화면에 있을 것이 아니다.

## 2. 사이클 1 — 구현

네 가지가 서로를 필요로 하므로 한 묶음으로 넣는다.

| # | 변경 | 해결하는 것 |
|---|---|---|
| 1 | `isSettled(key)` — 검수자가 손댄 항목(`recognitionValueSource === 'manual'`)을 남은 목록에서 제외 | §1.1 |
| 2 | 배너가 `N개 중 M개 완료 · K개 남음`으로 진행률 표시 | §1.1 |
| 3 | 남은 항목마다 **이름표 버튼** — 누르면 해당 카드로 스크롤하고 **입력 컨트롤에 포커스**까지 준다 | §1.2 |
| 4 | 미처리 항목에 **`이 값이 맞음`** 버튼 (값이 있을 때만) | §1.3 |
| 5 | `기술 진단 표시` 체크박스 — 기본 **꺼짐** | §1.4 |

설계 판단 두 가지.

- **포커스까지 준다.** 카드로 스크롤만 하면 검수자가 다시 마우스를 잡아야 한다. 도착과 동시에 키보드로 답할 수 있어야 이동이 의미가 있다.
- **`이 값이 맞음`은 값이 있을 때만 뜬다.** 빈 항목은 승인할 것이 없고, 값을 고르면 기존 경로로 자동으로 처리 완료가 된다.

## 4. 사이클 2 — 실사용 확인에서 결함 두 개 (2026-08-21)

작업자가 19페이지 원본으로 실제 검수 화면을 확인했다. **19페이지 일괄 업로드 경로는 정상 동작한다** — "1 / 19번째 학생 데이터입니다"까지 도달했고, [[MEASUREMENT_RENDER_PARITY_2026-08-19]]에 기록한 "숨겨진 탭에서는 판정할 수 없다"가 맞았다.

### 4.1 `기술 진단 표시`를 꺼도 진단이 남아 있었다

체크박스는 꺼져 있는데 카드마다 이런 것이 그대로 보였다.

```
Checkbox geometry matched 12/12 candidates; max normalized residual 0.0066...
Grid candidate rejected; row fallback used... [rows sel=-47,-49,-51 det=...
```

`renderDecisionTrace`와 `renderCoordinateDiagnostics`는 막았지만, **`renderCropSourceBadge`가 자기 몫의 진단 문자열(`recognitionCropDiagnostic`)을 따로 들고 있었다.** 세 군데였는데 두 군데만 막았다.

### 4.2 ★ 고신뢰인데 비어 있는 필드가 "확인 필요"에서 빠졌다

화면 실측:

```
학교유형   높음  미확정   선택 안 함    후보 중학교/21% 고등학교/6%
학년       높음  미확정   선택 안 함    후보 1학년/18% 2학년/9%
확인 필요 항목: 연령대, CAGI 08, CAGI 09, 문항6      ← 위 둘이 없다
```

`attentionFields`가 **신뢰도로만** 정해졌기 때문이다. 점수기는 확신했는데 게이트가 거부한 필드는 `high`인 채로 비어 있고, 그래서 목록에도 이동 버튼에도 개수에도 안 들어간다.

**검수자가 강조된 4개를 모두 처리하고 "모두 확인했습니다"를 읽은 뒤, 학교유형과 학년이 빈 채로 저장할 수 있다.** 내가 만든 진행률 표시가 오히려 그것을 안전하다고 말한다.

### 4.3 수정

| # | 변경 |
|---|---|
| 1 | `renderCropSourceBadge`의 진단도 `기술 진단 표시`에 연동 |
| 2 | **값이 없는 필드는 신뢰도와 무관하게 "확인 필요"에 포함** |
| 3 | 학생이 답하지 않은 칸을 위해 `비어 있는 것이 맞음` 버튼 — 값 없이도 처리 완료로 기록 |

3번이 2번의 짝이다. 정답표상 무표시인 칸(`p3 basic.gender` 등)은 비워두는 것이 정답이므로, 검수자가 **"봤고 비어 있는 게 맞다"**고 말할 수단이 없으면 그 칸은 영원히 미처리로 남는다.

### 4.4 미해결 — 계측기와 브라우저가 어긋난다

같은 PDF 1페이지에 대해:

```
노드 계측기   basic.schoolType  got=중학교  conf=high  src=grid  ok
브라우저      학교유형          높음  미확정  선택 안 함
```

**계측기는 채웠다고 하고 브라우저는 비어 있다.** [[MEASUREMENT_RENDER_PARITY_2026-08-19]]의 그 격차가 아직 남아 있다는 증거다. 다음 사이클에서 확인한다.
