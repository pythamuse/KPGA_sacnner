자동 입력률이 `CORRECT 108/135`에서 정체돼 있고, 남은 12칸 중 10칸을 풀어야 PRD 목표(118)에 닿는다. 정확도 작업은 계속하되, **채우지 못한 칸을 사람이 얼마나 빨리 처리하는가**는 별개의 지렛대다.

## 1. 사이클 1 — 검수 화면의 실제 마찰 진단

코드를 읽어 확인한 것. 추정이 아니라 `RecognitionReview.tsx`에 그렇게 쓰여 있다.

### 1.1 ★ 확인 필요 개수가 절대 줄지 않는다

`attentionFields`는 **신뢰도**로만 정해진다.

```ts
const attentionFields = reviewKeys.filter((key) => confidenceRank[getConfidenceLevel(key)] > 0);
```

그런데 `handleBasicChange` 계열은 `recognitionValueSource[field] = 'manual'`만 설정하고 **`confidence`는 건드리지 않는다.** 신뢰도는 사람이 보기 **전에** 인식기가 생각한 값이고 그 뒤로 바뀌지 않는다.

결과: 검수자가 방금 고친 항목이 계속 강조되고 계속 세어진다. **"확인 필요 4개"가 일을 아무리 해도 4개다.** 남은 것을 머릿속으로 추적해야 하고, 그것을 학생 19명에 대해 반복한다.

### 1.2 강조된 항목까지 가는 길이 없다

배너는 개수만 말하고 항목으로 이동하는 수단이 없다. 23개 필드 중 4~5개를 **테두리 색만 보고 스크롤로 찾는다.**

### 1.3 이미 맞는 값을 승인할 방법이 없다

낮은 신뢰도 항목은 값이 이미 맞는 경우가 많다 — 인식기가 확신을 못 했을 뿐이고 검수자가 크롭을 보고 동의하면 끝이다. 그런데 `select`에서 **같은 항목을 다시 고르면 change 이벤트가 발생하지 않는다.** "이게 맞다"고 말할 방법이 없으므로 그 항목은 영원히 미처리로 남는다.

### 1.4 기술 진단이 화면을 덮고 있다

`renderDecisionTrace`와 `renderCoordinateDiagnostics`가 **항상** 렌더된다. 정확도 조사를 위해 내가 넣은 것들이고, 지금은 이런 문자열이 필드마다 11px로 깔린다.

```
[match=1 win=12x12 #1 ref=22x20 off=-0.3,-0.4 ink=0.2,0.1 ext=0,0,0,0 core=0 dark=62 fix=0 sig=0 #2 ...]
```

**검수자가 4개를 찾기 위해 읽고 지나쳐야 하는 벽이다.** 조사에는 값졌지만 실무 화면에 있을 것이 아니다.

## 2. 사이클 1 — 구현

네 가지가 서로를 필요로 하므로 한 묶음으로 넣는다.

| # | 변경 | 해결하는 것 |
|---|---|---|
| 1 | `isSettled(key)` — 검수자가 손댄 항목(`recognitionValueSource === 'manual'`)을 남은 목록에서 제외 | §1.1 |
| 2 | 배너가 `N개 중 M개 완료 · K개 남음`으로 진행률 표시 | §1.1 |
| 3 | 남은 항목마다 **이름표 버튼** — 누르면 해당 카드로 스크롤하고 **입력 컨트롤에 포커스**까지 준다 | §1.2 |
| 4 | 미처리 항목에 **`이 값이 맞음`** 버튼 (값이 있을 때만) | §1.3 |
| 5 | `기술 진단 표시` 체크박스 — 기본 **꺼짐** | §1.4 |

설계 판단 두 가지.

- **포커스까지 준다.** 카드로 스크롤만 하면 검수자가 다시 마우스를 잡아야 한다. 도착과 동시에 키보드로 답할 수 있어야 이동이 의미가 있다.
- **`이 값이 맞음`은 값이 있을 때만 뜬다.** 빈 항목은 승인할 것이 없고, 값을 고르면 기존 경로로 자동으로 처리 완료가 된다.

## 4. 사이클 2 — 실사용 확인에서 결함 두 개 (2026-08-21)

작업자가 19페이지 원본으로 실제 검수 화면을 확인했다. **19페이지 일괄 업로드 경로는 정상 동작한다** — "1 / 19번째 학생 데이터입니다"까지 도달했고, [[MEASUREMENT_RENDER_PARITY_2026-08-19]]에 기록한 "숨겨진 탭에서는 판정할 수 없다"가 맞았다.

### 4.1 `기술 진단 표시`를 꺼도 진단이 남아 있었다

체크박스는 꺼져 있는데 카드마다 이런 것이 그대로 보였다.

```
Checkbox geometry matched 12/12 candidates; max normalized residual 0.0066...
Grid candidate rejected; row fallback used... [rows sel=-47,-49,-51 det=...
```

`renderDecisionTrace`와 `renderCoordinateDiagnostics`는 막았지만, **`renderCropSourceBadge`가 자기 몫의 진단 문자열(`recognitionCropDiagnostic`)을 따로 들고 있었다.** 세 군데였는데 두 군데만 막았다.

### 4.2 ★ 고신뢰인데 비어 있는 필드가 "확인 필요"에서 빠졌다

화면 실측:

```
학교유형   높음  미확정   선택 안 함    후보 중학교/21% 고등학교/6%
학년       높음  미확정   선택 안 함    후보 1학년/18% 2학년/9%
확인 필요 항목: 연령대, CAGI 08, CAGI 09, 문항6      ← 위 둘이 없다
```

`attentionFields`가 **신뢰도로만** 정해졌기 때문이다. 점수기는 확신했는데 게이트가 거부한 필드는 `high`인 채로 비어 있고, 그래서 목록에도 이동 버튼에도 개수에도 안 들어간다.

**검수자가 강조된 4개를 모두 처리하고 "모두 확인했습니다"를 읽은 뒤, 학교유형과 학년이 빈 채로 저장할 수 있다.** 내가 만든 진행률 표시가 오히려 그것을 안전하다고 말한다.

### 4.3 수정

| # | 변경 |
|---|---|
| 1 | `renderCropSourceBadge`의 진단도 `기술 진단 표시`에 연동 |
| 2 | **값이 없는 필드는 신뢰도와 무관하게 "확인 필요"에 포함** |
| 3 | 학생이 답하지 않은 칸을 위해 `비어 있는 것이 맞음` 버튼 — 값 없이도 처리 완료로 기록 |

3번이 2번의 짝이다. 정답표상 무표시인 칸(`p3 basic.gender` 등)은 비워두는 것이 정답이므로, 검수자가 **"봤고 비어 있는 게 맞다"**고 말할 수단이 없으면 그 칸은 영원히 미처리로 남는다.

### 4.4 미해결 — 계측기와 브라우저가 어긋난다

같은 PDF 1페이지에 대해:

```
노드 계측기   basic.schoolType  got=중학교  conf=high  src=grid  ok
브라우저      학교유형          높음  미확정  선택 안 함
```

**계측기는 채웠다고 하고 브라우저는 비어 있다.** [[MEASUREMENT_RENDER_PARITY_2026-08-19]]의 그 격차가 아직 남아 있다는 증거다. 다음 사이클에서 확인한다.

## 5. 사이클 3 — 실사용 요청 네 건 (2026-08-21)

작업자가 노트북으로 19명을 검수하면서 요청한 것들. 전부 **화면에서 실제로 확인**했다 — §2.1과 §4에서 확인 없이 내보낸 것이 결함 둘로 돌아왔다.

| # | 요청 | 구현 |
|---|---|---|
| 1 | 다음 학생으로 넘어갈 때 스크롤 맨 위로 | `currentDraftIndex` 변화에 반응하는 효과. 저장·건너뛰기 양쪽을 한 곳에서 덮는다 |
| 2 | 필수 항목 누락 시 해당 항목으로 자동 이동 | 저장 실패의 `saveErrors`에서 필드를 지목한 첫 오류로 `focusField`. `source.*`(업로드 오류)는 카드가 없으므로 요약에 맡긴다 |
| 3 | 수기 입력한 항목은 다른 색(회색) | `getFieldCardStyle`에 `isSettled` 분기를 **저장 오류 다음, 신뢰도보다 앞**에 |
| 4 | 검수 건너뛰기 버튼 (기술 진단 줄 오른쪽 끝) | `marginLeft: 'auto'`, 마지막 학생에서 자동 비활성화 |

### 5.1 신뢰도는 사람이 보기 전의 값이다

3번이 §1.1과 같은 뿌리다. 신뢰도는 인식기가 **보기 전에** 생각한 값이고 그 뒤로 바뀌지 않으므로, 검수자가 답을 넣은 칸도 계속 빨강/노랑으로 남았다. **다 처리한 화면이 여전히 문제투성이 화면으로 보였다.** 처리된 뒤에 그 칸에 대해 말할 가치가 있는 것은 "처리됐다" 하나뿐이다.

### 5.2 ★ `behavior: 'smooth'`를 두 곳에서 걷어냈다

1번을 검증하다 스크롤이 **1714 → 1813**으로 오히려 내려갔다. 원인은 제품 결함이 아니라 [[MEASUREMENT_RENDER_PARITY_2026-08-19]]의 그 제약이다 — 부드러운 스크롤은 `requestAnimationFrame`으로 구동되고, 컴포지팅하지 않는 창에서는 발화하지 않는다. 같은 창에서 잰 값:

```
behavior:'smooth'  →  scrollY 1813  (변화 없음)
behavior:'auto'    →  scrollY 0
rafFired           →  false
```

`auto`로 바꾸니 **1813 → 0**.

`focusField`도 같은 이유로 바꿨다. 이쪽은 더 나쁜 실패였다 — 스크롤은 죽고 `focus({preventScroll:true})`는 살아서, **화면에 없는 칸에 포커스가 들어간 채로 남았다.** 검수자는 보이지 않는 칸에 타이핑하게 된다. 측정값:

```
수정 전  포커스 review-field-basic-age, scrollY 1919 (그대로), 카드는 화면 밖
수정 후  포커스 review-field-basic-age, scrollY 793,  카드 화면 안
```

학생 전환에서 1700px를 부드럽게 굴리는 것은 어차피 검수자를 기다리게 할 뿐이다. **도착이 목적이지 활강이 목적이 아니다.**

### 5.3 검증 방법 — 스냅샷 주입

검수 화면은 PDF 업로드와 인식을 거쳐야 도달하는데, 브라우저 창에 로컬 파일을 붙일 수단이 없다. `localStorage`에 `kpga.review.session.v2.<jobId>` 스냅샷을 직접 써넣고 `이어서 하기`를 누르면 **학생 3명짜리 검수 화면으로 바로 들어간다.** 원본 이미지는 복원되지 않지만 배치·색·포커스·스크롤은 전부 실물이다.

측정값:

| 확인 | 결과 |
|---|---|
| 수기 수정 카드 배경 | `rgb(238,241,245)` — 낮음 `rgb(255,240,239)`, 기본 `rgb(247,248,250)`과 구분됨 |
| 건너뛰기 버튼 위치 | 우측 끝 691px (진단 체크박스 417px), 같은 줄 |
| 마지막 학생에서 | 자동 비활성화 |
| 건너뛴 뒤 | `3 / 3번째`, scrollY 0, 안내 문구 표시 |
| 저장 실패 후 | `필수 항목 1개가 비어 있어…`, 포커스 `review-field-basic-age`, 카드 화면 안 |
| 콘솔 | React 오류 없음 (400 두 건은 내가 일부러 낸 저장 실패) |

### 5.4 남는 것

**건너뛴 학생은 이 세션에서 돌아올 수 없다.** 인덱스를 뒤로 옮기는 경로가 없다. → §6에서 해결.

## 6. 사이클 4 — 이전/다음 이동, 그리고 그것이 드러낸 저장 결함 (2026-08-21)

§5.4를 받아 건너뛰기를 **양방향 이동**으로 바꿨다. 그런데 되돌아가기만 넣으면 안 된다.

### 6.1 ★ 되돌아가서 다시 저장하면 **행이 하나 더 생긴다**

저장 경로는 언제나 `students` 배열 **끝에 덧붙이는** 것이었고, API도 `students[length-1]`만 검증했다. 인덱스가 앞으로만 갔으니 그래도 됐다. 이동을 열면 그 전제가 깨진다 — 9번을 고치러 돌아가 다시 저장하면 **9번이 마지막 행으로 한 번 더 기록되고**, 그 뒤 학생들이 한 줄씩 밀린다.

그래서 이동과 함께 고쳤다.

| 층 | 변경 |
|---|---|
| API | `index`를 선택적으로 받는다. 없으면 종전대로 마지막 행. 범위를 벗어나면 400 |
| 클라이언트 | 저장된 학생과 초안을 **`cagiImageId`로 짝지어** 이미 가진 행을 찾는다 |
| 화면 | `이미 저장된 학생입니다 · 엑셀 N행`, 버튼도 `수정 내용 반영 (엑셀 N행)` |

**짝짓기를 위치가 아니라 이미지 id로 한 이유:** 건너뛰기가 두 목록의 정렬을 깨뜨린다. id는 저장(그대로 보존)과 세션 복원(렌더된 이미지만 제거)을 모두 통과한다. 별도 목록을 관리할 필요도, 스냅샷 버전을 올릴 필요도 없다.

### 6.2 저장하지 않고 떠나는 경우

이동은 저장이 아니므로, 이미 저장된 학생을 고치고 그냥 넘어가면 **엑셀에는 이전 값이 남는다.** 조용히 어긋나면 안 되므로 두 곳에서 말한다 — 카드 상단 `저장되지 않은 수정 있음`, 그리고 이동 직후 `N번째 학생의 수정 내용은 저장하지 않았습니다.`

### 6.3 측정값

| 확인 | 결과 |
|---|---|
| 양방향 이동 | `1→2→3→2→1`, 양 끝에서 각각 비활성화 |
| 신규 저장 | `existingRow -1`, 목록 1명 → 2명 |
| 저장된 학생으로 복귀 | 배너 `엑셀 3행`, 버튼 `수정 내용 반영 (엑셀 3행)` |
| 값 수정 후 | 배너에 `저장되지 않은 수정 있음` 추가 |
| 재저장 | `existingRow 0`, **목록 2명 유지**, 1행 학년이 `5학년`으로 갱신, 2행 그대로 |
| 재저장 안내 | `1번째 학생을 다시 저장했습니다. 엑셀 3행을 덮어썼습니다.` |
| 저장 없이 이동 | `수정 내용은 저장하지 않았습니다. 엑셀에는 이전 값이 남아 있습니다.` |

### 6.4 ★ 이 검증에서 두 시간을 태운 것 — 진단 도구가 거짓말을 했다

재저장 안내가 화면에 뜨지 않았다. 코드를 세 번 읽고, `console.log` → `document.title` → `window.__dbg`로 계측을 세 번 갈아끼우는 동안 전부 "그 줄은 실행되지 않았다"고 나왔다. 그런데 같은 저장이 **행은 정확히 갱신하고 있었다.**

원인은 코드가 아니었다. **dev 서버가 도는 중에 `npm run build`를 돌려 `.next`를 덮어썼고, 청크가 404가 되어 React가 하이드레이션되지 않았다.** 화면은 서버 렌더 HTML 그대로라 멀쩡해 보이고, 버튼은 아무 일도 하지 않는다. 앞선 "성공"들은 전부 **덮어쓰기 전 번들**이었다.

진단 근거는 콘솔에 있었다:

```
Refused to execute script from '.../main-app.js' because its MIME type ('text/html') is not executable
```

dev 서버를 재시작하자 세 계측이 모두 즉시 값을 냈고, 안내도 정상이었다. [[CLAUDE.md]] §4에 적었다. **§2의 "계측기가 무엇을 재고 있는지 확인한다"가 브라우저 쪽에도 그대로 적용된다** — 이번엔 계측기가 아니라 **계측 대상이 실행조차 되지 않고 있었다.**
