# 사진 경로 — 측정과 단계별 개선 계획 (2026-08-25)

## 배경

이 프로젝트는 **카메라로 찍은 사진을 인식하는 기능을 제공하고 있다.** 그런데
**저장소 어디에도 사진 기반 인식 정확도 측정이 없다.** 모든 숫자 — 정답표 19명,
`CORRECT 354/432`, 브라우저 확인 필요 135 · 자동 입력 302 · 오답 10, 잡음 바닥 76칸 —
는 전부 **스캔 PDF**에서 나왔다.

스캔 경로는 `WRONG = 0`을 절대 조건으로 지키는데([[CLAUDE.md]] §3), **사진 경로는 그 조건이
성립하는지 확인된 적이 없다.** 검증되지 않은 기능이 검증된 것처럼 제공되고 있다는 것이,
오독률 자체보다 앞서는 문제다.

### 왜 사진이 스캔보다 훨씬 어려운가 — 기제

이 파이프라인은 **모양을 인식하지 않는다. 기준 이미지와의 잉크 차이를 잰다.**

```ts
// markDensity.ts:1368
const residualInk = Math.max(0, actualInk - baselineInk - 0.08);
```

형태 통계(`largestComponentSize` · `largestComponentRatio` · `diagonalRatio`,
`markDensity.ts:1688-1755`)는 존재하지만 **통과/거부 문턱으로만** 쓰이고 점수에 들어가지
않는다(`hasStructuredTemplateMark`, `:1679-1686`). 체크·X·동그라미·낙서가 같게 취급된다.

그래서 **커밋된 빈 양식 PNG와 화소 단위로 맞아야 한다.** 정렬 탐색의 사거리는
`clamp(round(1/pitch), 1, 4)` — **약 1 소스 픽셀**이다(`markDensity.ts:1901-1906`).

그 예산이 얼마나 좁은지는 측정돼 있다.

| 관측 | 값 | 출처 |
|---|---|---|
| 같은 용지·같은 기기 재급지로 뒤집힌 칸 | **76칸** | [[WEAK_SIGNAL_STABILITY_PLAN_2026-08-24]] §21 |
| 그때 셀이 움직인 폭 | 1.7% ≈ **1.5px** | 같은 문서 §27.3 |
| 행 검출이 감당하는 기울기 예산 | `MAX_RULE_DRIFT_RATIO = 0.0025` (주석: 스캔은 최대 0.3도) | `tableRowDetection.ts:53-66` |

**급지 흔들림만으로 오차 예산이 소진된다.** 휴대폰 사진의 2도 기울기는 그 예산의 한 자릿수 밖이다.

### 지금 사진 경로가 실제로 하는 일

원근 보정은 **있다.** OpenCV.js를 Web Worker에서 돌린다
(`src/lib/documentScanner/perspectiveCorrect.worker.ts`).

- 그레이스케일 → `GaussianBlur(5,5)` → **세 가지 검출맵**: `Canny(50,150)`,
  `Canny(85,220)`, `adaptiveThreshold(GAUSSIAN, INV, 31, 11)` (`:101-121`)
- 맵마다 `findContours` → `approxPolyDP`를 **세 배율**(0.015 / 0.02 / 0.03)로 (`:161-172`)
- 볼록한 사각형만 남기고 `evaluateQuad`로 채점, 최고 신뢰도 선택 (`:174-189`)
- `getPerspectiveTransform` → `warpPerspective` → ROI 템플릿에 맞춘 **1422×1968** 고정 출력

경로별 설정 (`ImageUploadPanel.tsx`):

| 경로 | 검출 해상도 | 시간 제한 | 최소 신뢰도 |
|---|---|---|---|
| 카메라 촬영 | 전체 프레임 | 9000ms | 0.58 |
| 단일 파일 | 장변 ≤1600 | 9000ms | 0.58 |
| 일괄(이미지) | 장변 ≤1100 | **3000ms** | **0.62** |

PDF 렌더 페이지는 정책으로 제외된다(`perspectiveCorrectionPolicy.ts:8-14`).

### ★ 그런데 보정의 품질을 아무도 재지 않는다

- **`confidence`는 사각형의 그럴듯함이지 왜곡 잔차가 아니다.**
  `0.35·면적 + 0.30·종횡비 + 0.20·모서리일관성 + 0.15·각도`
  (`perspectiveCorrect.ts:174-184`). 종횡비 항은 **1.9배까지** 봐준다
- **워프 후 기하 검증이 없다.** 재투영 오차도, 잔차도, 템플릿 구조 대조도 없다
  (사람이 미리보기를 확인하는 단계와 서버의 양식 재분류는 있지만, 둘 다 기하를 재지 않는다)
- **테스트가 이미지를 한 장도 워프하지 않는다.** `tests/perspective-correct.test.ts`는
  합성 좌표로 모서리 정렬과 수락/거부만 본다
- **실패하면 원본이 그대로 올라간다.** 카메라·단일 경로는 **경고도 없다**
  (`ImageUploadPanel.tsx:477-491`, `:771-798`). 일괄만 한국어 경고를 큐에 넣는다
- 스펙(`Docs/04_OCR_FORM_RECOGNITION_SPEC.md:217-227`)이 정한 **재촬영 조건은 구현돼 있지 않다**

## 0단계 — 먼저 잰다. 아무것도 고치지 않는다

**이 단계를 건너뛰면 나머지 전부가 감으로 하는 일이 된다.** [[CLAUDE.md]] §2가 규정한 순서다.

### 0.1 필요한 표본

**같은 19명의 같은 용지**를 휴대폰으로 촬영한다. **정답표가 그대로 붙으므로 새 정답표가
필요 없다** — 이것이 이 측정을 싸게 만드는 핵심이다.

**처음부터 38장을 찍지 않는다.** 5명(10장)이면 자릿수는 나온다.

| 회차 | 분량 | 답하는 것 |
|---|---|---|
| 0-A | **5명 = 10장** | 사진이 스캔 대비 몇 배 나쁜가. 자릿수 |
| 0-B | 나머지 14명 = 28장 | 0-A가 "쓸 만하다"로 나왔을 때만 |

### 0.2 촬영 조건 — 두 종류를 나눠 찍는다

**섞으면 원인을 못 가린다.**

| 조건 | 어떻게 | 무엇을 분리하는가 |
|---|---|---|
| **정상 촬영** | 정면, 밝은 곳, 그림자 없이, 용지가 프레임 안에 다 들어오게 | 사진 경로의 **상한** |
| **현실 촬영** | 평소 쓰듯 — 약간 기울고, 손 그림자 지고, 살짝 흔들려도 그대로 | 실사용에서의 값 |

0-A에서는 **정상 촬영만** 한다. 그것도 나쁘면 현실 촬영은 볼 것도 없다.

### 0.3 판정

스캔 기준선과 나란히 놓는다.

```
                    스캔(기준선)   사진
CORRECT / 432          354          ?
WRONG                    7          ?
빈칸 침범                0          ?
원근 보정 성공률         해당없음     ?
```

| 결과 | 다음 |
|---|---|
| `WRONG`이 스캔과 비슷하고 `CORRECT`가 80% 이상 | 사진 경로는 쓸 만하다. 1단계로 |
| `WRONG`이 늘거나 빈칸 침범이 생김 | **기능을 경고와 함께 제한하는 것이 먼저다.** 1단계보다 우선 |
| `CORRECT`가 절반 이하 | 부분 개선으로 안 된다. 3·4단계(다중 프레임·분류기)로 건너뛴다 |

### 0.4 하니스 변경 (0단계에서 유일하게 쓸 코드)

지금 하니스는 PDF만 받는다(`tests/real-scan-measure.test.ts:51-53` 등). **디렉터리의
이미지 파일을 페이지로 받는 입력을 더한다.** 렌더 단계만 갈라지고 그 뒤는 같은 경로다.

```
PHOTO_CAGI_DIR="C:/.../사진/선별검사"  PHOTO_SAT_DIR="C:/.../사진/만족도"
```

> **사진을 PDF로 합쳐 오지 않는다.** 휴대폰의 "스캔" 기능이나 PDF 변환 앱은 **자체 원근
> 보정과 대비 강화를 적용한다.** 그러면 우리가 재려는 것이 사라진다. **원본 JPG 그대로** 둔다.

## 1단계 — 워프를 검증한다 (부품이 이미 있다)

### 무엇이 문제인가

`confidence`는 **사각형이 그럴듯한가**를 잰다. 정작 필요한 것은 **워프 후에 양식이 제자리에
왔는가**다. 지금은 그럴듯한 사각형이면 통과하고, 실패해도 원본이 조용히 올라간다.

### 무엇을 하는가

**보정 후 이미지에서 표 괘선을 검출해 템플릿 위치와 대조한다.** `tableGridDetection.ts`가
이미 그 일을 한다 — 새로 만들 것은 **대조와 판정**뿐이다.

```
보정된 이미지 → buildCagiGridDetection / buildSatisfactionGridDetection
             → 검출된 행·열 위치를 템플릿 기대 위치와 비교
             → 잔차가 기준 밖이면 재촬영 요구
```

이것이 카드 리더가 하는 일이다 — **알려진 구조가 제자리에 왔는지로 정합을 검증**한다.

### 판정 기준 (착수 전 등록)

- **잔차와 인식 결과가 상관이 있어야 한다.** 잔차가 큰 사진에서 `WRONG`이 늘지 않으면
  잔차는 쓸모없는 지표다 → 폐기
- 재촬영을 요구하는 문턱은 **0단계 데이터에서** 정한다. 감으로 고르지 않는다

### 곁들여 고칠 것

- **카메라·단일 경로의 조용한 실패.** 일괄에는 경고가 있는데 나머지엔 없다
  (`ImageUploadPanel.tsx:487-489`, `:781-783`)
- `perspectiveCorrect.ts`의 **죽은 코드** `detectDocumentQuad` / `warpToRectangle` /
  `loadOpenCv` — 호출부가 없다. 다시 배선되면 `evaluateQuad` 게이트를 우회한다

## 2단계 — 종이 테두리가 아니라 인쇄 구조로 정합한다

### 무엇이 문제인가

지금 정합은 **두 단계 모두 약하다.**

1. `pageBounds`(밝은 성분) → `contentBounds`는 **선형 스케일**뿐이다
   (`markDensity.ts:327-332`). 회전·원근을 표현할 수 없다
2. 셀 단위 `findBestBaselineAlignment`는 **평행이동만**, 사거리 **약 1픽셀**

### 무엇을 하는가

**검출된 괘선을 템플릿 괘선에 대응시켜 호모그래피를 적합한다.** 대응점을 찾는 코드는
이미 있다(`tableGridDetection.ts`) — **새로 만들 것은 적합 단계뿐이다.**

호모그래피는 회전·배율·원근을 한 번에 흡수한다. 이것이 카드 리더가 특징점 매칭 +
RANSAC으로 하는 일과 같은 것이고, 여기서는 **특징점이 이미 검출된 괘선**이다.

### 판정 기준 (착수 전 등록)

- **스캔에서 회귀가 없어야 한다.** 브라우저 오답 10 이하 · 빈칸 침범 0 · 확인 필요 135 이하
- **사진에서 개선이 있어야 한다.** 0단계 수치 대비
- 스캔이 나빠지면 **사진이 좋아져도 기각**한다. 스캔이 주 경로다

### 위험

이것은 **좌표계를 바꾸는 변경**이다. [[CLAUDE.md]] §5.5가
*"좌표계·페이지 기하는 병목이 아니다"* 를 닫아뒀는데, **그것은 스캔에 대한 결론이다.**
사진에서는 다시 열릴 수 있지만, **스캔 회귀 금지**를 절대 조건으로 건다.

## 3단계 — 여러 프레임의 합의 (이미 만들어 놓은 기제)

### 왜 이것이 강한가

§21이 잰 잡음 바닥 76칸은 **위험이자 자원**이다. 한 번 찍어 애매한 칸도, **두세 프레임이
같은 값을 내면 그것은 우연이 아니다.**

그리고 그 판정기는 **이미 만들어져 있다.** §24의 3스캔 합의 분류
(`stable-correct` / `gate wobbles`)가 정확히 그 기제다
(`tests/scan-repeat-measure.test.ts`).

```
지금(측정용)   3개 스캔 → 칸마다 세 읽기 → 세 번 다 같으면 stable
제품(제안)     2~3 프레임 → 칸마다 여러 읽기 → 일치하면 자동 입력, 갈리면 확인 필요
```

### 무엇을 하는가

촬영 화면에서 **연속 2~3프레임을 잡고**, 각각을 인식해 **칸 단위로 합의**한다.
합의된 칸만 자동 입력하고, 갈린 칸은 확인 필요로 남긴다.

### 판정 기준

- **오답이 줄어야 한다.** 확인 필요가 늘더라도 오답이 줄면 이득이다 — §3의 우선순위 그대로
- 프레임 수가 늘어난 만큼의 **시간 비용**을 잰다

### 이 단계의 특별한 성질

**인식을 하나도 안 고치고 오답을 줄일 수 있는 유일한 방법이다.** 다른 단계는 전부
파이프라인을 건드리지만, 이것은 **같은 파이프라인을 여러 번 돌려 합의를 본다.**

## 4단계 — 차감이 아니라 크롭 분류

### 왜 필요한가

브라우저 오답 10건의 기제는 [[FIELD_TEST_2026-08-21]] §22.4에 정리돼 있다.

```
X 취소        5건   취소한 칸이 잉크가 많아 이긴다
꼬리 침범     4건   체크 꼬리가 옆 칸을 넘는다
원 채우기     1건   ⓪을 새까맣게 메웠다
```

**전부 "잉크가 얼마나 있나"로는 못 가르는 것들이다.** X 취소를 취소로 알아보려면
**획의 방향과 교차**를 봐야 하고, 그것은 모양 인식이다.

### 무엇을 하는가

셀 크롭을 작은 분류기로 판정한다 — `표시 없음 / 표시 / 취소된 표시`.

**데이터 수집기는 이미 있다.** `src/lib/labelExport/`가 검수 완료된 학생에서 후보별 라벨을
모은다. **다만 특징 벡터만 저장하고 크롭은 저장하지 않는다**(`types.ts`의 `LabelRow`).
**크롭을 함께 저장하도록 넓히는 것이 첫 걸음이다.**

### 위험 — 가장 크다

- **19명으로 학습하면 §19.3의 과적합 함정에 그대로 걸린다.** 오답 10건 중 9건이 세 학생에서
  나온다. 새 응답자 표본 없이는 판정 자체가 불가능하다
- 모델 저장·추론·버전 관리가 저장소에 들어온다. 별개의 큰 변경이다

### 착수 조건

**새 응답자 표본이 먼저다**([[WEAK_SIGNAL_STABILITY_PLAN_2026-08-24]] §19.5).
그 전에는 크롭 수집만 해둔다 — **모으는 것은 지금 해도 손해가 없다.**

## 순서와 그 이유

```
0단계  측정            ← 이것 없이는 나머지가 전부 감이다
  ↓
1단계  워프 검증        ← 부품이 있고, 조용한 실패를 없앤다
  ↓
2단계  호모그래피 정합   ← 기하 예산을 1픽셀에서 늘린다
  ↓
3단계  다중 프레임 합의  ← 인식을 안 고치고 오답을 줄이는 유일한 길
  ↓
4단계  크롭 분류        ← 새 응답자 표본이 있어야 판정 가능
```

**1·2단계는 사진을 쓸 만하게 만드는 일이고, 3·4단계는 스캔에도 이득이 된다.**
0단계 결과가 나쁘면 1·2를 건너뛰고 3·4로 갈 수도 있다 — 그 판단은 숫자를 보고 한다.

## 이 계획이 지키는 것

- **계측을 먼저, 수정은 그다음** ([[CLAUDE.md]] §2)
- **단계마다 죽이는 조건을 착수 전에 등록** (§12.3 형태)
- **스캔 경로 회귀 금지** — 브라우저 오답 10 이하 · 빈칸 침범 0
- **합성 이미지로 판정하지 않는다** (§2) — 실제 촬영본으로만

## 0단계 · 1회차 — 사진이 격자 검출을 멈춰 세운다 (2026-08-26)

사용자가 1~5번 학생의 선별검사지·만족도조사를 각 5장씩 촬영해 주었다.
**정확도를 재기 전에 파이프라인이 사진을 처리할 수 있는지**부터 물었고, 못 한다.

### 0-1 먼저 확인된 것 — 두 가지는 문제가 아니다

| | |
|---|---|
| **EXIF 방향** | 문제 없음. 방향값 6이고 `sharp().rotate()`가 3024x4032 세로로 세운다 |
| **처리 속도** | 문제 없음. 1220만 화소에서 load 130ms · paperBounds 5ms · grid 83ms |

> **"파이프라인이 사진 크기를 감당 못 한다"고 먼저 적었다가 실측에서 틀렸다.** 5장짜리
> 프로브가 10분에 안 끝난 것을 크기 탓으로 읽었는데, 단계별로 재니 전부 빠르다.

### 0-2 업로드 축소가 일어나지 않는다

앱의 축소 사다리(`IMAGE_SHRINK_OPTIONS`, 상한 3.8MB)를 그대로 흉내 냈다.

```
세운 뒤 3024x4032  ->  scale 1.0 q0.86  ->  3024x4032  2.6~2.9MB
```

**한 단계도 줄지 않는다.** 스캔 경로가 893x1262(110만 화소)인 데 비해 사진은 1220만 화소가
그대로 서버에 도달한다. 속도는 문제가 아니지만, 검출기가 보는 세계가 11배 크다는 뜻이다.

### 0-3 ★ 멈춤의 원인 — 조합 폭발

파일에 즉시 기록하는 표식으로 좁혔다. `console.log`는 vitest가 버퍼링해서
**죽는 순간의 줄이 유실된다** — 그래서 처음에는 엉뚱한 단계를 범인으로 지목했다.

```
[13:08:09.316] cagi-p1.jpg grid done     53ms
[13:08:09.622] cagi-p2.jpg grid done     32ms
[13:08:09.854] cagi-p3.jpg grid…         <- 240초 넘게 반환 없음
```

[tableGridDetection.ts](../src/lib/recognition/tableGridDetection.ts)의
`matchTemplateLinePattern`이다.

```ts
const visit = (start: number, selected: number[]) => {
  if (selected.length === expected.length) { /* 채점 */ return; }
  const remaining = expected.length - selected.length;
  for (let index = start; index <= sorted.length - remaining; index++) {
    visit(index + 1, [...selected, sorted[index]]);
  }
};
```

**검출선 n개에서 기대선 k개를 고르는 C(n, k) 전수 탐색이고, 가지치기도 상한도 없다.**
가지치기가 없는 이유는 구조적이다 — 허용치 검사가 `gap / 선택 전체의 span`으로 정규화되므로
**접두사만으로는 기각할 수 없다.** 스캔은 n이 k에 가까워 순식간이지만 사진은 그렇지 않다.

### 0-4 조치 — 탐색 예산 상한

`TEMPLATE_LINE_MATCH_BUDGET = 200_000` 방문을 넘으면 **일치 없음**을 보고한다.
그것은 아무것도 맞지 않을 때 이미 나오던 결과이고, 필드는 행 검출이나 고정 템플릿으로 떨어진다.

**지금 상한 안에서 끝나는 입력의 동작은 그대로다.** 단위 테스트 129개 전부 통과.
사진 5장이 모두 완주한다.

> 부분 탐색이 우연히 찾은 최선을 반환하지 않는다. 전수를 못 본 탐색의 "최선"은 최선이 아니므로
> `null`을 돌려준다.

### 0-5 그래서 드러난 진짜 실패 — 격자가 안 잡힌다

```
사진        종이 검출            프레임    격자 필드(13개 중)
cagi-p1    coverage 0.66x0.69   usable        2
cagi-p2    coverage 0.81x0.84   usable        9
cagi-p3    coverage 0.71x0.75   usable        2
cagi-p4    coverage 0.63x0.66   usable        3
cagi-p5    coverage 0.67x0.71   usable       10
```

**좌표계는 선다. 표 구조를 못 찾는다.** 그리고 2에서 10까지 요동친다.

기제는 검출기 정의에 있다 — `detectVerticalLines`는 **한 픽셀 열을 세로로 훑어** 어두운 화소
비율이 문턱을 넘는 열만 선으로 친다. 사진은 원근으로 모든 괘선이 조금씩 기울어 있어
**한 열에 모이지 않고 여러 열로 흩어진다.** 그래서 선이 덜 잡히고, 잡힌 조각들을 템플릿에
맞추려는 조합 탐색이 폭발한다. **0-3과 0-5는 같은 원인의 두 얼굴이다.**

`pageInkRatio`가 0.72~0.81인 것도 같은 이야기다 — 나무 책상이 문턱(200)보다 어두워
**화면의 4분의 3이 "잉크"로 잡힌다.**

### 0-6 다음

정확도를 재는 것은 아직 이르다. 격자가 2/13만 잡히는 상태의 `CORRECT`는 인식 성능이 아니라
**좌표 실패를 재는 것**이다. 1단계(워프 검증)와 2단계(호모그래피 정합)가 이 측정 앞에 와야 한다.

## 1단계 · 1회차 — 보정은 한 번도 돈 적이 없었다 (2026-08-26)

**0-6에서 "1단계(워프 검증)를 먼저"라고 적었다. 검증해보니 워프가 실행된 적이 없었다.**

### 1-1 증상

사진을 순차 업로드하면 보정 확인 화면 없이 곧바로 올라간다. 저장된 파일을 재보니
`3024x4032` — EXIF 회전만 걸린 **원본**이다. `processSelectedFile`은 보정이 실패하면
조용히 원본을 올리므로, **밖에서는 보정된 페이지와 구분이 안 된다.**

계측기를 붙여 이유를 물었다(`__kpgaCorrectionProbe`, dev 전용):

```
status=skipped  method=none  confidence=0  reason=timeout
```

9초를 다 쓰고 죽는다.

### 1-2 원인 — `cv`는 thenable이다

워커 안에 단계별 핑을 넣고 잡았다.

```
created            +0ms
kpga-boot          +27ms   importScripts=function
onmessage          +27ms   "warmup"
import-start       +27ms
import-done        +120ms  cv=object  Mat=false
awaiting-runtime   +120ms
runtime-ready      +180ms  then="function"   ← cv.then 이 함수다
cv-resolved        ────    영원히 오지 않는다
```

`cv`는 emscripten Module이고 **`then` 메서드를 가진다.** 그래서 `resolve(cv)`는 프로미스를
그 module에 위임하고(thenable adoption), module의 `then`은 자기 자신으로 다시 해결하므로
**프로미스가 영원히 정착하지 않는다.** `await` 도 같은 함정을 밟는다.

그 뒤는 전부 이 하나에서 나온 것이다 — 클라이언트가 타임아웃 → 워커 terminate →
`reason=timeout` → 패널이 원본을 그대로 업로드. 일괄 경로는 페이지당 3초라 더 빨리 죽는다.

**조치**: `cv`를 상자에 넣어 프로미스가 thenable을 보지 않게 한다.

```ts
type OpenCvBox = { cv: any };
resolve({ cv });                          // resolve(cv) 아님
const { cv } = await loadOpenCvInWorker();
```

[perspectiveCorrect.worker.ts](../src/lib/documentScanner/perspectiveCorrect.worker.ts)와,
호출자가 없지만 같은 결함을 가진 [loadOpenCv.ts](../src/lib/documentScanner/loadOpenCv.ts)
둘 다 고쳤다.

**워밍업: 정착 안 함 → `ok=true` 293ms.**

### 1-3 계측기가 측정 대상을 바꾼 사고

진단 중에 `new Worker(new URL(...))`를 두 줄로 쪼갰다.

```ts
const workerUrl = new URL('./perspectiveCorrect.worker.ts', import.meta.url);
const worker = new Worker(workerUrl);
```

webpack의 워커 인식은 **인라인 형태만** 잡는다. 쪼개는 순간 워커가 아니라 `asset/resource`가
되어 원본 `.ts`가 그대로 방출되고, `.ts`는 `Content-Type: video/mp2t`로 나가며 `nosniff`가
걸려 있어 실행이 거부된다. 이 상태로 프로덕션 빌드를 돌려 **"프로덕션도 깨져 있다"고 판정할
뻔했다.** 인라인으로 되돌리니 정상 워커 청크가 나온다. CLAUDE.md §2 — 계측기가 무엇을 재고
있는지 확인하라 — 의 다섯 번째 사례.

### 1-4 보정이 실제로 하는 일 (사진 10장)

| | 결과 | 신뢰도 | 시간 |
|---|---|---|---|
| cagi-p1 | no-document | 0 | 668ms |
| **cagi-p2** | **corrected** | **0.950** | 530ms |
| cagi-p3 | no-document | 0 | 1392ms |
| cagi-p4 | no-document | 0 | 300ms |
| cagi-p5 | no-document | 0 | 334ms |
| sat-p1 | no-document | 0 | 241ms |
| **sat-p2** | **corrected** | **0.951** | 497ms |
| **sat-p3** | **corrected** | **0.989** | 406ms |
| **sat-p4** | **corrected** | **0.958** | 294ms |
| **sat-p5** | **corrected** | **0.987** | 278ms |

**10장 중 5장.** 성공하면 신뢰도가 0.95~0.99로 높고, `low-confidence`는 **한 번도 없다** —
깨끗한 사각형을 찾거나 아무것도 못 찾거나 둘 중 하나다. 시간은 전부 1.4초 이내.

### 1-5 그런데 보정된 페이지의 격자 검출이 0이다

`cagi-p2`는 눈으로 봐도 완벽히 펴졌고 정합 프레임이 빈 양식과 소수점 셋째 자리까지 같다
(`[0.093,0.081 0.886x0.868]`). 그런데 격자 필드가 **0개**다. 보정 전 원본은 9개였다.

크기를 900 / 1422 / 1654 / 2400으로 바꿔가며 재봤다. **전부 0이다. 해상도가 아니다.**

가르는 숫자는 `pageInkRatio`다.

```
빈 양식(스캔)        0.087
보정된 사진          0.615      ← 페이지의 61%가 "잉크"
원본 사진            0.717
```

`calculatePageQuality`는 `pixel < 200`이면 잉크로 센다. **스캐너 백지를 전제한 고정
임계값이다.** 실내 조명 아래 흰 종이는 그 아래로 내려가므로 페이지 전체가 잉크가 되고,
괘선 검출기는 온통 선인 화면에서 선을 못 찾는다.

### 1-6 조명 평탄화가 그것을 되돌린다

무거운 블러로 종이의 국소 밝기를 추정해 나눠준 뒤(배경 제거) 다시 쟀다.

| 이미지 | ink | 격자 필드 |
|---|---|---|
| 빈 양식 (기준) | 0.087 | **12** / 13 |
| 보정된 사진, 평탄화 없음 | 0.615 | **0** |
| 보정 + 평탄화 σ/8 | 0.169 | **11** |
| 보정 + 평탄화 σ/16 | 0.172 | **11** |
| 보정 + 평탄화 σ/32 | 0.164 | **11** |
| **원본 사진 + 평탄화만 (워프 없음)** | 0.270 | **11** |

두 가지가 나온다.

1. **평탄화가 잠금장치다.** 0 → 11. 블러 반경을 8배 바꿔도 11로 같다 — 맞춰 넣은 상수가
   아니라 견고한 연산이다.
2. **평탄화만으로도 11이 나온다. 워프 없이도.** 그리고 원본 사진의 콘텐츠 상자가
   `[0.142,0.134 0.716x0.730]`에서 빈 양식과 동일한 `[0.093,0.081 0.886x0.868]`로 붙는다 —
   **그림자가 정합 프레임까지 밀고 있었다.**

### 1-7 계획을 고쳐 적는다

**2단계(호모그래피)는 첫 표적이 아니다. 톤 정규화가 첫 표적이다.** 이 문서가 0단계에서
기하 문제로 진단한 것은 절반만 맞았다 — 괘선이 여러 열로 흩어지는 것도 사실이지만,
**그보다 먼저 페이지 전체가 잉크로 읽히고 있었다.**

아직 재지 않은 것: 이 11개 필드로 실제 인식이 무엇을 내는지. `WRONG = 0`은 여전히 절대
조건이고 사진 경로에서는 **한 번도 측정된 적이 없다.**

## 1단계 · 2회차 — 사진 경로에 처음으로 정답표를 댔다 (2026-08-26)

사진 5명은 스캔 세트와 **같은 학생, 같은 순서**다 (정답표 page2 = 14/여/중2/전부 0이
`cagi-p2` 사진과 일치). 그래서 `local-scans/answer-key.json`이 사진에 그대로 적용된다.
**사진 경로가 점수로 측정된 것은 이번이 처음이다.**

### 2-1 기준선

```
원본 사진 5명    CORRECT 8   WRONG 13   미확정 96
```

채워진 21칸 중 **13칸이 오답이다.** 그리고 실패가 계통적이다 — p5는 `cagi.q01~q06`이
전부 `"3"`인데 정답은 `"0"`이다. 격자가 통째로 밀려 있다는 뜻이다.

`WRONG = 0`이 절대 조건인 제품에서 이 숫자는 **"인식률이 낮다"가 아니라 "쓸 수 없다"**이다.

### 2-2 톤 정규화 — 기각

`pageInkRatio`가 스캔의 8배라는 것을 근거로 조명 평탄화를 태웠다.

| | CORRECT | WRONG | 미확정 |
|---|---|---|---|
| 원본 | 8 | 13 | 96 |
| 나눗셈 평탄화 (σ/16) | 1 | **0** | 116 |
| 배경 차감 gain 1.0 (ink를 스캔과 같은 0.09~0.13으로 맞춤) | 0 | **0** | 117 |

오답은 사라졌지만 **정답도 같이 사라졌다.** 게이트 추적이 이유를 말한다.

```
refused=grid-unverified   (13개 필드 전부 동일)
page=0.000   blank=0.156   shift=0
```

사진 셀이 완전 백색인데 빈 양식 같은 자리에는 인쇄 원이 15.6% 있다. **톤이 아니라 정렬
실패다.** `contentBoundsSource=template`이 그 뜻이다 — 종이 경계를 못 찾아 *이미지 전체가
종이*라고 가정한다. 스캔에서는 맞는 가정이고, 사진에서는 **격자가 책상 위에 얹힌다.**

**CLAUDE.md §5.4에 따라 기각한다.** 미확정이 96 → 116으로 늘었다. 오답이 준 것은 신호가
좋아져서가 아니라 게이트가 전부 거절해서다.

### 2-3 순서가 반대였다 — 워프가 먼저다

양면 모두 워프에 성공한 유일한 학생(2번)으로 세 조건을 나란히 쟀다. **같은 종이다.**

| 조건 | CORRECT | WRONG | 미확정 |
|---|---|---|---|
| 원본 사진 | 2 | 0 | 22 |
| **워프만** | **4** | **0** | **20** |
| 워프 + 배경 차감 | 1 | 0 | 23 |

**워프가 정답을 두 배로 만들고 `WRONG = 0`을 지킨다. 정규화는 그 위에서 깎아먹는다.**

1회차 §1-7에서 "톤 정규화가 첫 표적"이라고 적은 것은 **틀렸다.** 그 결론은 *워프되지 않은*
사진에서 나온 것이고, 거기서 평탄화가 한 일은 폴백 정합을 우연히 개선한 것이었다. 워프가
돌면 정합은 이미 옳고, 정규화는 채점기가 필요로 하는 잉크를 지울 뿐이다.

### 2-4 그러면 표적은 워프 성공률이다

10장 중 5장이 `no-document`, 신뢰도 0이다. `low-confidence`는 **한 번도 없다** — 깨끗한
사각형을 찾거나 아무것도 못 찾거나다.

사진을 나란히 보면 이유가 보인다. 다섯 장 모두 **밝은 나무 책상 위의 흰 종이**이고,
성공한 p2만 종이가 화면을 거의 채우며 테두리가 프레임과 나란하다. 나머지는 종이가 작고
회전이 있고 주변 나무가 넓다. 흰 종이 대 밝은 나무는 대비가 약해 Canny가 종이 테두리보다
**본문 블록 테두리**를 더 강하게 잡는다.

**이것이 2단계(인쇄 구조로 정합)가 원래 겨냥한 문제다.** 신분증 OCR이 카드 외곽선에
의존하지 않는 것과 같은 이유다. 다만 이제는 근거가 있다 — 워프가 도는 학생에서 정답이
두 배가 되고 오답이 0으로 유지된다는 측정값.

### 2-5 아직 열려 있는 것

- 워프 성공률 50%를 올리는 것. **표적 지표는 `no-document` 비율이다.**
- 워프된 학생 하나로 잰 CORRECT 4는 **표본 1**이다. 워프 성공률이 오르면 다시 재야 한다.
- 미확정 20칸은 여전히 크다. 워프가 도는 상태에서 무엇이 남는지는 아직 안 봤다.
