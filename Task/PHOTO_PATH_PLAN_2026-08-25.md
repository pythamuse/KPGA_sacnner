# 사진 경로 — 측정과 단계별 개선 계획 (2026-08-25)

## 배경

이 프로젝트는 **카메라로 찍은 사진을 인식하는 기능을 제공하고 있다.** 그런데
**저장소 어디에도 사진 기반 인식 정확도 측정이 없다.** 모든 숫자 — 정답표 19명,
`CORRECT 354/432`, 브라우저 확인 필요 135 · 자동 입력 302 · 오답 10, 잡음 바닥 76칸 —
는 전부 **스캔 PDF**에서 나왔다.

스캔 경로는 `WRONG = 0`을 절대 조건으로 지키는데([[CLAUDE.md]] §3), **사진 경로는 그 조건이
성립하는지 확인된 적이 없다.** 검증되지 않은 기능이 검증된 것처럼 제공되고 있다는 것이,
오독률 자체보다 앞서는 문제다.

### 왜 사진이 스캔보다 훨씬 어려운가 — 기제

이 파이프라인은 **모양을 인식하지 않는다. 기준 이미지와의 잉크 차이를 잰다.**

```ts
// markDensity.ts:1368
const residualInk = Math.max(0, actualInk - baselineInk - 0.08);
```

형태 통계(`largestComponentSize` · `largestComponentRatio` · `diagonalRatio`,
`markDensity.ts:1688-1755`)는 존재하지만 **통과/거부 문턱으로만** 쓰이고 점수에 들어가지
않는다(`hasStructuredTemplateMark`, `:1679-1686`). 체크·X·동그라미·낙서가 같게 취급된다.

그래서 **커밋된 빈 양식 PNG와 화소 단위로 맞아야 한다.** 정렬 탐색의 사거리는
`clamp(round(1/pitch), 1, 4)` — **약 1 소스 픽셀**이다(`markDensity.ts:1901-1906`).

그 예산이 얼마나 좁은지는 측정돼 있다.

| 관측 | 값 | 출처 |
|---|---|---|
| 같은 용지·같은 기기 재급지로 뒤집힌 칸 | **76칸** | [[WEAK_SIGNAL_STABILITY_PLAN_2026-08-24]] §21 |
| 그때 셀이 움직인 폭 | 1.7% ≈ **1.5px** | 같은 문서 §27.3 |
| 행 검출이 감당하는 기울기 예산 | `MAX_RULE_DRIFT_RATIO = 0.0025` (주석: 스캔은 최대 0.3도) | `tableRowDetection.ts:53-66` |

**급지 흔들림만으로 오차 예산이 소진된다.** 휴대폰 사진의 2도 기울기는 그 예산의 한 자릿수 밖이다.

### 지금 사진 경로가 실제로 하는 일

원근 보정은 **있다.** OpenCV.js를 Web Worker에서 돌린다
(`src/lib/documentScanner/perspectiveCorrect.worker.ts`).

- 그레이스케일 → `GaussianBlur(5,5)` → **세 가지 검출맵**: `Canny(50,150)`,
  `Canny(85,220)`, `adaptiveThreshold(GAUSSIAN, INV, 31, 11)` (`:101-121`)
- 맵마다 `findContours` → `approxPolyDP`를 **세 배율**(0.015 / 0.02 / 0.03)로 (`:161-172`)
- 볼록한 사각형만 남기고 `evaluateQuad`로 채점, 최고 신뢰도 선택 (`:174-189`)
- `getPerspectiveTransform` → `warpPerspective` → ROI 템플릿에 맞춘 **1422×1968** 고정 출력

경로별 설정 (`ImageUploadPanel.tsx`):

| 경로 | 검출 해상도 | 시간 제한 | 최소 신뢰도 |
|---|---|---|---|
| 카메라 촬영 | 전체 프레임 | 9000ms | 0.58 |
| 단일 파일 | 장변 ≤1600 | 9000ms | 0.58 |
| 일괄(이미지) | 장변 ≤1100 | **3000ms** | **0.62** |

PDF 렌더 페이지는 정책으로 제외된다(`perspectiveCorrectionPolicy.ts:8-14`).

### ★ 그런데 보정의 품질을 아무도 재지 않는다

- **`confidence`는 사각형의 그럴듯함이지 왜곡 잔차가 아니다.**
  `0.35·면적 + 0.30·종횡비 + 0.20·모서리일관성 + 0.15·각도`
  (`perspectiveCorrect.ts:174-184`). 종횡비 항은 **1.9배까지** 봐준다
- **워프 후 기하 검증이 없다.** 재투영 오차도, 잔차도, 템플릿 구조 대조도 없다
  (사람이 미리보기를 확인하는 단계와 서버의 양식 재분류는 있지만, 둘 다 기하를 재지 않는다)
- **테스트가 이미지를 한 장도 워프하지 않는다.** `tests/perspective-correct.test.ts`는
  합성 좌표로 모서리 정렬과 수락/거부만 본다
- **실패하면 원본이 그대로 올라간다.** 카메라·단일 경로는 **경고도 없다**
  (`ImageUploadPanel.tsx:477-491`, `:771-798`). 일괄만 한국어 경고를 큐에 넣는다
- 스펙(`Docs/04_OCR_FORM_RECOGNITION_SPEC.md:217-227`)이 정한 **재촬영 조건은 구현돼 있지 않다**

## 0단계 — 먼저 잰다. 아무것도 고치지 않는다

**이 단계를 건너뛰면 나머지 전부가 감으로 하는 일이 된다.** [[CLAUDE.md]] §2가 규정한 순서다.

### 0.1 필요한 표본

**같은 19명의 같은 용지**를 휴대폰으로 촬영한다. **정답표가 그대로 붙으므로 새 정답표가
필요 없다** — 이것이 이 측정을 싸게 만드는 핵심이다.

**처음부터 38장을 찍지 않는다.** 5명(10장)이면 자릿수는 나온다.

| 회차 | 분량 | 답하는 것 |
|---|---|---|
| 0-A | **5명 = 10장** | 사진이 스캔 대비 몇 배 나쁜가. 자릿수 |
| 0-B | 나머지 14명 = 28장 | 0-A가 "쓸 만하다"로 나왔을 때만 |

### 0.2 촬영 조건 — 두 종류를 나눠 찍는다

**섞으면 원인을 못 가린다.**

| 조건 | 어떻게 | 무엇을 분리하는가 |
|---|---|---|
| **정상 촬영** | 정면, 밝은 곳, 그림자 없이, 용지가 프레임 안에 다 들어오게 | 사진 경로의 **상한** |
| **현실 촬영** | 평소 쓰듯 — 약간 기울고, 손 그림자 지고, 살짝 흔들려도 그대로 | 실사용에서의 값 |

0-A에서는 **정상 촬영만** 한다. 그것도 나쁘면 현실 촬영은 볼 것도 없다.

### 0.3 판정

스캔 기준선과 나란히 놓는다.

```
                    스캔(기준선)   사진
CORRECT / 432          354          ?
WRONG                    7          ?
빈칸 침범                0          ?
원근 보정 성공률         해당없음     ?
```

| 결과 | 다음 |
|---|---|
| `WRONG`이 스캔과 비슷하고 `CORRECT`가 80% 이상 | 사진 경로는 쓸 만하다. 1단계로 |
| `WRONG`이 늘거나 빈칸 침범이 생김 | **기능을 경고와 함께 제한하는 것이 먼저다.** 1단계보다 우선 |
| `CORRECT`가 절반 이하 | 부분 개선으로 안 된다. 3·4단계(다중 프레임·분류기)로 건너뛴다 |

### 0.4 하니스 변경 (0단계에서 유일하게 쓸 코드)

지금 하니스는 PDF만 받는다(`tests/real-scan-measure.test.ts:51-53` 등). **디렉터리의
이미지 파일을 페이지로 받는 입력을 더한다.** 렌더 단계만 갈라지고 그 뒤는 같은 경로다.

```
PHOTO_CAGI_DIR="C:/.../사진/선별검사"  PHOTO_SAT_DIR="C:/.../사진/만족도"
```

> **사진을 PDF로 합쳐 오지 않는다.** 휴대폰의 "스캔" 기능이나 PDF 변환 앱은 **자체 원근
> 보정과 대비 강화를 적용한다.** 그러면 우리가 재려는 것이 사라진다. **원본 JPG 그대로** 둔다.

## 1단계 — 워프를 검증한다 (부품이 이미 있다)

### 무엇이 문제인가

`confidence`는 **사각형이 그럴듯한가**를 잰다. 정작 필요한 것은 **워프 후에 양식이 제자리에
왔는가**다. 지금은 그럴듯한 사각형이면 통과하고, 실패해도 원본이 조용히 올라간다.

### 무엇을 하는가

**보정 후 이미지에서 표 괘선을 검출해 템플릿 위치와 대조한다.** `tableGridDetection.ts`가
이미 그 일을 한다 — 새로 만들 것은 **대조와 판정**뿐이다.

```
보정된 이미지 → buildCagiGridDetection / buildSatisfactionGridDetection
             → 검출된 행·열 위치를 템플릿 기대 위치와 비교
             → 잔차가 기준 밖이면 재촬영 요구
```

이것이 카드 리더가 하는 일이다 — **알려진 구조가 제자리에 왔는지로 정합을 검증**한다.

### 판정 기준 (착수 전 등록)

- **잔차와 인식 결과가 상관이 있어야 한다.** 잔차가 큰 사진에서 `WRONG`이 늘지 않으면
  잔차는 쓸모없는 지표다 → 폐기
- 재촬영을 요구하는 문턱은 **0단계 데이터에서** 정한다. 감으로 고르지 않는다

### 곁들여 고칠 것

- **카메라·단일 경로의 조용한 실패.** 일괄에는 경고가 있는데 나머지엔 없다
  (`ImageUploadPanel.tsx:487-489`, `:781-783`)
- `perspectiveCorrect.ts`의 **죽은 코드** `detectDocumentQuad` / `warpToRectangle` /
  `loadOpenCv` — 호출부가 없다. 다시 배선되면 `evaluateQuad` 게이트를 우회한다

## 2단계 — 종이 테두리가 아니라 인쇄 구조로 정합한다

### 무엇이 문제인가

지금 정합은 **두 단계 모두 약하다.**

1. `pageBounds`(밝은 성분) → `contentBounds`는 **선형 스케일**뿐이다
   (`markDensity.ts:327-332`). 회전·원근을 표현할 수 없다
2. 셀 단위 `findBestBaselineAlignment`는 **평행이동만**, 사거리 **약 1픽셀**

### 무엇을 하는가

**검출된 괘선을 템플릿 괘선에 대응시켜 호모그래피를 적합한다.** 대응점을 찾는 코드는
이미 있다(`tableGridDetection.ts`) — **새로 만들 것은 적합 단계뿐이다.**

호모그래피는 회전·배율·원근을 한 번에 흡수한다. 이것이 카드 리더가 특징점 매칭 +
RANSAC으로 하는 일과 같은 것이고, 여기서는 **특징점이 이미 검출된 괘선**이다.

### 판정 기준 (착수 전 등록)

- **스캔에서 회귀가 없어야 한다.** 브라우저 오답 10 이하 · 빈칸 침범 0 · 확인 필요 135 이하
- **사진에서 개선이 있어야 한다.** 0단계 수치 대비
- 스캔이 나빠지면 **사진이 좋아져도 기각**한다. 스캔이 주 경로다

### 위험

이것은 **좌표계를 바꾸는 변경**이다. [[CLAUDE.md]] §5.5가
*"좌표계·페이지 기하는 병목이 아니다"* 를 닫아뒀는데, **그것은 스캔에 대한 결론이다.**
사진에서는 다시 열릴 수 있지만, **스캔 회귀 금지**를 절대 조건으로 건다.

## 3단계 — 여러 프레임의 합의 (이미 만들어 놓은 기제)

### 왜 이것이 강한가

§21이 잰 잡음 바닥 76칸은 **위험이자 자원**이다. 한 번 찍어 애매한 칸도, **두세 프레임이
같은 값을 내면 그것은 우연이 아니다.**

그리고 그 판정기는 **이미 만들어져 있다.** §24의 3스캔 합의 분류
(`stable-correct` / `gate wobbles`)가 정확히 그 기제다
(`tests/scan-repeat-measure.test.ts`).

```
지금(측정용)   3개 스캔 → 칸마다 세 읽기 → 세 번 다 같으면 stable
제품(제안)     2~3 프레임 → 칸마다 여러 읽기 → 일치하면 자동 입력, 갈리면 확인 필요
```

### 무엇을 하는가

촬영 화면에서 **연속 2~3프레임을 잡고**, 각각을 인식해 **칸 단위로 합의**한다.
합의된 칸만 자동 입력하고, 갈린 칸은 확인 필요로 남긴다.

### 판정 기준

- **오답이 줄어야 한다.** 확인 필요가 늘더라도 오답이 줄면 이득이다 — §3의 우선순위 그대로
- 프레임 수가 늘어난 만큼의 **시간 비용**을 잰다

### 이 단계의 특별한 성질

**인식을 하나도 안 고치고 오답을 줄일 수 있는 유일한 방법이다.** 다른 단계는 전부
파이프라인을 건드리지만, 이것은 **같은 파이프라인을 여러 번 돌려 합의를 본다.**

## 4단계 — 차감이 아니라 크롭 분류

### 왜 필요한가

브라우저 오답 10건의 기제는 [[FIELD_TEST_2026-08-21]] §22.4에 정리돼 있다.

```
X 취소        5건   취소한 칸이 잉크가 많아 이긴다
꼬리 침범     4건   체크 꼬리가 옆 칸을 넘는다
원 채우기     1건   ⓪을 새까맣게 메웠다
```

**전부 "잉크가 얼마나 있나"로는 못 가르는 것들이다.** X 취소를 취소로 알아보려면
**획의 방향과 교차**를 봐야 하고, 그것은 모양 인식이다.

### 무엇을 하는가

셀 크롭을 작은 분류기로 판정한다 — `표시 없음 / 표시 / 취소된 표시`.

**데이터 수집기는 이미 있다.** `src/lib/labelExport/`가 검수 완료된 학생에서 후보별 라벨을
모은다. **다만 특징 벡터만 저장하고 크롭은 저장하지 않는다**(`types.ts`의 `LabelRow`).
**크롭을 함께 저장하도록 넓히는 것이 첫 걸음이다.**

### 위험 — 가장 크다

- **19명으로 학습하면 §19.3의 과적합 함정에 그대로 걸린다.** 오답 10건 중 9건이 세 학생에서
  나온다. 새 응답자 표본 없이는 판정 자체가 불가능하다
- 모델 저장·추론·버전 관리가 저장소에 들어온다. 별개의 큰 변경이다

### 착수 조건

**새 응답자 표본이 먼저다**([[WEAK_SIGNAL_STABILITY_PLAN_2026-08-24]] §19.5).
그 전에는 크롭 수집만 해둔다 — **모으는 것은 지금 해도 손해가 없다.**

## 순서와 그 이유

```
0단계  측정            ← 이것 없이는 나머지가 전부 감이다
  ↓
1단계  워프 검증        ← 부품이 있고, 조용한 실패를 없앤다
  ↓
2단계  호모그래피 정합   ← 기하 예산을 1픽셀에서 늘린다
  ↓
3단계  다중 프레임 합의  ← 인식을 안 고치고 오답을 줄이는 유일한 길
  ↓
4단계  크롭 분류        ← 새 응답자 표본이 있어야 판정 가능
```

**1·2단계는 사진을 쓸 만하게 만드는 일이고, 3·4단계는 스캔에도 이득이 된다.**
0단계 결과가 나쁘면 1·2를 건너뛰고 3·4로 갈 수도 있다 — 그 판단은 숫자를 보고 한다.

## 이 계획이 지키는 것

- **계측을 먼저, 수정은 그다음** ([[CLAUDE.md]] §2)
- **단계마다 죽이는 조건을 착수 전에 등록** (§12.3 형태)
- **스캔 경로 회귀 금지** — 브라우저 오답 10 이하 · 빈칸 침범 0
- **합성 이미지로 판정하지 않는다** (§2) — 실제 촬영본으로만
