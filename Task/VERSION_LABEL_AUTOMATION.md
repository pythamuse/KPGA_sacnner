# 테스트 버전 라벨 자동화 — 주문서 (2026-09-07 등록, 착수 전)

사용자 지시로 **다음 라운드**에 넣는다. 이 문서는 착수할 사람이 바로 실행할 수 있게 사실만 적는다.

## 1. 왜

2026-09-07에 인식 개선 23커밋을 배포하면서 `src/app/page.tsx`의 라벨을 갱신하지 않았다. 배포된 화면이
나흘 전 빌드(`v2026-09-03.1`)를 가리켰고, **사용자가 그걸 보고 배포가 잘못됐는지 물었다.** 코드는 정상
배포돼 있었다. 손으로 올리는 규칙이라 빠뜨릴 수 있다.

## 2. 지금 규칙

[README.md](../README.md) §"배포마다 테스트 버전 번호 갱신 (필수)"(2026-08-10 도입):

- 위치: `src/app/page.tsx`의 `BrandHeader`, 문자열 `테스트 버전 v2026-09-03.1` (하드코딩)
- 형식: `v{배포일 YYYY-MM-DD}.{그날 몇 번째 배포인지}`
- **"코드만 바뀌고 이 줄이 그대로면 배포 자체를 빠뜨린 것으로 간주한다"**
- 문서 전용 커밋은 갱신하지 않는다

## 3. 만들 것

빌드 시점에 커밋에서 라벨을 뽑는다. 재료는 이미 있다:

- 호스트가 Vercel이다(`process.env.VERCEL`을 [uploadStore.ts:86](../src/lib/storage/uploadStore.ts)·[labelStore.ts:201](../src/lib/labelExport/labelStore.ts)가 쓴다)
- `NEXT_PUBLIC_*`의 **빌드 시점 치환**을 이 저장소가 이미 쓰고 있다([statelessSession.ts:15](../src/lib/stateless/statelessSession.ts))
- `next.config.mjs`에는 `env` 블록이 아직 없다

구현 방향(한 가지 안, 더 나은 방법이 있으면 바꿔도 된다):

```js
// next.config.mjs
env: {
  NEXT_PUBLIC_BUILD_SHA: (process.env.VERCEL_GIT_COMMIT_SHA || 'local').slice(0, 7),
  NEXT_PUBLIC_BUILD_DATE: new Date().toISOString().slice(0, 10),
},
```

## 4. ★ 반드시 빌드 시점에 고정할 것

**렌더 시점에 `new Date()`를 부르면 하이드레이션이 깨진다** — 서버와 클라이언트가 다른 값을 그린다.
`NEXT_PUBLIC_*` 치환은 빌드 때 문자열로 박히므로 안전하다. 이 함정을 피하는 것이 이 라운드의 유일한 기술적 위험이다.

로컬 `next dev`에서는 `VERCEL_GIT_COMMIT_SHA`가 없다. `local`처럼 **배포본과 구별되는** 값이 나와야 한다 —
로컬이 배포본처럼 보이면 이 라벨의 목적이 사라진다.

## 5. 이 라운드가 결정해야 할 것 (코드보다 먼저)

자동화는 빠뜨림을 없애지만 **사람이 읽는 신호 하나를 같이 없앤다.** 지금 규칙의 "이 줄이 그대로면 배포를
빠뜨린 것"은 2026-09-07에 실제로 작동해서 누락을 잡았다. 자동화하면 라벨은 항상 맞지만, 그 대신
"배포를 빠뜨렸다"는 상태 자체가 관측되지 않는다.

착수 전에 답할 것:

1. 라벨에 무엇을 보일 것인가 — 날짜만? 날짜+SHA? 순번은 버리는가(자동화하면 "그날 몇 번째"는 의미가 없다)
2. README의 수동 규칙을 **폐기**하는가, 자동 라벨과 병기하는가
3. 사용자가 화면의 SHA로 무엇을 하기를 기대하는가(커밋 대조? 단순 구별?) — 용도가 없으면 날짜만으로 충분하다

## 6. 완료 기준

- 배포본 화면의 라벨이 그 배포의 빌드를 **유일하게** 가리킨다
- 로컬 dev가 배포본과 구별된다
- 하이드레이션 경고 없음(빌드 시점 고정 확인)
- README §"배포마다 테스트 버전 번호 갱신"이 새 방식과 일치하게 갱신된다
- 이 변경 자체는 코드 변경이므로, **그 배포에는 아직 수동 규칙이 적용된다**(라벨을 손으로 한 번 더 올린 뒤 자동화가 인계받는다)
