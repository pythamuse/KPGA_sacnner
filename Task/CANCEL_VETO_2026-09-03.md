# 취소 표시 거부권 — 문턱 0.7이 §5.4 한도 안에 든다 (2026-09-03)

**표적**: 남은 오답 9칸은 전부 두 칸에 잉크가 있는 경합이고, 그중 다수는 학생이 한 칸에 표시했다가 X로 지운 자리다([FIELD_TEST](FIELD_TEST_2026-08-21.md) §34.10).
**작성**: 오퍼스 서브에이전트. 계측 `contest-shape` `f6c12b5`(형태 특징 8종, 트레이스 전용), 거부권 `cancel-veto` `a1d0a34`(4중 게이트 통과 뒤
`crossingScore ≥ 0.6`(기본) **이고** `inkBboxFill ≥ 0.22`면 자동값을 거절하고 경합으로 표시; 2위를 대신 채우지 않음). 시험 504 통과, off 바이트 동일(md5).
**판정**: 메인 에이전트.

## 1. 절차 사고 하나 — off를 `=0`으로 준 판정

첫 판정에서 off/on이 완전히 같은 수치로 나왔다. 원인은 코드가 아니라 판정 스크립트였다: `markDensity.ts`의 opt-in 플래그는 `Boolean(process.env.X)`로
검사하므로 **`MARK_CANCEL_VETO=0`은 거부권을 켠다.** 스캔 8회·사진 8회를 헛돌렸다. 변수를 비우고 다시 재니 네 세트 모두 main과 정확히 일치
(`361/5/71 · 346/8/83 · 348/3/86 · 307/9/121`) — 계측 커밋은 중립이다. CLAUDE.md §2에 못 박았다.

## 2. 문턱 곡선 (칸 단위, 한 번의 덤프로)

문턱마다 하네스를 다시 돌리는 대신, 스캔 PDF를 제품 설정(1.5배·0.86)으로 쪽 JPEG로 렌더하고(`.tmp/render-scan-pages.cjs`) `MARK_SHAPE_TRACE=1`로
후보 형태를 덤프한 뒤, **하네스가 실제로 자동 채운 칸**과 짝지어 문턱을 훑었다(`scratchpad/veto-sweep.py`). 0.6에서의 예측이 실제 하네스 델타와
칸 수까지 일치해(세트 1 −17 정답·−3 오답) 곡선을 신뢰할 수 있다.

| 표본 | 0.6: 오답↓ / 정답↓ / 비율 | **0.7: 오답↓ / 정답↓ / 비율** | 0.8 |
|---|---|---|---|
| 스캔 세트 1 | 3 / 17 / 6.7:1 | **1 / 7 / 8.0:1** | 0 / 6 (순손실) |
| 스캔 세트 2 | 1 / 17 / 18.0:1 | **1 / 8 / 9.0:1** | 0 / 4 |
| 스캔 세트 3 | 1 / 13 / 14.0:1 | **1 / 5 / 6.0:1** | 0 / 1 |
| **세 세트 합산(§5.4)** | **5 / 47 → 10.4:1 ✗** | **3 / 20 → 7.7:1 ✓** | — |
| 스캔 세트 4 (회색조) | 2 / 23 / 11.5:1 | **2 / 10 / 6.0:1** | 0 / 2 |
| 브라우저 19명 (래스터) | 4 / 14 / 3.5:1 | **3 / 7 / 3.3:1** | 2 / 4 |

`inkBboxFill` 문턱을 0.30으로 올리면 어느 배율에서도 오답이 하나도 안 빠진다(순손실) — 0.22를 유지한다.

**즉 채택 가능한 설정은 `crossing ≥ 0.7 & fill ≥ 0.22` 하나다.** 코드 기본값 0.6은 §5.4 한도를 넘으므로 병합 시 기본값을 0.7로 올려야 한다.
