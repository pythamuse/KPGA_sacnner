# 누적 학생 저장 시 비JSON 응답 분석 및 수정 계획

- 범위: 19명 묶음 처리 중 학생 저장 단계에서 발생한 비JSON 응답 및 저장 중단

## 1. 판정 원칙

이 문서는 화면에 표시된 최종 값 자체로 자동 인식의 성패를 판단하지 않는다. 이전 검수 단계에서 사용자가 다음 학생으로 넘어가기 위해 값을 수기로 수정할 수 있었기 때문이다.

- 자동 인식의 근거는 `자동 인식`, `미확정`, 낮은 신뢰도, 좌표 진단 메시지, 오류 메시지, 저장 결과로 한정한다.
- 수기 수정값은 저장 흐름을 검증하는 입력값일 수는 있지만 OCR 또는 좌표 인식 성공의 증거로 사용하지 않는다.
- 좌표/인식 문제와 저장 전송 실패는 독립된 결함으로 추적한다.

## 2. 관측된 사실

1. 동일한 두 PDF 묶음으로 학생 1명부터 순차 검수를 진행했다.
2. 최근 화면에서 현재 검수 대상은 `7 / 19번째 학생 데이터`이고, 우측 작성 완료 학생 데이터는 6명으로 표시된다. 즉, 기존 6명 저장 후 7번째 학생 저장 시도에서 실패한 상태다.
3. 화면 오류는 다음과 같이 표시된다.

   `학생 저장 처리 중 실패: Unexpected token 'R', "Request En"... is not valid JSON`

4. `src/app/page.tsx`의 저장 요청은 현재 검수 학생만 보내지 않고 `students: [...students, currentDraft]` 형태로 이전 저장 학생과 현재 검수 초안을 함께 `/api/students`에 보낸다.
5. 검수 초안은 원본 미리보기, 항목별 crop, 디버그 crop, 좌표 진단 등의 `data:` URL 기반 이미지를 포함할 수 있다. 이 데이터는 검수 UI에는 필요하지만 영속 저장용 `StudentData` 계약에는 필요하지 않다.
6. `/api/students`는 정상적인 애플리케이션 오류 경로에서 `NextResponse.json(...)`으로 JSON을 반환한다.
7. 클라이언트는 저장 응답에 대해 상태 코드 또는 응답 Content-Type을 확인하기 전에 `await res.json()`을 실행한다.

## 3. 사실에서 도출되는 원인

### 확정된 원인

저장 실패 화면의 직접 원인은 JSON이 아닌 응답 본문을 클라이언트가 JSON으로 파싱한 것이다. 따라서 실제 HTTP 상태 코드와 원본 오류 본문이 사용자에게 숨겨지고, `Unexpected token 'R'`이라는 2차 오류만 노출된다.

### 높은 확률의 근본 원인

저장 요청이 누적될수록 커지는 구조다.

1. 인식 단계가 검수용 이미지 Data URL과 진단 데이터를 포함한 풍부한 초안을 만든다.
2. 첫 저장 이후 응답으로 받은 학생 객체가 `students` 상태에 유지된다.
3. 다음 저장 때 이전 학생 전체와 현재 초안을 다시 전송한다.
4. 이전 객체에 검수용 이미지 또는 진단 데이터가 남아 있으면 요청 본문이 학생 수에 따라 계속 커진다.
5. 7번째 시도처럼 누적 크기가 특정 제한을 넘으면 Vercel 또는 앞단 프록시가 라우트 실행 전 요청을 거부할 수 있다. 이 종류의 응답은 일반 텍스트로 시작할 수 있으며, 화면의 `Request En...` 접두사와 부합한다.

이 가설은 요청 누적 구조와 오류 문구를 함께 설명한다. 다만 실제 상태 코드가 413인지, 어느 계층이 응답했는지는 현재 화면만으로 확정할 수 없다. 다음 배포에서는 안전한 요청/응답 진단으로 이를 확인해야 한다.

## 4. 원인이 아닌 것으로 분리한 항목

| 항목 | 판단 |
| --- | --- |
| 좌표 보정, OCR, 체크마크 인식의 낮은 신뢰도 | 검수 품질 문제지만 비JSON 응답 자체의 직접 원인은 아니다. |
| 일반적인 학생 데이터 검증 실패 | 정상 API 오류라면 JSON 응답이어야 한다. 이번 오류는 JSON 파싱 이전에 발생했다. |
| 엑셀 생성 로직 | 매 저장마다 전체 워크북을 생성하는 것은 성능 부담이 될 수 있으나, `Request En...` 비JSON 응답의 직접 증거는 아니다. |
| 화면에 표시된 연령/성별/학년 값 | 수기 수정일 수 있으므로 자동 인식의 증거로 사용하지 않는다. |

## 5. 수정 계획

### 5.1 저장용 DTO를 검수 UI 데이터와 분리

저장 직전에 명시적 allowlist 변환 함수(예: `toPersistedStudentData`)를 적용한다.

- 서버로 보내는 값은 `StudentData`의 기본정보, CAGI 응답, 만족도 응답, 최소한의 식별자만 포함한다.
- `cagiImageDataUrl`, `satisfactionImageDataUrl`, `cropDataUrls`, `cropDebugDataUrls`, OCR/좌표 진단 문자열, 화면 표시 전용 메타데이터는 절대 저장 요청에 포함하지 않는다.
- 서버도 수신 객체를 그대로 spread하지 않고 allowlist 기반으로 정규화한다.
- 예상하지 않은 `data:` URL 또는 검수 전용 키가 들어오면 JSON 형식의 400 오류로 명확히 거부하거나 제거한다. 권장 기본값은 제거 후 서버 로그에 키 이름과 바이트 수만 남기는 방식이다.

### 5.2 비JSON 응답을 안전하게 처리

클라이언트 저장 응답 파서를 다음 순서로 바꾼다.

1. `res.text()`를 한 번만 읽는다.
2. `Content-Type`이 JSON일 때만 `JSON.parse`한다.
3. 비JSON 또는 실패 상태면 HTTP 상태, Content-Type, 요청 식별자, 제한된 오류 본문 접두사만 사용자 친화적인 오류로 표시한다.
4. 원본 이미지, base64 문자열, 개인식별정보는 화면이나 로그에 출력하지 않는다.

이렇게 하면 프록시/배포 계층의 413, 502, 504 같은 오류가 JSON 파싱 오류로 가려지지 않는다.

### 5.3 누적 저장의 전송량을 일정하게 유지

현재의 무상태 처리 원칙은 유지하되, 전송 대상은 **작고 정규화된 학생 DTO**로 제한한다.

- 매 요청의 학생당 직렬화 크기가 검수 이미지 수와 무관하게 거의 일정해야 한다.
- 19명 저장 과정에서 요청 크기가 이미지 데이터에 비례해 증가하지 않아야 한다.
- 필요하면 워크북 생성은 마지막 다운로드 시점 또는 별도 명시적 생성 단계로 옮겨, 매 저장마다 전체 워크북을 다시 만들지 않는다.

### 5.4 안전한 관측성 추가

배포 후 정확한 실패 계층을 확인하기 위해 다음 정보만 기록한다.

- 요청 바이트 수, 학생 수, DTO 스키마 버전
- 응답 상태 코드, Content-Type, Vercel 요청 ID 등 비식별 상관관계 ID
- 제거된 검수 UI 필드의 키 이름과 개수

기록 금지 항목:

- 원본 이미지, crop Data URL, OCR 원문, 이름, 전화번호, 수기 입력값

## 6. 구현 및 검증 순서

1. 저장 DTO 변환 함수와 서버 정규화를 추가한다.
2. 클라이언트 비JSON 응답 처리를 추가한다.
3. 요청 크기/응답 메타데이터의 비식별 진단을 추가한다.
4. 단위 테스트로 DTO에 `data:` URL, crop, 진단 필드가 포함되지 않는지 검증한다.
5. 모의 일반 텍스트 413 응답에서 명확한 오류 메시지가 나오는지 검증한다.
6. 동일 PDF로 19명 연속 저장을 실행하고 각 저장 요청의 크기가 허용 범위 안에서 일정한지 확인한다.
7. 마지막으로 다운로드된 두 엑셀 파일의 행 수와 매칭을 확인한다.

- 7번째 이후 저장에서도 JSON 파싱 예외가 발생하지 않는다.

- 좌표/OCR 신뢰도 문제는 별도 지표로 계속 검수되며, 저장 전송 문제와 혼동되지 않는다.
