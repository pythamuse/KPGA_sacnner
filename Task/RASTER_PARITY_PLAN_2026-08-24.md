# 래스터 경로 정합 — 계획과 판정 기준

상위 문서: [CLAUDE.md](../CLAUDE.md) §5 · 배경: [FIELD_TEST_2026-08-21.md](FIELD_TEST_2026-08-21.md) §22~24

---

## 1. 왜 이 작업을 하는가

실사용 오답 10건이 두 부류로 정확히 갈렸다([[FIELD_TEST_2026-08-21]] §24).

```
양쪽 다 오답        5건 (p16 문항2~6)      인식 논리 — X 취소
브라우저에서만 오답  5건 (p8×3, p15, p19)   래스터/등록 경로
```

**경로 문제를 먼저 풀어야 하는 이유는 판정 불가 때문이다.** 두 경로가 다르면 인식 알고리즘을 고쳐도 무엇이 효과였는지 가릴 수 없다. 그리고 브라우저 5건은 노드가 이미 정답이거나 거부하고 있으므로, 경로가 맞으면 그대로 사라질 수 있다.

---

## 2. 처음 세운 전제와 그 근거

> **전제 A: 노드가 더 정확하므로 브라우저를 노드에 맞춘다.**

근거는 배치 전체 수치였다.

```
노드      자동 입력 359칸,  오답  7   →  오답률 1.9%
브라우저  자동 입력 302칸,  오답 10   →  오답률 3.3%
```

노드가 **57칸을 더 채우면서 오답은 3건 적다.** 동작점이 두 축 모두에서 낫다.

---

## 3. ★ 전제 A는 틀렸다

두 경로의 차이를 확인하다 원인을 찾았다.

```
노드 계측기   pdfjs-dist  4.10.38   (node_modules, package.json ^4.10.38)
브라우저      pdf.js      6.1.200   (CDN, PDFJS_VERSION)
```

**메이저 두 단계 차이다.** 설정값(scale 1.5 / quality 0.86)은 한 곳에서 공유하지만 **디코더 구현이 다르다.** 원본이 1비트 CCITTFax이므로 디코딩·다운샘플 경로 차이가 그대로 점수에 실린다.

이것이 전제를 두 가지로 무너뜨린다.

1. **노드의 정확도 우위가 버전 산물일 수 있다.** 4.10.38이 이 스캔에서 우연히 더 잘 맞는 것일 뿐, 더 옳은 렌더라는 근거가 없다
2. **방향이 반대다.** 사용자가 받는 것은 브라우저다. **계측기가 프로덕션을 모사해야지, 프로덕션을 계측기에 맞출 수 없다**

그리고 애초에 **브라우저 canvas(Skia)를 node-canvas(Cairo)와 바이트 동일하게 만들 수는 없다.** 전제 A는 실행 가능하지도 않았다.

> **정정된 방향 — 전제 B: 계측기를 브라우저(6.1.200)에 맞춘다.**

## 4. 수정 내용

| # | 대상 | 내용 |
|---|---|---|
| 1 | `package.json` | `pdfjs-dist`를 브라우저와 같은 **6.1.200**로 올린다 |
| 2 | 계측기 렌더 헬퍼 | v6 API 변경에 맞춘다 (`getDocument` 옵션·`CanvasFactory` 계약이 바뀌었을 수 있다) |
| 3 | 없음 | **제품 코드는 건드리지 않는다.** 이번 작업은 계측기 정합이다 |

**`PDFJS_VERSION`을 낮추지 마라.** 프로덕션을 계측기에 맞추는 방향은 금지다.

## 5. 판정 기준 (사전 등록)

수정 전에 예측을 적어둔다. 맞든 틀리든 그대로 기록한다.

### 5.1 예측

계측기가 브라우저와 같은 디코더를 쓰면 **노드 숫자가 브라우저 쪽으로 이동**할 것이다.

```
노드 현재   자동 입력 359,  오답 7,   CORRECT 354/432
예측        자동 입력이 302 쪽으로 내려가고, 오답이 10 쪽으로 올라간다
```

**즉 이 작업은 노드 숫자를 나쁘게 만들 것으로 예상한다.** 그것이 정직한 방향이다 — 지금 노드는 실사용보다 낙관적이다.

### 5.2 성공 조건

| 조건 | 판정 |
|---|---|
| 노드 오답 목록이 **브라우저 오답 목록에 가까워진다** | ✅ 성공 — 계측기가 실사용을 모사하게 됨 |
| 특히 **p8·p15·p19가 노드에서도 오답으로 나타난다** | ✅ 강한 성공 — 경로 차이가 원인이었음이 확정 |
| p7·p14가 노드 오답 목록에서 **사라진다** | ✅ 성공 — 그 둘은 v4 산물이었음 |
| 두 목록이 여전히 크게 다르다 | ❌ **버전이 원인이 아니다.** canvas/JPEG 구현 차이가 주범이고 정합은 불가능하다 → §7로 |

### 5.3 절대 조건

- **제품 코드 무변경.** `src/lib/recognition/**`, `src/components/**`, `PDFJS_VERSION` 모두 그대로
- `npx vitest run` 전부 통과
- `npm run build` 통과
- **브라우저 19명 재측정에서 오답이 10건을 넘지 않을 것** — 제품을 안 건드렸으므로 변하면 안 된다. 변하면 무언가 잘못 건드린 것이다

### 5.4 판정 절차

1. 수정 전 노드 19페이지 측정값을 기록 (현재: `CORRECT 354/432 · WRONG 7`)
2. 수정 후 같은 측정
3. 두 오답 목록을 브라우저 오답 10건과 대조
4. 브라우저 19명 재측정으로 제품 무변경 확인

## 6. 이 작업이 바꾸지 않는 것

**p16 다섯 건(X 취소)은 경로와 무관하게 양쪽에서 틀린다.** 이 작업으로 사라지지 않는다. 별도 과제다([[FIELD_TEST_2026-08-21]] §21).

그리고 §24.2의 경고가 유효하다 — **경로를 맞추면 노드에만 있던 오답이 실사용에 나타날 수 있다.** 지금은 노드가 낙관적이라 그 방향이지만, 반대 경우도 가능하다.

---

## 7. 전제 B도 틀렸을 경우

§5.2의 마지막 줄에 해당하면, 버전이 아니라 **canvas·JPEG 인코더 구현**이 주범이다. 그러면 정합은 불가능하고 방향을 바꿔야 한다.

**대안: 정합 대신 둔감화.** 문제의 본질은 "두 경로가 다르다"가 아니라 **"작은 래스터 차이로 승자가 뒤집힌다"** 이다. p8 만족도는 두 칸 차이가 1%p였다. 그 정도로 뒤집히는 파이프라인은 어느 경로에서도 불안정하다.

그 경우 표적은 **약한 신호에서의 안정성**이 되고, 판정 기준도 "두 경로 일치"가 아니라 "**래스터를 흔들어도 결과가 안 바뀌는 칸의 비율**"이 된다.

---

## 8. 부수적으로 기록해둘 것

브라우저가 pdf.js를 **CDN에서 로드**한다(`cdnjs` + `unpkg`). 즉 프로덕션 인식이 외부 호스트 가용성에 의존한다. 이번 작업 범위는 아니지만 기관 배포 시 검토 대상이다.

---

## 9. 결과 — **전제 B도 틀렸다** (2026-08-24)

`pdfjs-dist` 를 **4.10.38 → 6.1.200** 으로 올려 브라우저와 같은 디코더로 맞췄다.
(워크트리에 실제 6.1.200 설치, main 은 4.10.38 유지 → 비교 유효)

```
                  4.10.38                 6.1.200
CORRECT           354/432                 354/432
WRONG             7                       7
오답 목록          p7·p14·p16×5            p7·p14·p16×5   ← 완전히 동일
```

**한 칸도 달라지지 않았다.** §5.2의 마지막 줄에 해당한다.

> 두 목록이 여전히 크게 다르다 → ❌ **버전이 원인이 아니다.**

### 9.1 그러므로 정합은 도달 불가능하다

디코더를 같게 만들어도 노드와 브라우저는 여전히 다른 칸에서 틀린다. 남는 차이는

```
node-canvas (Cairo)  대  브라우저 canvas (Skia)     래스터라이저
libjpeg              대  Chrome JPEG 인코더         같은 quality 값에 다른 양자화
```

이고, **이 둘은 맞출 수 없다.** 브라우저 canvas를 node-canvas와 바이트 동일하게 만드는 방법은 없다.

### 9.2 표적을 §7의 대안으로 옮긴다

문제의 본질이 "두 경로가 다르다"가 아니라 **"작은 래스터 차이로 승자가 뒤집힌다"** 임이 확정됐다.

증거는 이미 있다 — 학생 8 만족도에서 두 칸 차이가 **1%p**였고, 그 정도로 뒤집혔다
([[FIELD_TEST_2026-08-21]] §23.3). 그렇게 뒤집히는 파이프라인은 **어느 경로에서도 불안정하다.**

**새 표적: 약한 신호에서의 안정성.**
**새 지표: 래스터를 흔들었을 때 결과가 바뀌지 않는 칸의 비율.**

### 9.3 이 라운드에서 남길 것

`pdfjs-dist` 6.1.200 업그레이드 자체는 **버리지 않는다.** 이유는 정합이 아니라 다른 데 있다.

- 계측기가 프로덕션과 **같은 메이저 버전**의 디코더를 쓰는 것이 옳다. 지금은 두 단계 뒤처져 있다
- 측정값이 바뀌지 않으므로 **위험이 없다** (`CORRECT 354 · WRONG 7` 동일, 테스트 119 통과, 빌드 통과)
- 다만 **이득도 없다.** 병합 판단은 §10에서

### 9.4 사전 등록이 한 일

이 라운드는 **예측이 틀렸음을 그대로 기록**하기 위해 존재한다. §5.1에서 "노드 숫자가 나빠질 것"이라고 적었는데 **아무것도 바뀌지 않았다.** 예측이 틀렸고, 그 덕에 §7의 대안으로 넘어갈 근거가 생겼다.

만약 판정 기준을 미리 적지 않았다면 "동일하니 성공"으로 읽고 정합 작업을 계속했을 것이다.
