# 무상태 인식 구조 계획 — Blob 없이, 요청에 이미지를 실어 보낸다 (2026-09-03, 브랜치 `stateless-recognize`)

사용자 결정(2026-09-03): **현 구조(Vercel Blob 업로드 → `/api/recognize`가 Blob에서 읽음)는 그대로 두고**, Blob을 쓰지 않는
무상태 구조는 이 브랜치에서 계획·실험한다. 동기는 Vercel **Advanced Blob 연산 급증**(배치당 `put` 38 + `list` + `del`
≈ 40~80회)과 "불필요한 연산을 서버 부하로 만들지 않는다"는 장기 원칙이다. 이 문서는 페이블 5.1이 직접 썼고, 구현은
CLAUDE.md §0의 상한(코드 = 코덱스, 조사 = 오퍼스)대로 위임한다.

## 1. 지금 구조가 Blob을 쓰는 이유와 비용

| 단계 | 지금 | Blob 연산 |
|---|---|---|
| 업로드 | 브라우저가 PDF를 쪽 단위 JPEG로 굽고 `/api/upload`에 쪽마다 POST → `uploadStore.put` (`src/lib/storage/uploadStore.ts:135,191`) | **put × 38** |
| 인식 | `/api/recognize`가 `materializeUploadBatch`(`route.ts:366`)로 Blob에서 38장을 읽어 스크래치에 쓴 뒤 19명을 한 요청에서 인식 | get × 38 (simple) |
| 정리 | 인식 직후 `deleteUploadBatches` → `deleteBlobPrefix`: `list`(prefix) + `del`(경로들) (`uploadStore.ts:349-357`); 화면 초기화·작업 정리도 같은 경로 | **list ≥1, del ≥1** |

Blob은 **인식 요청과 업로드 요청이 다른 서버리스 인스턴스에 떨어져도 파일을 찾기 위한 임시 저장소**일 뿐이다
(Task/STATELESS_ARCHITECTURE_MIGRATION.md 사이클 6). 파일이 살아 있는 시간은 업로드 직후부터 인식 완료까지 몇 분이다.
즉 **저장소가 필요한 것이 아니라 전달 통로가 필요한 것**이며, 그 전달은 요청 본문으로 대신할 수 있다.

## 2. 목표 구조

```
브라우저                                     서버(/api/recognize/student)
PDF → 쪽 JPEG(사다리 1.5/1.25/1.0)   ──┐
                                        ├── multipart: cagi.jpg + sat.jpg + meta ──▶ 인식 1명 ──▶ 초안 JSON(값·출처·근거·크롭)
학생 i의 두 장만 골라 전송            ──┘                                              (Blob 접근 0, 디스크 잔류 0)
19명 = 요청 19개(동시 2~3개)
```

- **요청 단위 = 학생 1명**(선별검사지 1장 + 만족도 1장). 본문 ≈ 292KB × 2 ≈ 0.6MB — Vercel 서버리스 요청 본문 상한(4.5MB) 안.
  배치 전체(≈11MB)를 한 요청에 실을 수 없으므로 학생 단위가 자연스럽다.
- 서버는 본문의 두 이미지를 그 요청의 스크래치 디렉터리에만 쓰고(`os.tmpdir()`, 요청 종료 시 삭제) 지금의
  `recognizeStudentForms(cagiPath, satPath, options)`를 **그대로** 호출한다. 인식 코드는 한 줄도 바뀌지 않는다.
- 응답은 지금 `/api/recognize`가 학생마다 만드는 것과 같은 객체(값·출처·근거·크롭 data URL·등록 메타). 클라이언트는
  19개 응답을 지금과 같은 `drafts[]`로 모은다. 검수·저장·엑셀 경로는 무변경(`/api/students`는 이미 무상태).
- Blob 호출 0. `@vercel/blob` 의존성은 이 경로에서 사라진다(다른 곳에서 안 쓰면 제거).

## 4. 실험 순서 (이 브랜치)

1. **계측 먼저**: 지금 구조의 배치당 Blob 연산 수를 로컬에서 세는 카운터(`uploadStore`의 put/list/del 호출 로그, env 뒤)
   → 문서의 "40~80회" 추정을 실측으로 바꾼다.
2. 코덱스 라운드 A — `/api/recognize/student` 신설 + 노드 시험(multipart로 두 장을 보내 응답이 기존 배치 응답의 해당 학생
   항목과 **바이트 동일**한지). 기존 경로 무변경.
3. 코덱스 라운드 B — 클라이언트 전환(플래그 `NEXT_PUBLIC_STATELESS_RECOGNIZE=1`일 때만). 플래그 off = 지금 그대로.
4. 위임자 판정 — 로컬 dev + `next start`에서 세트 1: 브라우저 값 대조가 현재 기준선(자동 339·오답 9, FIELD_TEST §34.1)과
   **동일**해야 한다. 그리고 Vercel 프리뷰 배포에서 배치 1회 → Blob 연산 0, 함수 실행 시간·메모리 기록.
5. 통과하면 플래그 기본 ON → 레거시 경로 삭제 라운드.

## 5. 위험과 대응

1. **OCR 워커 콜드스타트 반복** — 학생 단위 요청이 서로 다른 인스턴스에 떨어지면 tesseract 초기화(수 초)가 반복된다.
   대응: 동시성 2~3으로 제한해 인스턴스 재사용을 유도하고, 첫 요청에만 6초 예산을 주고 나머지는 1초로 유지(클라이언트가
   순번을 보내면 지금 `ocrBudget`의 규칙을 그대로 쓸 수 있다). 실측으로 판단.
2. **함수 시간 상한** — 지금은 19명이 한 요청(최대 24초, `maxDuration` 미선언)이라 상한에 더 가깝다. 학생 단위는 요청당
   1~6초라 오히려 안전하다. `maxDuration = 30` 명시.
3. **재시도·부분 실패** — 학생 하나가 실패해도 나머지 18명은 완료된다. 실패 학생만 재전송(같은 이미지가 메모리에 있음).
4. **클라이언트 메모리** — 38장 JPEG ≈ 11MB를 탭 메모리에 유지. 이미 IndexedDB 캐시가 같은 양을 갖고 있으므로 추가 부담은
   작다. 모바일 촬영 경로(개별 업로드)는 애초에 학생 단위라 영향 없음.
5. **개인정보** — 이미지가 서버 디스크·Blob에 남지 않는다(요청 스크래치는 응답 후 삭제). PRD §10·C5와 방향이 같다.
6. **동시 사용자** — 19개 병렬 요청 × 사용자 수만큼 함수 호출이 늘지만, 지금도 업로드 38회 + 인식 1회 = 39회라 총 호출 수는
   **줄어든다**(19 + 0).

## 6. 하지 않는 것

- 인식을 브라우저로 옮기는 것(Docs/17 §3.2) — 정확도 근거가 없고 재보정이 선행돼야 한다. 이 계획은 **전달 통로만** 바꾼다.
- Blob에 zip으로 묶어 올리는 절충(연산 20배 감소) — 무상태가 목표면 중간 단계가 필요 없다. 실험이 실패하면 그때 절충안으로.

- 브라우저: 세트 1 자동 339 · 오답 9 · 빈칸이어야 하는 5칸 유지.
- Vercel 프리뷰: 배치 1회에 Blob advanced 연산 **0**, 함수 오류 0, 학생당 실행 시간 기록.
