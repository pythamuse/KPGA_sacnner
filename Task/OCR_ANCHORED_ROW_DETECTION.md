# OCR 텍스트 앵커 기반 문항 행(row) 위치 보정

## 배경

[[RECOGNITION_ACCURACY_DYNAMIC_ROW_DETECTION]]에서 도입한 동적 표 행 검출(어두운 가로줄 패턴 매칭)을 배포한 뒤에도, 실제 사용자의 검수 화면 스크린샷에서 CAGI 01~03/05/06이 근접-무작위에 가까운 후보 점수(예: 0/21%, 1/21%, 2/0%)로 낮은 신뢰도로 나오고, **학년(basic.grade) 필드는 크롭 미리보기가 CAGI 안내문구("본인 자신이 이런 경험들을...")를 그대로 보여줄 만큼 완전히 엉뚱한 영역을 읽고 있음**이 확인됐다.

이 세션에서 조사한 결과 두 가지가 새로 드러났다:
1. 기존 `tableRowDetection.ts`는 `cagiQuestionYs`/`cagiLateQuestionYs`(CAGI 1~9 문항 표)와 `satisfactionBinaryYs`/`satisfactionScaleYs`(만족도 문항 표)만 다룬다. `roiTemplates.ts`의 `schoolTypeCandidates`/`gradeCandidates`(학교유형·학년 체크박스 클러스터)는 애초에 이 동적 검출의 대상이 아니었다 — 즉 이 영역은 지금까지 어떤 동적 보정 안전망도 없이 순수 고정 좌표로만 동작해왔고, 스크린샷에서 가장 심하게 깨진 것도 이 영역이다.
2. 사용자가 신분증/신용카드 인식 방식(카드 모서리 전체를 못 찾아도, 글자 자체를 앵커로 삼아 위치를 특정하는 방식)을 참고 아이디어로 제안했다 — [문제 설명과 1차 검토는 이 대화의 앞선 응답 참고].

## 사이클 1 — 설계, 범위 결정, 작업지시서

### 작업 내용

**범위 결정 (사용자 지시)**: OCR 엔진은 **영역(행) 위치를 찾는 용도로만** 쓴다. 체크박스에 실제로 마킹됐는지 판정하는 것은 지금처럼 픽셀 스캔(`calculateDarkPixelDensity`)으로 그대로 구현한다 — OCR이 마킹 인식 자체를 대체하지 않는다.

**왜 마킹 인식에는 OCR/ML을 도입하지 않는가**:

1. 체크박스 마킹(체크, 동그라미 등)은 활자·필기 "문자"가 아니라 사용자가 임의로 그은 표시다. 표준 OCR 문자 인식 모델이 다루는 대상과 범주가 다르고, 이런 마크를 문자로 인식시키려 하면 오히려 무작위 오인식을 유발할 수 있다.
2. 마킹 유무를 제대로 분류하려면 이 양식에 특화된 마킹 스타일(체크, 동그라미, 학생마다 다른 필압/모양)로 라벨링된 학습 데이터가 필요한데, 전혀 없다 — 처음부터 데이터 수집·라벨링이 필요해 작업 범위가 크게 벌어진다.
3. 반대로 지금의 픽셀 밀도 방식은 **앵커(영역)만 정확하면 실제로 잘 동작한다는 증거가 있다** — 스크린샷에서 CAGI04(우연히 앵커가 맞은 문항)는 "높음" 신뢰도로 정확히 인식됐다. 즉 근본 문제는 "마크를 못 읽는 것"이 아니라 "엉뚱한 곳을 보고 있는 것"이므로, 마킹 인식 자체를 바꾸는 것보다 위치 파악만 고치는 것이 문제에 더 정확히 대응하는 최소 변경이다.
4. 스코프를 좁게 유지하는 것이 이번 세션 내내 반복해온 안전 원칙과 일치한다. 새 ML 분류기는 실패 모드가 훨씬 다양하고 예측하기 어렵다(단순 켜짐/꺼짐이 아니라 확률적 오분류). 지금까지 두 번의 심각한 사고([[MOBILE_CAPTURE_PERSPECTIVE_CORRECTION]])가 전부 "새 기능이 충분히 방어적이지 않아서" 발생했다는 점을 감안하면, 이번에도 스코프를 최소로 유지하는 쪽이 안전하다.

**도입했을 때 얻을 수 있는 이점** (참고용, 이번에는 착수하지 않음):
- 애매한 마크(반쯤 지운 표시, 겹쳐 그은 표시, 동그라미 vs 체크 등)를 픽셀 밀도보다 정교하게 구분할 가능성.
- 단순 어두운 픽셀 비율이 아니라 마크의 "형태"를 보고 판정하므로, 인쇄된 원문자 자체가 어두워서 생기는 오탐을 줄일 가능성.
- 후보값별로 더 의미 있는 확률/신뢰도 산출 가능(현재는 최고점-차점 점수차 휴리스틱에 의존).

**예상 문제** (참고용):
- 이 양식의 실제 마킹 스타일을 반영한 라벨링된 학습 데이터가 없어 처음부터 수집·라벨링이 필요하다.
- 외부 비전 API를 쓰면 [[RECOGNITION_ACCURACY_DYNAMIC_ROW_DETECTION]] 사이클 1에서 이미 보류한 개인정보 정책 문제가 재부상한다.
- 자체 모델을 학습·구동하려면 이 프로젝트 규모(강사 1명, 학생 수십 명)에 비해 과한 ML 인프라/유지보수 부담이 생긴다.
- 처리 시간·비용이 늘고, 지금의 "픽셀 비율 몇 %"보다 분류기 confidence는 사람이 바로 이해·디버깅하기 어렵다.

**Plan B (이번 방식이 실제로 잘 통하지 않을 경우)**:
1. 1차 완화: 앵커로 쓰는 문자열 범위를 넓히거나(원문자 대신 인접 한글 텍스트도 시도), OCR 엔진/설정을 교체해 재시도.
2. 2차: 마킹 인식 자체에도 제한적으로 ML을 도입 — 단, 반드시 자체 학습 모델(외부로 이미지 전송 없이)만 검토하고, 학습 데이터 확보 방안을 먼저 정한다.
3. 이전에 검토했던 비전 API 하이브리드([[RECOGNITION_ACCURACY_DYNAMIC_ROW_DETECTION]] 사이클 1의 C안, 저신뢰 항목만 보조)도 재검토 대상이 될 수 있으나, 정책 결정이 필요해 사용자/기관 확인 없이는 착수하지 않는다.

### 기술 설계

**OCR 엔진**: `tesseract.js`(`package.json`에 `^5.1.0`으로 이미 있으나, 지금까지 실제로 한 번도 로드/실행된 적이 없다 — `detectCheckmarks.ts` 주석에 "Tesseract.js 로드 없이 파일명 기반 매핑만 수행"이라고 명시되어 있다. 즉 이번이 첫 실사용이라 **이 환경(로컬 Node, Vercel 서버리스)에서 실제로 동작하는지 자체가 검증되지 않은 상태**다).

**반드시 서버 사이드(Node)에서만 실행한다. 브라우저/WASM-in-browser 경로는 만들지 않는다** — 이번 세션에 클라이언트 WASM(OpenCV.js) 때문에 웹페이지 전체 프리징 사고가 두 번 발생했다([[MOBILE_CAPTURE_PERSPECTIVE_CORRECTION]] 사이클 5). tesseract.js도 WASM 기반이라 같은 클래스의 위험이 있으므로, 반드시 `/api/recognize` 처리 중 서버에서만 호출한다.

**범위(이번 사이클)**: CAGI/만족도 문항 표의 행 검출(`tableRowDetection.ts`)에 OCR 기반 텍스트 라인 검출을 **추가 입력**으로 얹는다. 기존 `detectHorizontalLines`(어두운 픽셀 가로줄 스캔)를 대체하지 않고, 더 신뢰도 높은 우선 후보로 얹는다:

1. OCR로 검색 영역 내 텍스트 단어/줄의 바운딩 박스를 얻는다 (글자를 **정확히 읽을 필요는 없다** — 원문자 "①②③④"처럼 표준 OCR 학습 데이터에 없는 글리프라도, 텍스트 형태의 획 구조가 있으면 위치(바운딩 박스)는 감지될 가능성이 높다. 이번 기능은 인식된 문자열의 정확성에 의존하지 않고 **위치만** 사용한다).
2. 그 Y좌표들을 기존 `matchRowPattern`(이미 테스트된 간격-패턴 매칭 로직)에 그대로 통과시킨다 — 새 매칭 로직을 만들지 않는다.
3. OCR 라인으로 확신 있는 매칭을 못 찾으면 기존 `detectHorizontalLines` 결과로 재시도한다(오늘의 동작 그대로).
4. 그것도 확신이 없으면 빈 객체 `{}`를 반환해 기존 동작으로 폴백한다(기존 하드 요구사항 유지).
5. OCR 호출 자체가 실패(엔진 로드 실패, 타임아웃 등)해도 절대 예외를 던지지 않고, 빈 배열로 취급해 3번 경로로 자연스럽게 넘어간다.

**이번 사이클에서 다루지 않는 것 (명시적 범위 제외)**: `schoolTypeCandidates`/`gradeCandidates`(학교유형·학년) 클러스터는 스크린샷에서 가장 심하게 깨진 부분이지만, `tableRowDetection.ts`의 "문항 표 행" 매칭 방식과 구조가 달라(표가 아니라 2차원 체크박스 격자) 같은 방식을 바로 적용할 수 없다. OCR 프리미티브(tesseract.js가 이 환경에서 실제로 동작하는지) 자체를 먼저 검증하지 않은 채 더 복잡한 2차원 앵커 보정까지 함께 설계하는 것은 무리라고 판단해, **이번 사이클은 이미 검증된 `matchRowPattern` 인프라를 재사용할 수 있는 문항 표 케이스로 한정**한다. 학교유형/학년 보정은 이 사이클의 OCR 프리미티브가 실제로 유효하다고 확인되면 다음 사이클에서 별도로 설계한다.

**작업지시서 (Codex에 위임)**:

1. `src/lib/recognition/ocrTextLines.ts`(신규):
   ```ts
   export interface OcrTextLine { y: number; confidence: number; }
   export async function detectOcrTextLines(
     imageBuffer: Buffer, imageWidth: number, imageHeight: number,
     searchTop: number, searchBottom: number, xLeft: number, xRight: number,
   ): Promise<OcrTextLine[]>
   ```
   - `sharp`로 `(xLeft, searchTop)`~`(xRight, searchBottom)` 영역만 크롭한 버퍼를 만들어 그 크롭에만 tesseract.js `recognize()`를 실행한다(전체 페이지 OCR은 느리고 불필요).
   - Tesseract 결과의 단어/줄 바운딩 박스를 순회해, confidence가 지나치게 낮은(예: 30 미만) 항목과 폭이 지나치게 좁은(노이즈로 추정) 항목은 제외한다.
   - 남은 박스들의 Y 중심을 크롭 좌표계에서 원본 이미지 좌표계로 되돌리고(`+= searchTop`), Y가 가까운 것끼리(같은 줄) 묶어 하나의 `OcrTextLine`으로 합친다 — `detectHorizontalLines`의 인접 그룹핑 방식을 참고한다.
   - `tesseract.js` 로드나 인식 중 어떤 예외가 나든 catch해서 빈 배열을 반환한다. 절대 위로 던지지 않는다.
   - 언어팩은 한국어(`kor`)를 사용한다. 워커/언어팩 로딩은 모듈 내부에서 지연 초기화 + 캐싱한다(반복 호출마다 새로 초기화하지 않는다).

2. `src/lib/recognition/tableRowDetection.ts` 수정:
   - `findRowMatch`를 확장해 OCR 결과를 우선 시도하고, 실패하면 기존 픽셀 라인 검출로 폴백하도록 한다(위 "기술 설계" 1~4번 순서 그대로).
   - `buildCagiRowOverrides`/`buildSatisfactionRowOverrides`가 비동기(`Promise`)가 되는 것은 불가피하다 — 호출부(`detectCheckmarks.ts`)는 이미 `async` 함수이므로 `await`만 추가하면 된다.
   - 기존 동기 버전 동작(순수 픽셀 라인)은 그대로 남겨두고, OCR을 오직 "먼저 시도하는 추가 후보"로만 앞에 끼워 넣는다 — 기존 테스트가 그대로 통과해야 한다.

3. `src/lib/recognition/detectCheckmarks.ts`: `buildCagiRowOverrides`/`buildSatisfactionRowOverrides` 호출부에 `await` 추가, CAGI/만족도 이미지 버퍼를 `detectOcrTextLines`에 넘기도록 배선.

4. 테스트: `tests/ocr-text-lines.test.ts`(신규) — 기존 `tests/table-row-detection.test.ts`의 SVG 합성 이미지 패턴을 따르되, `<line>` 대신 실제 한글 텍스트를 `<text>` 요소로 렌더링한 이미지로 `detectOcrTextLines`가 대략적인 Y 위치를 감지하는지 확인한다. Tesseract 인식 자체가 이 테스트 환경(Vitest, 로컬 Node)에서 정상 동작하지 않을 가능성도 있으므로, **이 테스트가 실패하거나 타임아웃되면 즉시 보고할 것** — 이번 사이클의 가장 큰 미검증 리스크(이 환경에서 tesseract.js가 실제로 동작하는가)를 가장 먼저 확인하는 것이 목적이다.
5. 기존 전체 테스트(`tests/table-row-detection.test.ts` 포함 11개 파일)가 회귀 없이 그대로 통과해야 한다.
6. `npm run build`가 통과해야 한다(특히 tesseract.js가 Next.js 서버 번들에 포함될 때 빌드가 깨지지 않는지 확인 — 문제가 있으면 `next.config.js`의 `serverExternalPackages` 등으로 조정 필요할 수 있다는 점을 인지하고 진행할 것).

이 작업이 끝나면 (a) 파일별 변경 내용, (b) 전체 테스트/빌드 결과, (c) 특히 `ocr-text-lines.test.ts`가 실제로 무엇을 감지했는지(빈 배열이었는지, 실제 위치를 잡았는지)를 상세히 보고할 것 — 이 사이클의 목적 자체가 "이 환경에서 OCR 기반 앵커링이 조금이라도 신호를 주는지" 확인하는 것이므로, 테스트가 통과했다는 사실보다 **무엇이 감지됐는지 내용**이 중요하다.
