## 사이클 1 — 만족도 콘텐츠 상자가 페이지마다 다르다

### 1.1 계측

19페이지 × 2폼의 페이지 기하와 표별 등록 상태를 노드에서 뽑고, 브라우저 결과와 대조했다.

먼저 상위 가설부터 정리했다 ([[FIELD_TEST_2026-08-21]] §18): 페이지 위치는 `r=-0.550`으로 주범이 아니고, **좌표 붕괴(+0.590)와 2순위 상승(+0.614)** 이 더 잘 설명한다. 둘은 서로 `+0.631`로 붙어 있어 **표 등록 정확도** 하나의 두 얼굴로 보인다.

그 다음 페이지 기하를 봤다. 콘텐츠 상자 폭·좌변·높이·기울기는 브라우저 실패와 **상관이 약하다**(|r| ≤ 0.47). 그런데 표를 하나로 좁히자 완전히 갈렸다.

```
satisfaction.scale   verified   콘텐츠 폭  732 733 733 736 736 736 736 737 761  (11페이지)
                     candidate  콘텐츠 폭  778 790 790 797 804 807 808 812      (8페이지)
                                            ↑ 761과 778 사이에 빈 구간
```

**연속적 흔들림이 아니라 이봉분포다.**

### 1.2 빈 양식이 어느 쪽이 맞는지 결정한다

```
satisfaction-blank.png   1654x2337,  콘텐츠 폭 1358  →  893px 환산 733.1
```

**정상군 732~737이 기준과 일치하고, 이상군 778~812가 최대 11% 넓다.** 넓은 쪽은 상자가 페이지 전폭에 가깝게 벌어진다(예: p13 L=59 W=812 → 59~871 / 893). 스캔 가장자리 잡음을 물고 있다는 뜻이다.

콘텐츠 상자는 **정규화 좌표계의 분모**다. 11% 넓어지면 모든 ROI가 그만큼 밀리고, 그래서 표 등록이 검증을 통과하지 못한다.

### 1.3 원인 추정

`loadImageAnalysisData` → `detectPaperContentBounds(image, pageBounds)`가 19페이지 중 8페이지에서 **인쇄 영역이 아니라 스캔 가장자리까지** 포함한다. 19페이지 전부 `src=paper`이므로 프레임/다크 폴백이 아니라 이 함수 자체다.

CAGI 쪽은 폭으로 갈리지 않는다(겹침) — 사이클 1의 범위는 만족도로 한정한다.

### 1.4 계획

- Codex에 위임: `detectPaperContentBounds`가 페이지마다 일관된 인쇄 영역을 내도록 한다
- **빈 양식이 같은 함수를 통과한다.** `cagi-blank` 1465, `satisfaction-blank` 1358이 흔들리면 템플릿 좌표계 전체가 어긋난다 — 불변이어야 한다
- 임계값을 템플릿 폭에 맞춰 깎는 것은 금지. 원인(가장자리 잡음 포함)을 제거해야 한다

### 1.5 위임 결과 (Codex, 5분)

원인: `detectDarkPixelBounds`가 **인쇄선의 반복성을 보지 않고 어두운 픽셀 하나까지 외곽점으로 채택**했다. JPEG 스캔의 급지 그림자·가장자리 잡음이 좌우 경계를 벌렸다.

수정: 가로 외곽을 **시트 높이의 0.5% 이상 반복되는 어두운 열**에서만 잡는다. 이 경로는 **중간 명암값이 있는(=압축된) 이미지에만** 적용하고, 1비트 자산은 기존 경로를 유지한다. 템플릿 폭·페이지 번호·사후 클램프 없음.

### 1.6 측정 (내가 직접, 위임 대상의 자체 보고는 채택하지 않음)

| 항목 | 이전 | 이후 | 판정 |
|---|---|---|---|
| 만족도 콘텐츠 폭 | 732~812 (이봉) | **732~738** | ✅ |
| `satisfaction.scale` verified | 11/19 | **19/19** | ✅ |
| `satisfaction.binary` verified | 17/19 | 18/19 | ✅ |
| `satisfaction.frequency` verified | 17/19 | 18/19 | ✅ |
| 빈 양식 기준값 | 1465 / 1358 | **1465 / 1358** | ✅ 불변 |
| 노드 계측기 | 108/135 · WRONG 0 | **108/135 · WRONG 0** | ✅ 회귀 없음 |
| 단위 테스트 | 113 | 113 | ✅ |

노드 계측기가 중립인 것은 예상된 결과다 — 6페이지만 재는데 그중 폭이 틀렸던 것은 6페이지 하나뿐이다. **이 변경의 판정자는 브라우저 19명이다.**

### 1.7 ★ 판정이 막혔다 — 그리고 그게 다음 작업이 됐다

규칙 2대로 브랜치를 밀어 프리뷰 배포를 받았다. 배포는 성공했으나 **URL이 Vercel SSO로 보호돼 있다.** 로그인은 할 수 없다(자격증명 입력 금지).

프로덕션에 올려 재면 되지만 그건 규칙 2를 버리는 것이다. 그래서 **배포 자체를 없애는 쪽**을 봤다.

`uploadStore.ts`의 `usesLocalMemoryStore()`는 `!process.env.VERCEL`이므로 **로컬에서는 이미 메모리 스토어를 쓰게 되어 있다.** 그런데 로컬 dev에서 `/api/recognize`가 `409 UPLOAD_INTEGRITY_ERROR`를 낸다 — 업로드는 200인데 읽기가 빈다.

의심: `LOCAL_MEMORY_UPLOADS`가 모듈 수준 `Map`이라 **Next.js dev에서 두 라우트가 인스턴스를 공유하지 못한다.**

이것이 풀리면 **배포 없이 매 사이클을 로컬에서 측정**할 수 있다. 사이클 1b로 위임했다.

### 1.8 사이클 1이 CAGI를 조금 나쁘게 했고, 그것이 더 큰 것을 드러냈다

콘텐츠 폭 수정은 CAGI 페이지에도 적용된다(이미지 톤으로 분기하므로). CAGI 폭도 734~737로 수렴했다. 그런데 **CAGI 표 등록은 두 페이지 나빠졌다.**

```
cagi.primary  candidate   7페이지 {3,5,8,9,10,16,19}  →  9페이지 {+11,12}
cagi.basic    failed      4페이지 {5,7,9,14}          →  6페이지 {+18,19}
satisfaction.scale verified  11/19  →  19/19
```

11·12번은 이전에 폭이 776~796으로 **넓었을 때 verified**였다. 좁혀지자 candidate가 됐다.

**왜 넓은 쪽이 CAGI에서 더 나았는가**를 보니 근본 문제가 나왔다.

```
만족도  빈 양식 733  ↔  스캔 733     일치
CAGI    빈 양식 791  ↔  스캔 736     7% 불일치
```

두 빈 양식은 8% 차이나는데 두 스캔군은 3px 차이다. 만족도가 정확히 맞으므로 **CAGI 빈 양식이 이상치**다.

### 1.9 ★ 같은 래스터에서 직접 비교

빈 양식과 같은 1654px 폭으로 스캔을 렌더해 인쇄 외곽을 나란히 놨다.

```
CAGI  빈 양식   L=154  R=1619   W=1465
CAGI  스캔 p1   L=152  R=1513   W=1361      왼쪽은 맞고 오른쪽이 106px 짧다
CAGI  스캔 p7   L=152  R=1511   W=1359

만족도 빈 양식  L=155  R=1513   W=1358
만족도 스캔 p1  L=155  R=1510   W=1355      일치
```

**왼쪽 경계는 셋 다 152~155로 같다. 오른쪽만 CAGI 빈 양식이 1619로 혼자 튄다** — 나머지는 전부 1510~1513이다.

CAGI 빈 양식의 인쇄 외곽이 실제 CAGI 스캔보다 **오른쪽으로 106px(6.4%) 넓다.** 콘텐츠 상자는 모든 ROI의 분모이므로, CAGI의 모든 템플릿 사각형이 그만큼 가로로 늘어난 좌표계에서 나온다.

**이것이 [[SCAN_DISTORTION_2026-08-20]] §10.2에서 잰 `scaleX = -12~-14%`(선택지 중심의 가로 축척 오차)의 근원으로 보인다.** 그때는 게이트에 축척 항이 없다는 것까지만 갔고 왜 축척이 어긋나는지는 몰랐다. 후보 구간이 페이지 폭의 일부이므로 6.4%의 외곽 오차가 더 큰 상대 오차로 나타나는 것은 자연스럽다.

**사이클 2 대상이다.** 먼저 그 106px 띠에 무엇이 있는지 확인해야 한다 — 빈 양식이 뭔가를 더 가지고 있는지, 스캔이 오른쪽을 잘라먹는지.

## 사이클 1 판정 — **기각 보류**

로컬 브라우저로 19명을 재측정했다.

```
사이클 1 적용:  6 12 11 8 10 7 5 4 11 8 11 6 5 11 7 5 3 2 3  = 135
기준선:         6 12 11 8 10 7 5 4 11 8 11 6 5 11 7 5 3 2 3  = 135
```

**한 칸도 달라지지 않았다.** 노드에서 `satisfaction.scale`을 11/19 → 19/19로 올렸는데 브라우저는 무변동이다.

이유는 이미 관측돼 있었다 — [[FIELD_TEST_2026-08-21]] §18의 브라우저 스크레이프에서 p16·p17·p19의 만족도 5점 표는 **브라우저에서 이미 `격자 검증 완료`**였다. 노드가 뒤처져 있었을 뿐이다. **사이클 1은 노드에만 있던 결함을 고쳤다.**

게다가 노드 CAGI 등록은 두 페이지 나빠졌다(§1.8).

**규칙상 이득 없는 변경은 병합하지 않는다.** 다만 §1.9에서 드러난 CAGI 빈 양식 문제와 같은 좌표계 사안이므로 **사이클 2와 묶어서 판정**한다. 사이클 2가 이득을 내지 못하면 둘 다 되돌린다.

### 이 사이클이 남긴 교훈

**노드 등록 상태를 개선 지표로 쓰면 안 된다.** 노드가 `candidate`라고 해서 브라우저가 실패하는 것이 아니다. 판정 지표는 **브라우저 19명의 확인 필요 합계**와 **노드 계측기의 `WRONG`/`CORRECT`** 둘뿐이다.

## 사이클 2 — CAGI 빈 양식의 6.4% 오차를 제거했다. **결과는 무변동.**

### 2.1 수정

Codex가 `cagi-blank.png`의 오른쪽 외곽을 정하던 2픽셀 선을 배제하도록 고쳤다. 자산 파일은 편집하지 않았다.

```
CAGI 빈 양식   R=1619  →  R=1513      (스캔 1511~1513과 일치)
만족도 빈 양식  R=1513  →  R=1513      (불변, 요구대로)
```

`tableRowDetection.ts`도 함께 바꿨다 — 좁아진 좌표계에서 글자 획이 행 경계로 잡히지 않도록, 가장 가까운 선 대신 **타당한 행 높이 범위 안의 최적 쌍**을 고른다.

### 2.2 판정

| 지표 | 기준선 | 사이클 1+2 |
|---|---|---|
| 브라우저 19명 합계 | **135** | **135** |
| 학생별 | 6·12·11·8·10·7·5·4·11·8·11·6·5·11·7·5·3·2·3 | **한 칸도 동일** |
| 노드 계측기 | 108/135 · WRONG 0 | 108/135 · WRONG 0 |
| 단위 테스트 | 114 | 114 |

**기각.**

### 2.3 ★ 왜 6.4% 오차가 아무것도 바꾸지 않는가

코드에 답이 있다. 격자 검출은 템플릿을 **출발 가설로만** 쓰고 실제로 찾은 괘선에 등록하며, 그 허용치가 `GRID_TEMPLATE_TOLERANCE_RATIO = 0.35`다. **6.4%는 35% 안에 한참 들어간다.**

즉 좌표계는 실제로 틀렸고, **그리고 병목이 아니다.** 파이프라인이 스스로 흡수한다.

이것으로 사이클 1도 함께 기각한다. 남기는 것은 **사이클 1b(로컬 저장소)**, 빈 양식 교정 테스트, 프로브, 그리고 문서다.

## 사이클 3 — 표적 선정

되돌린 뒤 남은 135칸을 군집별로 셌다.

```
만족도 5점(7~10)        35칸  25.9%
기본정보(성별/학교/학년)  26칸  19.3%
CAGI                    26칸  19.3%
만족도 예/아니오(2~6)     20칸  14.8%
연령대                   19칸  14.1%   ← 단일 항목 최대 (19/19 전원)
만족도 문항1              9칸   6.7%
```

**기본정보 26칸**을 골랐다. 가장 크지는 않지만 **기제가 가장 뚜렷하게 계측돼 있다.**

무표시 칸이 14%를 내면 거부되고 2%면 통과한다. 그리고 학생 15의 `남 20% / 여 16%`처럼 **양쪽이 함께 올라간다** — 표기가 번진 것이 아니라 **빼야 할 인쇄 잉크가 안 빠진 것**을 가리킨다.

주문에 계측을 먼저 요구했고(가설이 틀렸으면 그렇게 보고하도록), 임계값·`0.08` 상수·자산 편집을 모두 금지했다. **통과 기준이 내려가는 것이 아니라 무표시 칸의 점수가 내려가야 한다.**

### 3.1 계측 (Codex, 수정 전)

19페이지 57개 기본정보 그룹에서 `점수(실제잉크/빈양식잉크)`를 뽑았다.

```
p1  학교유형   .003(.112/.171)  .174(.226/.046)  .046(.171/.170)  .003(.016/.065)
p15 학교유형   .010(.076/.095)  .139(.212/.084)  .005(.029/.065)  .085(.147/.141)
```

**가설은 부분적으로만 맞았다.** 전역 ROI 좌표가 틀린 것이 아니었다. 작은 래스터에서 페이지와 빈 양식의 **픽셀 위상**이 달라 인쇄 테두리 잔여가 한쪽 방향으로 남았다.

그리고 정렬 오프셋이 **탐색 경계에 붙은 칸이 여럿**이었다 — p14 `(+3.00,+0.50)`, p15 `(-2.67,+1.00)`. 탐색 범위 자체가 좁다는 신호다(이번에 손대지 않았다).

### 3.2 수정과 판정

기본정보 체크박스 비교에만 쌍선형 샘플링을 넣었다. CAGI·만족도는 기존 최근접 유지. 임계값·`0.08`·ROI 좌표·자산 모두 무변경(직접 확인).

| 단위 테스트 | 114 | 114 |
| **브라우저 19명 합계** | **135** | **136** |

학생 3에서 **학년이 자동 입력되던 것이 거부로 바뀌었다.** 고치려던 바로 그 필드 부류에서 한 칸을 잃었다.

## 사이클 4 — 정렬 탐색 범위: 중립

기본정보 정렬 오프셋이 탐색 경계에 붙는 칸을 줄였다.

```
경계 부착      12칸 → 7칸       (최상위 후보 기준 7 → 5)
최종 오프셋    |x|=3, |y|=3
```

Codex가 더 넓은 범위(`reach=5,4`)도 시험했고 **`WRONG 1`이 나와 적용하지 않았다** — 주문의 절대 조건을 스스로 지켰다. 그리고 정직하게 보고했다: `probe ±4`에서 여전히 16/72가 경계에 붙으므로 **범위만이 원인은 아니다.**

| 지표 | 기준선 | 사이클 4 |
|---|---|---|
| 노드 계측기 | 108/135 · WRONG 0 | 108/135 · WRONG 0 |
| 단위 테스트 | 114 | 114 |
| **브라우저 19명** | **135** | **135** |

**기각.** 악화는 없지만 이득도 없다. 정렬 품질 자체는 실제로 좋아졌으나(경계 부착 12→7) 실사용 결과는 한 칸도 움직이지 않았다.

### 이 사이클이 더한 것

사이클 3에서 좁혀둔 "기본정보 = 픽셀 위상/정렬 문제"라는 그림에서, **정렬을 더 잘해도 결과가 안 바뀐다**는 것이 확인됐다. 사이클 3(샘플링)은 악화, 사이클 4(범위)는 중립이다.

**기본정보 26칸의 원인은 정렬 정밀도가 아니다.** 다음 시도는 이 축이 아닌 곳에서 찾아야 한다.
