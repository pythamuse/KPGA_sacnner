## 2. 가장 중요한 발견: 템플릿 좌표는 정확하다

빈 양식에서 표 괘선을 검출해 각 응답 행의 중심을 실측하고, 현재 `roiTemplates.ts` 값과 비교했다.
좌표는 앱 런타임과 동일하게 `loadImageAnalysisData`의 `contentBounds` 기준 정규화 값이다.

| 대상 | 실측 행 중심 | 현재 템플릿 | 오차 |
|---|---|---|---|
| CAGI Q1~Q7 | 0.3335, 0.3592, 0.3848, 0.4018, 0.4189, 0.4360, 0.4531 | 0.334, 0.358, 0.383, 0.401, 0.419, 0.436, 0.455 | **≤0.002** |
| 만족도 Q2~Q6 | 0.4293, 0.4775, 0.5257, 0.5610, 0.5968 | 0.43, 0.478, 0.526, 0.561, 0.596 | **≤0.001** |
| 만족도 Q7~Q10 | 0.7510, 0.7815, 0.8120, 0.8420 | 0.75, 0.78, 0.811, 0.841 | **≤0.001** |

**페이지 높이의 0.1~0.2% 이내로 일치한다. 템플릿은 처음부터 정확했다.**

## 3. §2 원인분석 정정 — 내가 틀렸다

[[COORDINATE_REGISTRATION_AND_RESPONSE_PRIOR_PLAN]] §12와 [[RECOGNITION_ARCHITECTURE_REDESIGN]] §2에서 나는 이렇게 주장했다:

> "템플릿은 행 간격이 불균등([1, 1, 0.729, 0.729])하다고 주장하는데, 인쇄된 표의 같은 유형
> 응답 행은 거의 항상 균등하다. 실측 편차 40~48%가 그 차이(약 37%)와 일치하므로,
> 검출기는 옳고 템플릿이 틀렸다."

**빈 양식을 보니 이 전제가 사실이 아니다. 행 간격은 실제로 불균등하고, 템플릿이 그걸 정확히 반영하고 있었다.** 이유는 단순하다 — **일부 문항이 2줄짜리라 행 높이가 2배다**:

- **CAGI Q2**: "돈내기 게임을 같이 하는 친구들과 어울리느라 다른 친구들과의 약속을 어긴 적 있나요?" → 2줄
- **만족도 Q3**: "도박중독의 심각성(폐해, 부작용)을 알게 되었다." + "-폐해: 범법행위 또는 시도, 언어적·신체적 폭력행사..." → 2줄

2배 높이 행이 하나 끼면 중심 간 간격이 `[1, 1, 0.667, 0.667, ...]` 꼴이 되는데, 이것이 템플릿의 `[1, 1, 0.729, 0.729]`와 거의 같다. **불균등이 정상이다.**

따라서 직전 라운드에서 "템플릿 간격 대조를 버리고 균등성 검사로 교체"한 재설계는 **틀린 전제에서 출발했고, 정확한 정보(템플릿 패턴)를 버리고 사실이 아닌 가정(행은 균등하다)으로 바꾼 것**이다. CAGI가 그 검사를 통과한 건 CV가 0.20으로 우연히 0.25 문턱 아래였기 때문이지, 행이 균등해서가 아니다.

## 4. 그렇다면 진짜 원인: 괘선 검출 감도

같은 빈 양식에서 검출 임계값을 스윕했다(답안 열 구간, 필요한 괘선 개수 대비):

| darkThreshold | minDarkRatio | CAGI Q1~7 검출 수(필요 8) | 만족도 Q2~6 검출 수(필요 6) |
|---|---|---|---|
| 200/220/240 | **0.5** | 3 | 2 |
| 200/220/240 | 0.4 | 3 | 3 |
| 200/220/240 | **0.3** | **8 ✓** | **7 ✓** |

- **`darkThreshold`는 전혀 영향이 없다**(200/240 결과가 동일). 괘선은 충분히 검다.
- **`minDarkRatio`만이 결정적**이다. 0.5에서는 표의 굵은 바깥 테두리만 잡히고, **행 사이의 얇은 내부 괘선이 전부 누락**된다. 0.3이면 정확히 필요한 개수가 잡힌다.

현재 코드:
- `tableGridDetection`은 `detectHorizontalLines(..., 0.3)` — **0.3을 쓴다.**
- `tableRowDetection.findRowMatch`는 `detectHorizontalLines(image, ...)` — **기본값 0.5를 쓴다.**

이것이 실사용 진단 `행: 픽셀 insufficient_lines (행 선 4/5개)`의 정확한 원인이다. **오염된 사진이라서가 아니라, 티 하나 없는 빈 양식에서도 0.5로는 내부 괘선을 못 찾는다.**

## 5. 부수 발견

- **`contentBoundsConfident = false`** — 완벽한 빈 스캔에서도 페이지 프레임을 "확신"하지 못한다. `hasUsableFormBounds`는 통과하므로 자동 인식은 되지만, 양식 내용 기반 분류(`classifyByImageContent`)는 항상 파일명 힌트로 폴백한다는 뜻이다. 현재로선 안전한 동작이지만, 프레임 판정 기준이 실사용 입력에 비해 과하게 엄격하다는 신호다.
- **`npm test` 실행이 `templates/`의 원본 엑셀 2개를 변경한다.** `Docs/05_HARNESS.md` 1번 규칙("원본 엑셀 템플릿 파일은 절대 변경하지 않는다")을 위반한다. 이번엔 `git checkout`으로 되돌렸지만, 테스트가 원본을 건드리지 않도록 별도 수정이 필요하다(아래 작업지시서 5번).

## 6. 작업지시서 (Codex, Luna-Max)

**배경**: 위 §2~§4를 반드시 먼저 읽을 것. 핵심은 **템플릿 좌표는 정확하고(오차 0.1%), 문제는 순전히 괘선 검출 감도**라는 것이다. 직전 커밋(`53435b5`)의 균등성 검사는 틀린 전제 위에 있다.

1. **`tableRowDetection.ts`의 괘선 검출 감도 수정**: `findRowMatch`가 `detectHorizontalLines`를 호출할 때 기본값 0.5 대신 **0.3**을 명시적으로 넘긴다(`tableGridDetection`이 이미 쓰는 값과 통일). 빈 양식 실측상 0.3이 정확히 필요한 개수를 찾고 0.5는 절반 이하만 찾는다.

2. **균등성 검사(`53435b5`에서 도입)를 템플릿 간격 패턴 대조로 되돌린다.** §2·§3에서 템플릿이 정확함이 실측으로 증명됐으므로, 템플릿 패턴은 균등성 가정보다 **더 많은 정보를 담은 더 엄격한 검증**이다. 다만 `toleranceRatio`는 기존 0.35를 유지하고, 균등성 검사는 완전히 제거하지 말고 **보조 조건으로만 남겨도 된다**(둘 다 만족해야 통과). 어느 쪽이든 "실제 표의 불균등한 간격을 정상으로 받아들일 것"이 요구사항이다.

3. **회귀 테스트 추가 — 이번 작업의 가장 중요한 산출물**: 새로 커밋된 `tests/fixtures/blank-form/cagi-blank.png`와 `satisfaction-blank.png`를 사용해, **실제 양식 이미지에서 CAGI Q1~Q9와 만족도 Q1~Q10 전부가 격자/행 검출에 성공하는지** 검증하는 테스트를 추가한다(`tests/blank-form-detection.test.ts` 신규). 각 필드의 `recognitionCropSource`가 `'fixed'`가 **아니어야** 한다. 이 테스트가 앞으로 "실제 양식에서 좌표를 못 찾는" 회귀를 잡는 유일한 방어선이다. 합성 이미지가 아니라 진짜 양식이라는 점이 핵심이다.

4. **검출된 행 중심이 템플릿 값과 일치하는지도 검증**한다(§2 표의 실측값 기준, 허용 오차 ±0.01 정도). 좌표가 미래에 드리프트하면 즉시 잡히도록.

5. **`npm test`가 `templates/` 원본 엑셀을 변경하지 않도록 수정**한다(§5). 테스트는 반드시 사본에서 작업해야 한다. 수정 후 `npm test` 실행 뒤 `git status`가 `templates/` 변경을 보이지 않아야 한다.

6. 자동 확정 안전장치(`allowAutoValue`, `requiresHighVisualConfidence`)는 **이번에도 건드리지 않는다.**

7. `npm test`, `npm run build` 통과 확인 후 `src/app/page.tsx` 버전 마커를 규칙대로 갱신하고 커밋·푸시.

보고 시: (a) 파일별 변경, (b) 테스트/빌드 결과, (c) **3번 테스트에서 CAGI/만족도 각 문항이 실제로 어떤 source(`grid`/`row`/`fixed`)로 판정됐는지 전체 목록** — 이게 이번 라운드의 진짜 결과다, (d) 5번 수정 후 `git status`가 깨끗한지 확인 결과.

## 7. 2026-08-11 후속 운영 규칙

이번 실사용 PDF와 빈 양식의 대조 결과, 템플릿 좌표 자체는 맞고 응답 판독과 손글씨 OCR을 별도로 다뤄야 한다는 점이 확인됐다. 후속 구현은 아래 규칙을 반드시 지킨다.

1. **응답 값은 빈 양식 차분으로 판독한다.** 인쇄된 동그라미와 표선의 어두운 픽셀을 그대로 점수화하지 않는다. 동일 좌표의 빈 양식에서 이미 존재하는 잉크를 제거하고, 새로 추가된 필기 흔적만 후보 간 비교한다.
2. **문항 좌표와 마크 판독을 혼동하지 않는다.** 격자 괘선 검증이 통과한 후보 셀만 자동 입력할 수 있다. 괘선 검증 실패, 중복 셀, 행/열 기하 불일치는 검수 후보로 남기며 응답 빈도 가중치로 덮어쓰지 않는다.
3. **PDF와 사진은 같은 템플릿 등록·격자 검증을 사용하되, 카메라 전용 원근 보정은 입력 종류에 따라 분리한다.** PDF.js가 렌더한 PDF 페이지는 이미 평면 사각형 래스터이므로 브라우저의 OpenCV 원근 보정 Worker를 호출하지 않는다. PDF의 페이지별 미세 오프셋은 서버의 템플릿 등록과 격자 검증으로 처리한다. 반대로 카메라·직접 사진은 신뢰할 만한 문서 사각형이 검출될 때만 원근 보정을 시도하며, 실패하면 원본을 보존한 채 동일한 등록·검증 단계로 진행한다. PDF에 카메라 Worker를 적용해 페이지마다 같은 "보정 엔진을 사용할 수 없음" 경고를 반복하는 구현은 금지한다.
4. **기본정보는 검증된 경우에만 자동 저장한다.** 성별·학교유형·학년의 행 또는 열 기하가 독립적으로 검증되지 않으면 값은 비워 두고 검수자가 결정한다. 연령은 손글씨 OCR 신뢰도가 60 미만이면 오답을 저장하지 않는다.
5. **엑셀 확장 XML은 네임스페이스와 함께 복원한다.** `extLst`를 되삽입할 때 템플릿의 루트 네임스페이스와 `mc:Ignorable` 토큰도 함께 병합하고, 생성 파일에서 미선언 접두사를 검사한다.

구체적인 실사용 회귀 결과와 이번 구현의 제한 사항은 `Task/TEMPLATE_BASELINE_RECOGNITION_AND_WORKBOOK_REPAIR_2026-08-11.md`에 기록한다.
