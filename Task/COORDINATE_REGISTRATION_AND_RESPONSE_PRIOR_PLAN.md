# 좌표 등록 재설계 및 응답 사전확률 적용 계획

작성일: 2026-08-05

## 1. 목적과 범위

실제 사용자 검수 화면에서 보고된 CAGI와 예방교육 만족도조사의 ROI 오류를 문항 표 구조별로 분리한다. 이 문서는 현재 관찰, 원인 가설, 안전한 개선 순서, 응답 빈도 활용 원칙을 기록한다. 구현 또는 자동 확정 정책을 변경하기 전의 기준 문서다.

대상 파일:

- `src/lib/recognition/detectCheckmarks.ts`
- `src/lib/recognition/tableGridDetection.ts`
- `src/lib/recognition/tableRowDetection.ts`
- `src/lib/recognition/roiTemplates.ts`
- `src/lib/recognition/markDensity.ts`
- `src/components/RecognitionReview.tsx`

## 2. 현재 관찰

### 2.1 공통

- 원본은 종이 전체가 비교적 잘 보이는 스캔/촬영 이미지다.
- 검수 원본 미리보기는 정상이어도, 문항별 crop은 실제 체크 셀과 일치하지 않는다.
- 따라서 단순한 체크 마크 판별 실패가 아니라 문서 좌표계 등록과 표 블록 분리가 먼저 실패한 사례다.
- 후보 퍼센트는 실제 응답 확률이 아니라 현재 crop 안의 어두운 픽셀 점수다. 표 선, 인쇄된 원형 숫자, 글자가 체크 표시보다 더 진하면 오답 후보가 높아질 수 있다.

### 2.2 CAGI 기본정보

| 항목 | 화면 관찰 | 현재 판단 |
|---|---|---|
| 연령대 | crop에 수기 `14`가 보이지만 입력칸이 비어 있음 | 현재 CAGI 경로는 `basic.age`를 crop으로만 제공하며 숫자를 읽어 `draft.basic.age`에 넣는 OCR/숫자 판별 단계가 없음 |
| 학교유형 | 원본의 중학교 체크 위치와 후보 ROI가 불일치 | 정적 정규화 좌표가 불확실한 문서 경계를 기준으로 변환되어 틀어짐 |
| 학년 | 다음 안내문까지 포함하는 낮은 위치를 추종 | 정적 정규화 좌표의 세로 등록 오차 |

화면의 연령대 배지 `확인`은 `높음`이 아닌 medium confidence다. 수기 숫자가 crop에 보인다는 사실만으로 값이 인식된 것은 아니다.

### 2.3 CAGI 1~9번

| 구간 | 화면 관찰 | 진단 |
|---|---|---|
| 1~6번 | 표 블록을 대체로 향하지만 후보 간 점수 차이가 작음 | 선택지 셀 중앙과 마크의 분리가 불완전하거나 인쇄 요소가 함께 측정됨 |
| 7번 | 비교적 올바른 행을 보지만 low confidence | 후보 `3/34%`, `1/27%`, `2/25%`처럼 점수 차가 작아 자동 확정 기준을 통과하지 못함 |
| 8번 | 실제 행에서 미세하게 벗어남 | 8~9번의 별도 표 헤더와 행 높이 전환을 일반 행 간격과 동일하게 해석함 |
| 9번 | 조기개입 서비스 안내 영역을 crop함 | 특수 표 하단의 행 등록이 크게 누적 이탈함 |

CAGI 8~9번은 1~7번과 선택지 문구 및 표 헤더가 다르므로, 하나의 연속 행 모델로 처리하면 안 된다.

### 2.4 예방교육 만족도조사 1~10번

| 구간 | 화면 관찰 | 진단 |
|---|---|---|
| 1번 | 빈 여백과 표 경계선 중심으로 crop | 문항 1의 독립 4선택지 표를 찾지 못함 |
| 2~6번 | 같은 예/아니오 열 일부를 반복해서 crop | 문항 행 분리 실패 |
| 7번 | 5점 척도 표의 헤더를 crop | 만족도 표의 첫 응답 행 시작점 등록 실패 |
| 8번 | 실제 체크와 무관한 `0`을 높음으로 자동 선택 | 인쇄된 원형 숫자/선의 명암을 수기 체크로 오인한 위험한 false positive |
| 9~10번 | 일부 응답 행에 접근하지만 행/열 매칭 불안정 | 5점 척도 격자 등록 미완성 |

만족도조사는 다음 세 표를 독립적으로 탐지해야 한다.

1. 문항 1: 4개 선택지 1행
2. 문항 2~6: 예/아니오 2열 x 5행
3. 문항 7~10: 5점 척도 5열 x 4행

## 3. 원인 가설

1. 페이지 외곽 또는 내용 경계가 충분히 신뢰되지 않으면, 정적 템플릿의 정규화 좌표가 전체적으로 이동한다.
2. 동적 격자 검출은 현재 답안 표 일부에만 적용되며 CAGI 기본정보, CAGI 8~9번 특수 표, 만족도 3개 표 블록을 독립적으로 등록하지 않는다.
3. 표 셀의 인쇄 원형과 수기 체크를 구분하는 특징이 부족하다. 현재의 단순 어두운 픽셀 밀도는 `0` 같은 인쇄 기호에도 높은 점수를 줄 수 있다.
4. crop이 틀어진 상태에서도 후보 점수가 계산되므로, 점수 자체가 높아도 문항-셀 매칭의 품질을 보장하지 않는다.

## 3.1 테스트 결과 및 원인 분석

### 테스트 입력과 결과

| 테스트 | 입력 | 관찰 결과 | 결론 |
|---|---|---|---|
| 모바일/파일 이미지 CAGI + 만족도 | 종이 전체가 보이고 기울기가 비교적 적은 동일 샘플 | 두 양식이 검수 화면까지 도달했으나 기본정보와 다수 문항 crop이 실제 응답 셀을 벗어남 | 양식 분류 또는 업로드 실패가 아니라 좌표 등록 실패 |
| CAGI 기본정보 | 원본의 나이 `14`, 중학교, 학년 체크가 보이는 페이지 | 연령대 crop에는 `14`가 보이지만 입력값은 비어 있음. 학교유형/학년 crop은 주변 표나 안내문까지 포함 | 연령대 값 추출 기능 부재 및 기본정보 정적 ROI 이탈 |
| CAGI 1~7 | 일반 4선택지 표 | 7번은 실제 행에 근접하지만 후보 점수 차가 작아 low confidence | 셀 정렬 또는 마크 분리 품질 부족. 올바른 행에 있어도 확정 근거가 부족함 |
| CAGI 8~9 | 별도 응답 문구와 헤더가 있는 하단 특수 표 | 8번은 소폭 이탈, 9번은 조기개입 서비스 안내 영역을 crop | 일반 1~7 행 간격을 특수 표에 연장 적용한 블록 전환 실패 |
| 만족도 1 | 독립 4선택지 표 | 빈 여백/가로선 위주 crop | 첫 표의 시작점과 열 좌표 등록 실패 |
| 만족도 2~6 | 예/아니오 2열 x 5행 표 | 비슷한 열 조각이 문항 카드마다 반복 | 각 행의 분리 또는 행 번호 매칭 실패 |
| 만족도 7~10 | 5점 척도 5열 x 4행 표 | 7번은 헤더, 8번은 실제 체크와 무관한 `0`을 high confidence로 선택, 9~10번도 불안정 | 표 헤더/응답 행 경계 등록 실패와 인쇄 원형 false positive가 결합 |
| 19페이지 CAGI + 만족도 PDF | 각 PDF가 실제 19페이지인 일괄 스캔 파일 | 이전에는 18/19장으로 계산됐으나 `unknown` 페이지를 업로드 칸 기준으로 보존한 뒤 19쌍 처리 경로가 복구됨 | 이번 ROI 문제와 별개로 PDF 누락 문제는 분류 폴백 정책 문제였음 |
| JBIG2 포함 PDF | 브라우저 PDF.js 렌더링에서 JBIG2 경고가 발생한 PDF | 빈 캔버스가 원본/ROI 미리보기로 전달되는 현상 확인 후 WASM 경로와 빈 캔버스 차단 적용 | 이번 좌표 이탈과 별개인 렌더링 입력 손상 문제였음 |

### 원인 구분

이번 검수 화면의 문제는 다음 선행 오류들과 구분해야 한다.

| 구분 | 증상 | 현재 판단 |
|---|---|---|
| PDF 렌더링 오류 | 원본/ROI가 흰색 또는 비어 보임 | JBIG2 처리와 빈 캔버스 차단 문제. 좌표 인식 오류와 독립 |
| PDF 장수 불일치 | 19페이지 PDF가 18페이지로 집계됨 | `unknown` 분류 페이지가 묶음에서 빠진 업로드 분류 정책 문제. 좌표 인식 오류와 독립 |
| 양식 불일치 | 올바른 파일이 반대 양식으로 분류됨 | 불확실한 문서 경계에서 내용 기반 분류가 업로드 칸 힌트를 뒤집은 문제 |
| 현재 ROI 오류 | 원본은 보이나 crop이 다른 행/헤더/안내문을 가리킴 | 페이지 경계 이후의 표 블록 등록과 셀 매칭 문제 |

### 근거 기반 원인 판정

1. 원본 미리보기에는 두 설문지가 온전히 보이므로, 현재 사례는 빈 PDF 캔버스나 업로드 누락으로 설명되지 않는다.
2. CAGI 9번 crop이 조기개입 안내문을 가리키는 것은 마크 점수 조정만으로 해결할 수 없는 좌표 블록 전환 실패의 직접 증거다.
3. 만족도 8번이 인쇄된 `0`을 high confidence로 선택한 것은 높은 마크 점수가 실제 수기 응답을 뜻하지 않는다는 직접 증거다.
4. 연령대 crop의 `14`와 빈 입력값의 조합은 OCR 오인식이 아니라 현재 코드 경로에 숫자 값을 `draft.basic.age`로 넣는 단계가 없다는 기능 공백을 보여준다.
5. 따라서 현재 우선순위는 임계값, 후보 순위, 응답 빈도 조정이 아니라 표 블록 등록과 인쇄 기호 제거다.

## 4. 개선 원칙

### 4.1 좌표 등록 우선

- 페이지별로 문서 경계, 표 블록, 행, 열 순서로 등록한다.
- 각 표 블록은 독립된 기준점과 격자 수를 가진다. 한 블록의 y좌표 보정값을 다른 블록에 재사용하지 않는다.
- 행/열 수, 셀 종횡비, 교차점, 표 외곽선을 모두 만족하는 경우에만 실제 픽셀 셀을 인식 ROI로 사용한다.
- 등록 품질이 부족하면 자동값을 비워 두고 low confidence 및 원본 대조를 유지한다. 정적 템플릿은 crop 안내용 폴백일 뿐 자동 확정 근거가 아니다.

### 4.2 마크 판별

- 인쇄된 원형 숫자와 수기 체크를 구분하기 위해 셀 내부 중심의 국소 잉크 변화, 선 두께, 기울어진 획, 연결 성분을 함께 평가한다.
- 인쇄 기호가 모든 셀에 반복되는 구조는 문항별 상대 비교만으로는 충분하지 않다. 빈 양식 기준 이미지 또는 같은 행의 선택지 간 공통 인쇄 패턴 제거가 필요하다.
- 자동 확정은 `좌표 등록 신뢰도`, `마크 판별 점수`, `최고 후보와 차순위 후보의 점수 차`를 모두 통과해야 한다.

### 4.3 기본정보

- 연령대는 `14`처럼 한두 자리 숫자를 읽는 전용 숫자 ROI와 값 검증 범위로 구현한다. crop 존재 여부로는 값을 확정하지 않는다.
- 학교유형과 학년은 정적 비율 좌표 대신 상단 기본정보 표의 교차선을 기준으로 셀을 등록한다.
- 연령대/학교유형/학년의 crop과 실제 입력값은 같은 등록 좌표를 사용해야 한다.

## 5. 응답 빈도 가중치 검토

### 5.1 제공된 초기 사전값

아래 값은 현재 운영 경험에 따른 초기 가설이며, 실제 라벨 데이터가 쌓이기 전에는 확률 또는 정답 규칙으로 취급하지 않는다.

| 양식 | 문항 | 빈도가 높다고 보고된 응답 | 자동 확정 시 추가 주의 |
|---|---|---:|---|
| CAGI | 1, 2, 3, 6, 7, 9 | 0 | 보조 우선순위로만 사용 |
| CAGI | 4, 5, 8 | 0 | 다른 응답도 발생하므로 높은 시각 신뢰도 없이는 0으로 보정 금지 |
| 만족도 | 1 | 0 | 다른 응답도 자주 발생하므로 높은 시각 신뢰도 없이는 0으로 보정 금지 |
| 만족도 | 2, 3, 4, 5, 6 | 1 | 보조 우선순위로만 사용 |
| 만족도 | 7, 8, 9, 10 | 4 | 다른 응답도 발생하므로 높은 시각 신뢰도 없이는 4로 보정 금지 |

### 5.2 적용해도 되는 범위

응답 빈도는 다음을 모두 충족할 때만 후보 순위를 보조할 수 있다.

1. 페이지 및 표 블록 등록이 신뢰 기준을 통과했다.
2. 해당 문항의 모든 선택지 셀이 실제 픽셀 좌표로 확보됐다.
3. 시각 후보가 근소한 차이로 동률 또는 준동률이다.
4. 결과는 `자동 확정`이 아니라 검수 화면의 추천값 또는 medium confidence로 남긴다.

개념적으로는 `최종 후보 점수 = 시각 마크 점수 + 제한된 사전확률 보정`을 사용할 수 있다. 단, 사전확률 보정의 상한은 시각 점수를 뒤집을 수 없게 제한한다.

### 5.3 적용하면 안 되는 범위

- ROI가 다른 문항/안내문/표 헤더를 가리키는 경우
- 페이지 또는 표 블록 등록이 실패한 경우
- 인쇄 원형을 체크로 오인할 수 있는 경우
- 위 표의 `자동 확정 시 추가 주의` 문항에서 시각 근거가 약한 경우

이 경우 빈도 가중치는 신뢰도를 올리지 않으며, 값은 비워 둔 채 검수한다. 빈도 기반으로 빈칸을 채우면 실제 위험 신호나 부정 응답을 체계적으로 지우게 된다.

### 5.4 데이터 기반 전환 조건

- 수동 검수로 확정된 샘플을 양식·문항·응답별로 최소 100건 이상 축적한다.
- 응답 비율, 카메라/스캐너별 오류율, 문항별 false positive/false negative를 분리 측정한다.
- 가중치 적용군과 미적용군을 비교해 실제 정답률이 개선되는지 확인한다.
- 특히 CAGI 4·5·8과 만족도 1·7~10은 재현율보다 잘못된 자동 확정을 더 엄격하게 제한한다.

## 6. 조기개입 서비스 개인정보 입력 알림

### 요구사항

선별검사지의 조기개입 서비스 영역에서 이름과 전화번호가 모두 수기로 입력된 것으로 감지되면, 해당 페이지의 검수 화면에 알림을 표시한다.

### 안전한 처리 원칙

- 이름 또는 전화번호 자체는 OCR 추출, 검수 카드 표시, 로그, 엑셀 저장 대상이 아니다.
- `개인정보 입력 가능성 감지` 여부와 페이지 번호만 남긴다.
- 이름 칸과 전화번호/이메일 칸을 별도 ROI로 판별하고, 두 영역 모두 수기 입력 흔적이 있을 때만 알림 후보로 만든다.
- 문서 경계 또는 조기개입 표 등록이 불확실하면 자동 알림을 확정하지 않고 수동 확인 대상으로 남긴다.
- 조기개입 영역의 표기 또는 삭제 흔적은 CAGI 1~9 응답 추출과 양식 분류에 영향을 주지 않는다.

### 알림 문구 기준

`선별검사지 N페이지의 조기개입 서비스 영역에서 이름 및 연락처 입력 흔적이 감지되었습니다. 개인정보는 저장하지 않으며, 원본을 확인해 후속 절차를 진행하세요.`

## 7. 구현 순서와 검증 기준

1. 현재 샘플에 대해 문항별 실제 셀과 crop의 일치 여부를 라벨링한다.
2. CAGI 기본정보, CAGI 1~7, CAGI 8~9를 독립 블록으로 등록한다.
3. 만족도 1, 2~6, 7~10을 독립 블록으로 등록한다.
4. 등록 성공 시에만 셀 단위 마크 판별을 수행하고, 실패 시 자동값을 금지한다.
5. 빈 양식 또는 인쇄 기호 기준 제거를 적용해 인쇄 원형 false positive를 측정한다.
6. 수동 검수 라벨 데이터가 축적된 뒤에만 응답 빈도 가중치를 medium 추천값으로 시험한다.
7. 조기개입 이름/전화번호 동시 입력 알림을 개인정보 비저장 방식으로 추가한다.

완료 기준:

- CAGI 기본정보 및 1~9번 crop이 각각 실제 문항의 선택지 행/열을 포함한다.
- 만족도 1, 2~6, 7~10의 crop이 각 표 블록을 넘지 않는다.
- 원본의 인쇄 원형만으로 high confidence 값이 확정되지 않는다.
- 좌표 등록 실패 시 빈도 가중치가 자동값을 만들지 않는다.
- 조기개입 이름/연락처 경고는 페이지 번호만 제공하고 개인정보 텍스트를 저장하지 않는다.

## 8. 이번 단계 결론

현재 우선순위는 OCR 모델 교체나 응답 빈도 적용이 아니라 셀 좌표 등록의 신뢰성 회복이다. 응답 빈도는 좌표와 마크 판별이 모두 유효한 제한된 상황에서만 사람이 빠르게 검수할 수 있도록 돕는 보조 신호로 검토한다.

## 9. 2026-08-05 구현 결과

### 9.1 반영한 좌표 인식 변경

- 문서 전체의 어두운 영역을 찾아 정적 템플릿을 이동시키던 보정은 제거했다. 이 방식은 제목, 안내문, 인쇄 문자를 표로 오인해 서로 다른 문항의 ROI가 같은 위치를 추종하는 원인이었다.
- CAGI는 `1~7`, `8~9` 문항 표를, 만족도조사는 `1`, `2~6`, `7~10` 표를 독립된 행·열 격자로 탐지한다. 기대한 행·열 수, 간격, 셀 크기가 모두 일치할 때만 실제 셀 좌표를 자동 인식에 사용한다.
- CAGI 8~9번은 별도 표의 행을 사용하므로, 9번이 조기개입 안내 영역을 crop하던 문제를 차단했다.
- 만족도 7~10번은 하단 5점 척도 표의 행을 사용하므로, 7번이 표 헤더를 crop하거나 8번이 인쇄된 `0`을 답으로 오인하던 문제를 줄인다.
- 연령, 성별, 학교유형, 학년은 현재 자동 확정 대상이 아니다. 상단 기본정보 표의 위치를 검수 crop으로 제공하며, 숫자 OCR과 기본정보 셀 등록은 후속 작업으로 남긴다.

### 9.2 자동 확정 안전장치

- 페이지 전체의 문서 범위가 유효하고, 해당 문항의 실제 격자 셀을 모두 찾았을 때만 자동 응답값을 제안한다.
- CAGI 4·5·8 및 만족도 1·7·8·9·10은 빈도가 높은 응답이 있더라도, 높은 시각 신뢰도를 통과하지 못하면 자동으로 채우지 않는다.
- 제공된 응답 빈도는 아직 자동값, 점수 가산, 빈칸 보정에 사용하지 않는다. 특히 만족도 문항 1의 실제 저장값 체계는 `1~4`이므로, 사용자 관찰의 `0` 표기는 곧바로 저장값으로 변환하지 않는다.
- 따라서 좌표 등록 또는 마크 판별이 불확실한 값은 의도적으로 비워 두고 검수 화면에서 확인한다.

### 9.3 조기개입 서비스 알림

- 조기개입 서비스의 이름 칸과 연락처 칸에 모두 수기 입력 흔적이 있을 때, 해당 CAGI 페이지 번호만 포함한 경고를 반환한다.
- 이름·전화번호·이메일의 텍스트는 OCR로 읽지 않고, 응답 데이터·엑셀·로그·경고 문구에 저장하지 않는다.
- 조기개입 영역의 체크 또는 개인정보 입력 흔적은 CAGI 1~9 문항 인식 좌표와 양식 분류를 바꾸지 않는다.

### 9.4 로컬 샘플 검증 결과

- 제공된 스캐너 샘플에서 CAGI 1~9의 격자 셀과 만족도 2~10의 격자 셀을 각각 독립적으로 등록했다.
- CAGI 7번과 9번, 만족도 7번과 8번의 검수 crop이 기존처럼 다른 문항·헤더·조기개입 안내문을 가리키지 않고 해당 응답 행을 가리키는 것을 확인했다.
- 만족도 1번은 단일 행 표의 경계 검출이 부족할 수 있어 현재는 정적 검수 crop과 수동 확인을 유지한다. 이 문항은 높은 시각 신뢰도 정책도 적용한다.
- CAGI 기본정보는 올바른 상단 표 주변을 보여 주지만 자동값을 채우지 않는다. 예를 들어 연령 숫자가 보이더라도 숫자 OCR이 구현되기 전까지는 수동 검수 대상이다.

### 9.5 후속 검증 기준

1. 카메라 사진과 일괄 스캔 PDF에서 각 표 블록이 독립적으로 등록되는지 확인한다.
2. CAGI 4·5·8, 만족도 1·7~10이 약한 근거만으로 자주 응답되는 값으로 자동 확정되지 않는지 확인한다.
3. 조기개입 이름·연락처 동시 입력 시 페이지 번호만 알리고 개인정보 텍스트가 화면·응답·로그에 없는지 확인한다.
4. 수동 검수 확정 데이터가 문항별 100건 이상 쌓인 뒤에만 응답 빈도를 medium 추천값으로 실험한다.

## 10. 2026-08-06 실배포 재현: §9.4의 "로컬 샘플 검증" 결과가 실사용 데이터에서 재현되지 않음

### 10.1 관찰 (실제 배포본, 19쌍 일괄 스캔 PDF)

사용자가 `kpga-sacnner.vercel.app`(커밋 `e27138c` 반영 이후)에 실제 19페이지 CAGI PDF + 19페이지 만족도 PDF를 업로드해 검수 화면 스크린샷을 제공했다. 1/19번째 학생 기준:

- CAGI 01~09 전부 "낮음" 또는 "확인" 배지. 후보 점수가 0/29%, 2/12%, 1/9%처럼 근소한 차이로 흩어져 있다(§3.1이 "false positive"의 근거로 삼았던 패턴과 동일).
- crop 이미지 다수가 **두 개 이상의 인접 행 내용이 함께 보이는 넓은 가로 스트립**이다(예: CAGI 01~09 각 카드의 crop에 원문자 두 줄이 겹쳐 보임, 만족도 문항2 crop에 "아니오/예" 헤더와 체크 표시가 함께 보임).
- 학교유형/학년 crop은 여전히 인접 행·안내문이 섞인 넓은 블록을 보여준다(§2.2에서 지적된 것과 같은 증상).
- 연령대는 crop에 손글씨 "14"가 선명하게 보이지만 입력값은 비어 있다(§2.2, §9.1에서 이미 "미구현"으로 확인된 내용과 일치 — 새 증상 아님).

**이것은 §9.4("CAGI 7번과 9번, 만족도 7번과 8번의 검수 crop이... 해당 응답 행을 가리키는 것을 확인했다")가 주장한 로컬 검증 결과와 배치된다.** 로컬 샘플(정확한 출처 불명, 이 문서에 파일로 남아있지 않음)에서는 격자 검출이 성공했지만, 실제 사용자의 일괄 스캔 PDF에서는 (a) 격자 검출 자체가 실패해 구식 정적 템플릿 crop으로 조용히 폴백했거나, (b) 격자 검출이 "성공"으로 판정됐지만 잘못된 행/열에 매칭됐을 가능성이 있다. **현재 코드에는 이 둘을 구분할 방법이 전혀 없다** — `detectCheckmarks.ts`가 `recognitionCropRects[field]`를 격자 검출 성공 시(`if (gridCells)`)에만 채우고, 실패 시엔 `fieldCrop.ts`의 `findCropRect()`(순수 정규화 템플릿 좌표, 이번 세션 최초 원인 진단 대상이었던 바로 그 좌표계)로 조용히 넘어가는데, 이 전환이 검수 화면 어디에도 표시되지 않는다.

### 10.2 코드 추적으로 확인한 사실

- `src/lib/recognition/detectCheckmarks.ts`: CAGI/만족도 각 그룹마다 `cagiGridOverrides[group.field]`(격자 검출)가 있으면 그 결과로, 없으면 `cagiRowOverrides[group.field]`(OCR/픽셀 행 검출)로, 그것도 없으면 `analyzeChoiceGroup` 내부에서 정규화 템플릿 좌표로 폴백한다. `recognitionCropRects`(검수 화면 crop의 근거)는 **격자 검출 성공 시에만** 채워진다.
- `src/lib/recognition/fieldCrop.ts`의 `generateFieldCropBuffer`는 `pixelRect`(= `recognitionCropRects[field]`)가 없으면 `findCropRect(field)`로 폴백해 **원래 문제였던 정규화 템플릿 좌표**로 crop을 만든다.
- `src/components/RecognitionReview.tsx`의 `renderFieldCropPreview`는 기본적으로 **디버그 오버레이(빨간 ROI 박스 + 라벨)가 없는** `cropDataUrls` crop만 인라인으로 보여주고, 오버레이가 있는 버전은 별도 "ROI 확인" 링크를 새 탭으로 열어야만 볼 수 있다.
- 결론: 지금 화면에서는 **crop이 격자 검출로 나온 것인지, 행 검출로 나온 것인지, 정규화 템플릿 폴백인지 사용자가 구분할 방법이 없고**, 어느 소스든 빨간 박스 없이 잘려서 보이므로 "이 crop 경계가 실제로 어디를 겨냥했는지"조차 클릭 한 번 더 하지 않으면 확인할 수 없다. 이게 사용자가 지적한 "잘린 부분이 맞는 부분을 제대로 인식하고 있는지 파악할 수 있게" 요구사항의 정확한 원인이다.

### 10.3 작업지시서 (Codex에 위임)

**중요한 범위 결정**: 이번 라운드는 격자/행 검출의 임계값을 또 조정하지 **않는다**. §3.1~§9까지 이미 여러 차례 "로컬/합성 샘플에서 확인됨 → 실사용 데이터에서 재현 안 됨"이 반복됐다(이번 §10이 그 최신 사례). 근거 없이 파라미터를 또 건드리면 같은 패턴이 반복될 뿐이다. 대신 **다음 재테스트에서 실제로 무슨 일이 일어나는지 사용자가 직접 확인할 수 있는 진단 정보를 추가**하는 것을 이번 라운드의 유일한 목표로 한다.

1. **각 필드에 crop 출처(provenance)를 명시적으로 기록한다.**
   - `src/lib/recognition/detectCheckmarks.ts`에서 `recognitionCropRects`를 채울 때, 각 필드가 격자 검출(`'grid'`)·행 검출(`'row'`)·정규화 템플릿 폴백(`'fixed'`) 중 무엇으로 결정됐는지 함께 기록한다. 예: `RecognitionDraft`에 `recognitionCropSource?: Record<string, 'grid' | 'row' | 'fixed'>` 필드를 추가하고, CAGI/만족도 각 그룹 처리 루프에서 `gridCells`가 있으면 `'grid'`, 없고 `cagiRowOverrides[group.field]`(또는 만족도 쪽)가 있으면 `'row'`, 둘 다 없으면 `'fixed'`로 기록한다.
   - `analyzeChoiceGroup`이 실제로 어떤 좌표를 썼는지(row override 사용 여부)는 이미 `markDensity.ts` 호출부에서 알 수 있는 정보이므로, 그 판단을 다시 계산하지 말고 호출 시점의 인자로부터 그대로 도출할 것 — 별도의 재계산/재검출 로직을 새로 만들지 않는다(안전 원칙: 새 코드가 새로운 검출 시도를 하지 않고 기존 판단 결과를 기록만 하도록 최소화).

2. **`recognitionCropSource`를 검수 화면 응답에 실어 보낸다.**
   - `src/lib/recognition/buildSourcePreview.ts`와 `src/app/api/recognize/route.ts`가 `recognitionCropSource`를 `draft.source`(또는 draft 최상위)에 포함해 프론트엔드까지 전달하도록 배선한다.

3. **검수 화면에서 크롭 출처와 ROI 경계를 클릭 없이 바로 보여준다.**
   - `src/components/RecognitionReview.tsx`의 `renderFieldCropPreview`가 기본으로 보여주는 이미지를 **디버그 오버레이가 있는 버전**(`cropDebugDataUrls`, 빨간 ROI 박스 + 중심선 포함)으로 바꾼다. "ROI 확인" 링크는 그대로 두되(새 탭에서 원본 배율로 크게 보는 용도로는 여전히 유용하다), 카드 자체에 이미 경계가 보이게 한다.
   - 각 crop 카드에 `recognitionCropSource[field]` 값을 작은 배지로 표시한다(예: "격자 검출" / "행 검출" / "고정 좌표"). 색상은 기존 confidence 배지와 겹치지 않게 회색 계열로 충분하다.
   - 이 변경은 표시 방식만 바꾸는 것이므로 인식 로직·자동 확정 안전장치(§4, §9.2)는 전혀 건드리지 않는다.

4. **PDF 배치 스캔 페이지의 해상도/DPI가 격자 검출 허용오차 상수와 실제로 맞는지 점검한다.**
   - §9.6이 "낮은 DPI 경고는... 별개"라고 결론지었지만, 이번 §10.1 재현은 정확히 PDF 일괄 스캔 입력에서 나왔다. `tableGridDetection.ts`의 `xTolerance`/`yTolerance`(각각 `baseWidth * 0.035`, `baseHeight * 0.03`)와 `detectHorizontalLines`/`detectVerticalLines`의 `darkThreshold`/`minDarkRatio` 상수가, 로컬 테스트 픽스처(주로 어떤 해상도로 만들어졌는지)와 실제 PDF 렌더링 해상도(현재 PDF→이미지 변환 스케일/DPI 설정) 사이에 크게 다른 픽셀 스케일을 가정하고 있지 않은지 코드 읽기로 확인하고, 있다면 그 사실만 보고한다(파라미터를 바로 고치지 말고, 무엇이 왜 다른지 §10에 추가로 기록할 것 — 위 "중요한 범위 결정" 원칙 참고).

5. **테스트**: 기존 전체 테스트(회귀 없이 통과)에 더해, `recognitionCropSource`가 grid/row/fixed 각 케이스에서 올바르게 기록되는지 확인하는 단위 테스트를 `tests/table-grid-detection.test.ts` 또는 `tests/recognition-mark-density.test.ts`에 추가한다. `npm test`, `npm run build` 결과를 보고할 것.

이 작업이 끝나면, 사용자가 같은 19쌍 PDF로 다시 검수 화면을 열었을 때 각 필드 crop에 빨간 ROI 박스와 "격자/행/고정" 배지가 바로 보여야 한다. **다음 단계(임계값 조정 여부 포함)는 이 배지가 실제로 무엇을 보여주는지 확인한 뒤에 결정한다.**

### 10.5 다음 작업을 위한 피드백

- 사용자가 같은(또는 동등한) 19쌍 배치 스캔으로 재검수해, 각 필드에 실제로 어떤 배지("격자 검출"/"행 검출"/"고정 좌표")가 붙는지 확인해야 한다. 이 결과가 다음 라운드의 방향을 결정한다 — 대부분 "고정 좌표"라면 격자/행 검출 자체가 실사용 조건에서 거의 발동하지 않는다는 뜻이고, "격자 검출"인데도 잘못된 위치라면 매칭 로직 자체의 정확성 문제다.
- 10.4에서 기록한 "8px 하한 vs 축소 재시도" 가설은 다음 라운드에서 검증할 후보 원인 중 하나로 남긴다 — 배지 데이터로 실제 어느 케이스가 우세한지 먼저 확인한 뒤 착수한다.
- 여전히 기본정보(연령대 숫자 OCR, 학교유형/학년 격자 등록)는 이번 범위 밖이며 §2.2·§9.1·§10.1에서 계속 미해결로 남아있다.
