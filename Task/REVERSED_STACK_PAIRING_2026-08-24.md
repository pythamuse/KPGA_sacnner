# 역순 묶음 짝짓기 — 배경과 구현 계획 (2026-08-24)

## 배경

한 학생은 **선별검사지(앞면) 1장 + 만족도조사(뒷면) 1장**으로 구성된다. 19명이면 앞면 묶음
19장, 뒷면 묶음 19장이다.

연속 급지(ADF) 스캐너로 앞면 묶음을 스캔하면 1, 2, 3 … 19 순서로 나온다. 그런데 **그 뭉치를
그대로 뒤집어 뒷면을 스캔하면 물리적으로 19, 18, 17 … 1 순서**가 된다. 지금은 사용자가 매번
손으로 한 장씩 넘겨 되돌린다. **이 기능은 그 수동 단계를 없애는 것이 목적이다.**

## 지금까지는 사람이 손으로 되돌려 왔다

**현재 산출물은 오염되어 있지 않다.** 사용자가 스캔 후 뒷면 묶음을 손으로 한 장씩 넘겨
정순으로 되돌린 뒤 업로드해 왔다. 짝짓기는 그 전제 위에서 올바르게 동작한다.

> **초안은 이 절을 "조용한 오염"이라고 썼다. 틀렸다.** 시스템이 역순을 받지 못한다는 사실에서
> 역순이 실제로 업로드되고 있다고 넘겨짚었다. 사용자는 그 앞단에서 이미 막고 있었다.

**없애려는 것은 그 수동 단계다.** 열아홉 장을 손으로 뒤집는 일은 반복 작업이고,
**두 장이 한꺼번에 넘어가면 순서가 어긋난다.**

## 그리고 수동 단계의 실패만 검출되지 않는다

순서가 틀어지는 두 경로는 검출 여부가 다르다.

| 어디서 | 결과 | 검출되는가 |
|---|---|---|
| **스캔 중 겹침 급지** | 한 장이 통째로 빠진다 (19장 대 18장) | **된다.** `/api/recognize`의 장수 검사에 걸린다 |
| **손으로 되돌릴 때 두 장이 함께** | 열아홉 장 다 있는데 **두 장이 서로 바뀐다** | **안 된다** |

두 번째가 검출되지 않는 이유는 짝짓기가 순서만 믿기 때문이다.
[batchMatcher.ts](../src/lib/recognition/batchMatcher.ts)는 양쪽을 정렬해 **i번째끼리** 붙이고,
두 양식은 **식별 필드를 하나도 공유하지 않는다** — 기본정보(연령대·성별·학교유형·학년)는
선별검사지에만 있고 만족도에는 문항1~10뿐이다. 그래서 두 학생의 만족도가 서로 바뀌어도
장수도 맞고 양식 분류도 통과하며, **검수자가 두 원본 이미지를 나란히 봐도 누구 것인지
알 방법이 없다.**

**즉 이 기능은 검출되지 않는 유일한 순서 실패 경로를 제거한다.** 수동 단계가 사라지면
거기서 나올 수 있던 뒤바뀜도 함께 사라진다.

## 사이클 1 — 설계 (2026-08-24)

### 1.1 검토한 방식

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 명시적 역순 지정** | 뒷면 묶음이 역순임을 사용자가 지정 | **채택.** 보고된 작업 흐름에 정확히 대응하고 오탐이 없다 |
| **B. 자동 감지** | 앞뒷면을 내용으로 짝지어 역순을 스스로 판단 | **기각** (§1.2) |
| **C. 썸네일 재배열 UI** | 임의 순서를 손으로 맞춘다 | **보류.** 전 묶음 역전이라는 실제 문제에 과하다. 임의 뒤섞임이 실제로 보고되면 그때 |

### 1.2 B(자동 감지)를 기각하는 이유 — 다시 열려면 새 증거가 필요하다

**두 양식을 잇는 신호가 없다.**

- 공통 식별 필드가 없다. 기본정보는 선별검사지에만 있다
- 이름·연락처는 선별검사지의 **조기개입 서비스 영역**에만 나타나고, 이 제품은 개인정보를
  저장하지 않는 것을 전제로 설계돼 있다. 짝짓기에 쓰려면 그것을 읽어야 하므로 **설계 원칙과
  충돌한다.** 성능 문제가 아니라 방향의 문제다
- 물리적 단서(접힌 모서리, 스테이플 자국, 잉크 배어남)는 양면이 같은 종이일 때 원리적으로는
  신호가 되지만, 볼펜에서는 배어남이 거의 없고 종이 결함은 매 묶음 다르다. **v1의 근거로 삼기에
  너무 약하다**

기각을 뒤집으려면 *"이 신호가 19명에서 몇 번 맞았다"* 는 측정치가 필요하다.

### 1.3 어디서 뒤집는가 — 두 방식

순서를 바로잡을 수 있는 지점은 둘이고, 둘 다 목적을 달성한다.

| | **A. 짝을 지을 때 뒤집는다** | **B. 올릴 때 페이지 번호를 뒤집어 저장한다** |
|---|---|---|
| 아는 곳 | 짝짓기 + 표시 **두 곳** | 분할기 **한 곳**. 이후 계층은 순서를 몰라도 된다 |
| 저장물 | 원본 PDF와 **1:1로 유지**. `satisfaction_page_007`이 원본 7쪽이다 | `satisfaction_page_001`이 원본 19쪽이 된다 |
| 원본 이미지 표시 · 디버그 오버레이 · `materializeUploadBatch` 무결성 검사 | 전부 소스 기준으로 참 | 전부 재번호 기준. *"만족도 PDF 7쪽을 봐라"* 가 통하지 않는다 |
| **설정을 잘못 골랐을 때** | 설정만 바꿔 **다시 인식.** 재업로드 없음 | **19장을 다시 올려야 한다** |

**A를 채택한다.** 결정적인 것은 마지막 줄이다. 이 작업의 목적이 사람의 실수를 없애는 것인데,
**설정 자체도 잘못 고를 수 있다.** A에서는 그것이 클릭 한 번이고 B에서는 업로드를 다시 한다.
수동 단계를 없애려다 더 비싼 되돌리기를 만들면 이득이 줄어든다.

B의 장점(순서를 아는 곳이 하나)은 실재하지만, 그 대가로 **저장물이 원본과 어긋난다.** 이
프로젝트는 측정과 디버깅을 원본 페이지 번호로 해왔고([[CLAUDE.md]] §3의 `p3`·`p5`·`p12` 표기가
전부 그것이다), 그 대응이 깨지면 지금까지의 기록이 읽기 어려워진다.

> 사용자가 **PDF 자체를 뒤집어서 올리는** 세 번째 방식도 있다. 그러나 그것은 수동 단계를
> 종이에서 파일로 옮길 뿐 없애지 못하므로, 이 작업의 목적과 어긋난다.

```ts
export type StackOrder = 'same' | 'reversed';

export function matchBatch(
  cagiPaths: string[],
  satisfactionPaths: string[],
  satisfactionOrder: StackOrder = 'same',
): MatchPair[]
```

`satisfactionOrder === 'reversed'`이면 정렬된 뒷면 배열을 뒤집어 짝짓는다.
기본값 `'same'`이 지금 동작이므로 **호출부를 고치지 않으면 아무것도 변하지 않는다.**

> 앞면 묶음이 뒤집히는 경우(뭉치를 엎어 급지)도 원리적으로 가능하다. 지금은 보고된 적이
> 없으므로 뒷면 쪽만 넣되, 같은 모양으로 `cagiOrder`를 더할 수 있게 시그니처를 잡는다.

### 1.4 단계

**1단계 — 뒤집기 자체 (핵심)**

- `matchBatch`에 `satisfactionOrder` 인자 추가. 기본값은 현재 동작
- `/api/recognize`가 요청 본문에서 `satisfactionOrder`를 받아 **`'same' | 'reversed'`로 검증**한
  뒤 넘긴다. 검증 실패는 400 (`INVALID_STACK_ORDER`)
- [ImageUploadPanel.tsx](../src/components/ImageUploadPanel.tsx)의 2단계 업로드 칸에 선택
  컨트롤을 두고 인식 요청에 실어 보낸다
- 문구는 원인을 말한다: *"연속 급지로 스캔해 뒤집힌 순서 그대로입니다 (19 → 1)"*

**2단계 — 잘못 고른 것이 보이게 (안전망)**

1단계만으로는 **빠뜨리면 여전히 조용히 틀린다.** 그래서 인식 시작 전에 실제 짝을 보여준다.

```
1번 학생 = 선별검사지 1장 + 만족도조사 19장
19번 학생 = 선별검사지 19장 + 만족도조사 1장
```

처음과 끝만 보여도 역순 여부가 한눈에 드러난다. 검수 화면의 원본 이미지 탭에도 **몇 번째
장인지**를 표시한다.

**3단계 — 되돌리기 (복구)**

사용자는 대개 **검수 중에** 알아차린다. 그때 19장을 다시 올리게 하면 안 된다. 업로드 산출물은
서버에 남아 있으므로 **"뒷면 순서를 반대로 하고 다시 인식"** 을 붙인다. 재업로드 없이
`matchBatch`만 다시 부르고 인식을 재실행한다.

> 검수하던 값이 날아가므로 확인을 받는다. 3단계는 1·2단계가 병합된 뒤에 별도 사이클로 한다.

### 1.5 테스트 계획

**새 스캔이 필요 없다.** 지금 표본으로 왕복 항등식을 만들 수 있다.

| | 검증 |
|---|---|
| **단위** | `matchBatch(c, s, 'reversed')`가 `(c[i], s[n-1-i])`를 짝짓는다. 길이 불일치는 여전히 던진다. 기본 인자에서 기존 동작과 동일 |
| **★ 왕복 항등** | **뒷면 PDF의 페이지를 뒤집어** 올리고 `'reversed'`로 인식한 결과가, 원본 뒷면을 `'same'`으로 인식한 결과와 **칸 단위로 같아야 한다.** 같지 않으면 뒤집기가 짝짓기 말고 다른 것도 건드린 것이다 |
| **회귀** | `satisfactionOrder`를 주지 않은 기존 경로가 `CORRECT 354/432 · WRONG 7`을 그대로 낸다 |
| **브라우저** | [[CLAUDE.md]] §5.2 절차로 19명. 판정은 **확인 필요 135 · 자동 입력 302 · 오답 10 무변동**이다. 이 기능은 인식을 건드리지 않으므로 **숫자가 움직이면 그 자체가 실패다** |

왕복 항등 시험은 [tests/scan-repeat-measure.test.ts](../tests/scan-repeat-measure.test.ts)의 비교
로직을 그대로 쓸 수 있다 — 두 실행의 자동 입력값을 칸 단위로 대조하는 것이 같은 일이다.

### 1.6 하지 않을 것

- **자동 감지를 넣지 않는다** (§1.2)
- **개인정보를 짝짓기에 쓰지 않는다.** 이름이 읽히더라도 쓰지 않는다
- **인식 로직을 건드리지 않는다.** 이 작업의 정답은 인식 숫자가 **하나도 안 움직이는 것**이다
- **업로드 저장물의 페이지 번호를 바꾸지 않는다** — B가 아니라 A를 고른 결과다 (§1.3)

### 2.2 테스트 결과

**단위** — 전체 스위트 129개 통과(실스캔 2개는 환경변수 없어 skip).

**실제 역순 스캔** — 사용자가 같은 용지를 세 번 스캔해 주었고 **3세트의 뒷면은 일부러 역순으로**
스캔했다. 재스캔 하니스가 이제 **production `matchBatch`를 직접 호출**하므로 복사본이 아니라
실제 경로를 시험한다.

```
run A (뒷면 정순)   자동 361  CORRECT 354  WRONG 7  빈칸 침범 0
run B (뒷면 정순)   자동 344  CORRECT 336  WRONG 8  빈칸 침범 3
run C (뒷면 역순)   자동 342  CORRECT 339  WRONG 3  빈칸 침범 0
```

**C가 통과한다.** 짝짓기가 틀렸다면 만족도 열 문항이 통째로 남의 것이 되어 정답표와 어긋난
칸이 수십으로 튀어야 한다. **3이다.**

> **세 실행의 수치를 서로 비교하지 마라.** A·B·C는 서로 다른 스캔이고, 그 사이의 차이는
> 순서와 무관한 이유로 생긴다(§21의 잡음 바닥 76칸). *"C의 3이 A의 7보다 낫다"* 는 식으로
> 읽으면 안 된다 — 초안이 그렇게 적고 있었다.

**브라우저** — dev에서 19장씩 올려 컨트롤을 눈으로 확인했다. `aria-pressed`가 선택을 따르고,
역순을 고르면 짝 표시가 뒤집힌다.

```
같은 순서: 1번 학생 = 선별검사지 1장 + 만족도조사 1장  · 19번 학생 = … 19장 + … 19장
역순:      1번 학생 = 선별검사지 1장 + 만족도조사 19장 · 19번 학생 = … 19장 + … 1장
```

## 사이클 3 — 만족도 기준 2×3 전수 검증 (2026-08-24)

### 3.1 사이클 2의 논증은 절반이었다

사이클 2는 역순 세트를 `reversed`로 돌려 `CORRECT 339 / WRONG 3`을 얻고 통과라 했다.
**그것만으로는 부족하다** — 애초에 역순이 아닌 스캔도 좋은 점수를 낸다. 플래그가 실제로
일한다는 것을 보이려면 **정방향 세트를 엉뚱한 학생에게 붙이는 것까지** 보여야 한다.

그래서 만족도 세 세트 × 두 순서 설정의 **전수**를 쟀다. 통과 조건은 **대각선**이다.

통제한 것:

- **선별검사지는 1세트로 고정.** 앞면이 상수라 뒷면 짝짓기만 변수로 남는다
- **만족도 각 장은 한 번만 인식**하고, 그 장이 몇 번 학생 것인지는 `matchBatch`가 돌려준 짝이
  정한다 — 시험 대상인 산술이 실제로 개입한다
- **만족도 10개 필드만 채점.** 앞면이 섞이면 대비가 희석된다

### 3.2 결과 — 대각선이 나왔다

```
  세트                      order      auto  CORRECT  WRONG
  만족도 1 (기존, 정방향)      same       152      146      6
  만족도 1                   reversed   152      120     32
  만족도 2 (새 스캔, 정방향)    same       144      138      6
  만족도 2                   reversed   144      115     29
  만족도 3 (새 스캔, 역순)     same       141      121     20
  만족도 3                   reversed   141      138      3
```

```
세트        올바른 순서    틀린 순서
1세트       96.1%         78.9%
2세트       95.8%         79.9%
3세트       97.9%         85.8%
```

**세 세트 모두 자기 실제 순서에서 제 학생에게 붙고, 반대 설정에서 어긋난다.**

> **행 안에서만 비교한다.** 세 세트는 서로 다른 스캔이므로 96.1% 대 97.9%처럼 행을 가로질러
> 비교하면 순서와 무관한 인식 차이를 기능의 성과로 읽게 된다.

### 3.3 틀린 순서에서도 79%가 맞는 이유

정답표로 만족도 10개 필드의 학생 구분력을 쟀다.

```
전체 171쌍
  값이 완전히 같은 쌍   30    {p1,p4,p6,p7,p10,p11,p13,p17} 여덟 명이 서로 전부 동일
  차이 분포            0:30  1:54  2:32  3:15  4:27  5:11  6:2
  임의의 두 학생이 같은 답을 낼 확률   80.2%
```

**틀린 순서의 점수 78.9% / 79.9% / 85.8%는 그 80.2%와 같은 값이다.** 즉 잘못 짝지었을 때의
점수는 "부분적으로 맞은 것"이 아니라 **무작위 재짝짓기의 기대값 그 자체**다. 대비가 96% 대
80%로 좁아 보이는 것은 기능이 약해서가 아니라 **학생들의 만족도 응답이 서로 많이 겹치기 때문**이다.

### 3.4 그리고 이것이 §1의 위험을 다시 확인해준다

전 묶음 역전은 이렇게 20%p 차이로 드러나지만, **두 장만 뒤바뀌면 거의 보이지 않는다** —
어차피 임의의 두 학생이 80% 겹치므로, 두 장 교환은 기껏해야 서너 칸을 움직인다.
[[WEAK_SIGNAL_STABILITY_PLAN_2026-08-24]] §21이 잰 잡음 바닥이 76칸이라는 것과 겹쳐 놓으면,
**부분적 순서 오류는 계측으로 잡을 수 없다.** 수동 단계를 없애는 것이 유일한 방어라는
§1의 결론이 여기서 숫자로 확인된다.

### 3.6 ★ 이 표는 인식률이 아니다 — 초안이 그렇게 읽히게 썼다

사용자가 지적했다: *"역순이 결과를 나쁘게 만든다는 전제가 틀렸다. 매칭되는 세트가 달라질 뿐,
인식률에 도움도 방해도 되지 않는다."* **맞다.**

`recognizeStudentForms(cagiPath, satPath)`는 **그 장의 파일만 본다.** 한 장의 인식 결과는
그 장이 몇 번 학생에게 붙든 동일하다. 순서는 **어느 정답표 행과 대조되는가**만 바꾼다.

그런데 초안은 그 수를 `CORRECT`/`WRONG`이라 부르고 %로 적어 **인식 성능처럼 보이게** 했다.
특히 *"3세트 97.9%가 기준선 96.1%보다 높다"* 는 **서로 다른 스캔의 인식 차이를 기능의 성과로**
적은 것이다. 열 이름을 `agrees`/`disagrees`로 바꾸고, 행을 가로지르는 비교를 금지하는 문장을
출력에 넣었다.

**측정 자체는 유효하다.** 재는 것이 *"i번 학생에게 붙은 장이 정답표 i행과 맞는가"* 이므로
**짝짓기가 맞았는지**를 정확히 잰다. 잘못된 것은 이름과 해석이었다.

**그리고 이 기능의 목적도 다시 적어둔다** — 인식 개선이 아니라 **손으로 열아홉 장을 뒤집는
수동 단계와 거기서 나오는 휴먼 에러를 없애는 것**이다. §1과 §3.4가 그것을 말하고 있고,
이 표는 그 기능이 의도대로 짝을 짓는다는 확인일 뿐이다.
