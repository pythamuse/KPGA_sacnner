# 역순 묶음 짝짓기 — 배경과 구현 계획 (2026-08-24)

## 배경

한 학생은 **선별검사지(앞면) 1장 + 만족도조사(뒷면) 1장**으로 구성된다. 19명이면 앞면 묶음
19장, 뒷면 묶음 19장이다.

연속 급지(ADF) 스캐너로 앞면 묶음을 스캔하면 1, 2, 3 … 19 순서로 나온다. 그런데 **그 뭉치를
그대로 뒤집어 뒷면을 스캔하면 물리적으로 19, 18, 17 … 1 순서**가 된다. 사용자가 매번 손으로
다시 정렬해야 하고, 그 정렬을 빠뜨리면 잘못된 결과가 나온다.

## 이것은 편의 기능이 아니라 조용한 오염이다

현재 짝짓기는 [batchMatcher.ts](../src/lib/recognition/batchMatcher.ts) 한 곳에서 일어난다.

```ts
const sortedCagi = [...cagiPaths].sort(naturalSort);
const sortedSat = [...satisfactionPaths].sort(naturalSort);
for (let i = 0; i < sortedCagi.length; i++) {
  pairs.push({ cagiPath: sortedCagi[i], satisfactionPath: sortedSat[i] });
}
```

**i번째끼리 붙인다.** 뒷면이 역순이면 1번 학생의 선별검사지에 19번 학생의 만족도가 붙고,
그것이 19명 전원에게 일어난다.

그리고 **어디에서도 걸리지 않는다.**

- 장수는 맞으므로 `/api/recognize`의 개수 검사(19 = 19)를 통과한다
- 양쪽 다 정상 양식이므로 양식 분류기(`classifyForm`)도 통과한다
- 두 양식은 **공통 식별 필드를 하나도 공유하지 않는다** — 기본정보(연령대·성별·학교유형·학년)는
  선별검사지에만 있고 만족도에는 문항1~10뿐이다. 검수자가 두 원본 이미지를 나란히 봐도
  **어느 학생 것인지 알 방법이 없다**

인식 오답은 한 칸이 틀리고 검수자가 잡을 수 있지만, 이 실패는 **19명 전원의 만족도 응답이
통째로 남의 것이 되고 아무도 모른 채 중앙 시스템에 올라간다.** 심각도가 다르다.

## 사이클 1 — 설계 (2026-08-24)

### 1.1 검토한 방식

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 명시적 역순 지정** | 뒷면 묶음이 역순임을 사용자가 지정 | **채택.** 보고된 작업 흐름에 정확히 대응하고 오탐이 없다 |
| **B. 자동 감지** | 앞뒷면을 내용으로 짝지어 역순을 스스로 판단 | **기각** (§1.2) |
| **C. 썸네일 재배열 UI** | 임의 순서를 손으로 맞춘다 | **보류.** 전 묶음 역전이라는 실제 문제에 과하다. 임의 뒤섞임이 실제로 보고되면 그때 |

### 1.2 B(자동 감지)를 기각하는 이유 — 다시 열려면 새 증거가 필요하다

**두 양식을 잇는 신호가 없다.**

- 공통 식별 필드가 없다. 기본정보는 선별검사지에만 있다
- 이름·연락처는 선별검사지의 **조기개입 서비스 영역**에만 나타나고, 이 제품은 개인정보를
  저장하지 않는 것을 전제로 설계돼 있다. 짝짓기에 쓰려면 그것을 읽어야 하므로 **설계 원칙과
  충돌한다.** 성능 문제가 아니라 방향의 문제다
- 물리적 단서(접힌 모서리, 스테이플 자국, 잉크 배어남)는 양면이 같은 종이일 때 원리적으로는
  신호가 되지만, 볼펜에서는 배어남이 거의 없고 종이 결함은 매 묶음 다르다. **v1의 근거로 삼기에
  너무 약하다**

기각을 뒤집으려면 *"이 신호가 19명에서 몇 번 맞았다"* 는 측정치가 필요하다.

### 1.3 채택안 — 어디에 넣는가

**짝짓기 시점에 넣는다. 업로드 시점이 아니다.**

업로드 단계에서 페이지 번호를 뒤집어 저장하는 방법도 있지만 그러면 **저장된 산출물이 원본
PDF와 어긋난다.** 원본 이미지 표시·디버그 오버레이·`materializeUploadBatch`의 무결성 검사가
모두 페이지 번호를 신뢰하므로, 저장물은 원본에 충실하게 두고 **짝을 지을 때만 뒤집는다.**

```ts
export type StackOrder = 'same' | 'reversed';

export function matchBatch(
  cagiPaths: string[],
  satisfactionPaths: string[],
  satisfactionOrder: StackOrder = 'same',
): MatchPair[]
```

`satisfactionOrder === 'reversed'`이면 정렬된 뒷면 배열을 뒤집어 짝짓는다.
기본값 `'same'`이 지금 동작이므로 **호출부를 고치지 않으면 아무것도 변하지 않는다.**

> 앞면 묶음이 뒤집히는 경우(뭉치를 엎어 급지)도 원리적으로 가능하다. 지금은 보고된 적이
> 없으므로 뒷면 쪽만 넣되, 같은 모양으로 `cagiOrder`를 더할 수 있게 시그니처를 잡는다.

### 1.4 단계

**1단계 — 뒤집기 자체 (핵심)**

- `matchBatch`에 `satisfactionOrder` 인자 추가. 기본값은 현재 동작
- `/api/recognize`가 요청 본문에서 `satisfactionOrder`를 받아 **`'same' | 'reversed'`로 검증**한
  뒤 넘긴다. 검증 실패는 400 (`INVALID_STACK_ORDER`)
- [ImageUploadPanel.tsx](../src/components/ImageUploadPanel.tsx)의 2단계 업로드 칸에 선택
  컨트롤을 두고 인식 요청에 실어 보낸다
- 문구는 원인을 말한다: *"연속 급지로 스캔해 뒤집힌 순서 그대로입니다 (19 → 1)"*

**2단계 — 잘못 고른 것이 보이게 (안전망)**

1단계만으로는 **빠뜨리면 여전히 조용히 틀린다.** 그래서 인식 시작 전에 실제 짝을 보여준다.

```
1번 학생 = 선별검사지 1장 + 만족도조사 19장
19번 학생 = 선별검사지 19장 + 만족도조사 1장
```

처음과 끝만 보여도 역순 여부가 한눈에 드러난다. 검수 화면의 원본 이미지 탭에도 **몇 번째
장인지**를 표시한다.

**3단계 — 되돌리기 (복구)**

사용자는 대개 **검수 중에** 알아차린다. 그때 19장을 다시 올리게 하면 안 된다. 업로드 산출물은
서버에 남아 있으므로 **"뒷면 순서를 반대로 하고 다시 인식"** 을 붙인다. 재업로드 없이
`matchBatch`만 다시 부르고 인식을 재실행한다.

> 검수하던 값이 날아가므로 확인을 받는다. 3단계는 1·2단계가 병합된 뒤에 별도 사이클로 한다.

### 1.5 테스트 계획

**새 스캔이 필요 없다.** 지금 표본으로 왕복 항등식을 만들 수 있다.

| | 검증 |
|---|---|
| **단위** | `matchBatch(c, s, 'reversed')`가 `(c[i], s[n-1-i])`를 짝짓는다. 길이 불일치는 여전히 던진다. 기본 인자에서 기존 동작과 동일 |
| **★ 왕복 항등** | **뒷면 PDF의 페이지를 뒤집어** 올리고 `'reversed'`로 인식한 결과가, 원본 뒷면을 `'same'`으로 인식한 결과와 **칸 단위로 같아야 한다.** 같지 않으면 뒤집기가 짝짓기 말고 다른 것도 건드린 것이다 |
| **회귀** | `satisfactionOrder`를 주지 않은 기존 경로가 `CORRECT 354/432 · WRONG 7`을 그대로 낸다 |
| **브라우저** | [[CLAUDE.md]] §5.2 절차로 19명. 판정은 **확인 필요 135 · 자동 입력 302 · 오답 10 무변동**이다. 이 기능은 인식을 건드리지 않으므로 **숫자가 움직이면 그 자체가 실패다** |

왕복 항등 시험은 [tests/scan-repeat-measure.test.ts](../tests/scan-repeat-measure.test.ts)의 비교
로직을 그대로 쓸 수 있다 — 두 실행의 자동 입력값을 칸 단위로 대조하는 것이 같은 일이다.

### 1.6 하지 않을 것

- **자동 감지를 넣지 않는다** (§1.2)
- **개인정보를 짝짓기에 쓰지 않는다.** 이름이 읽히더라도 쓰지 않는다
- **인식 로직을 건드리지 않는다.** 이 작업의 정답은 인식 숫자가 **하나도 안 움직이는 것**이다
- **업로드 저장물의 페이지 번호를 바꾸지 않는다** (§1.3)

### 1.7 다음 작업을 위한 피드백

- 1·2단계를 한 묶음으로 구현한다. **1단계만 병합하면 빠뜨림에 대한 방어가 없다**
- 3단계(재인식)는 인식 재실행 비용과 검수 상태 소실을 다뤄야 하므로 별도 사이클
- 앞면 역순은 아직 관측되지 않았다. 관측되면 §1.3의 시그니처로 대칭 확장
