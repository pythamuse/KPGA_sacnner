# 인식 아키텍처 전면 재검토 (2026-08-10)

> 이 문서는 [[COORDINATE_REGISTRATION_AND_RESPONSE_PRIOR_PLAN]]에서 §9~§12에 걸쳐 반복된
> "진단 추가 → 재테스트 → 또 진단 추가" 루프를 중단하고, 설계 자체를 다시 보기 위해
> 작성한다. 사용자의 지적("계속 같은 테스트만 반복하고 해결이 안 되고 있는데, 설계 방법부터
> 전면 재검토할 것")에 따른 것이며, 그 지적은 정확하다.

## 1. 지금까지 무엇을 반복했는가 (솔직한 자기평가)

| 라운드 | 한 일 | 결과 |
|---|---|---|
| §9 | 격자 검출 도입, "로컬 샘플에서 확인됨" | 실사용 재현 실패 |
| §10 | crop 출처 배지 추가(격자/행/고정) | 진단 정보만 늘음 |
| §11 | 실패 사유 분류 추가(lines_undetected/insufficient/gap_mismatch) | 진단 정보만 늘음 |
| §12 | 실패 편차 수치화(최대 편차 %) | 진단 정보만 늘음 |

**§10~§12는 전부 "진단을 더 자세히 보여주기"였고, 실제 인식은 한 번도 개선되지 않았다.** 매번 "근거 없이 임계값을 조정하지 않겠다"는 이유로 진단만 추가했는데, 결과적으로 세 라운드를 진단에만 쓰고 정작 근본 원인은 건드리지 않았다. 이건 신중함이 아니라 회피였다.

## 2. 이번 실측이 드디어 밝혀낸 것

§12에서 추가한 편차 수치가 이번 스크린샷에 실제로 찍혔다:

| 필드군 | 진단 |
|---|---|
| CAGI 08~09 | `격자: gap_mismatch (최대 편차 33% (허용 18%))`, `행: 픽셀 gap_mismatch (최대 편차 46% (허용 35%))` |
| 만족도 문항2 | `격자: gap_mismatch (최대 편차 40% (허용 35%))` |
| 만족도 문항3~6 | `격자: gap_mismatch (최대 편차 48% (허용 35%))` |
| 만족도 문항1 | `격자: insufficient_lines (가로선 3/2개, 세로선 4/5개)` |

편차가 33~48%다. **임계값을 조금 넓혀서 될 문제가 아니고, 그렇다고 "완전히 딴 곳을 보고 있다"고 하기엔 또 애매한 크기다.** 이 어정쩡한 크기가 결정적 단서였다.

`roiTemplates.ts`의 좌표를 직접 계산해봤다:

```
만족도 q02~06 (예/아니오 5행) 템플릿 행 간격: [0.048, 0.048, 0.035, 0.035]
                              → 상대 비율: [1, 1, 0.729, 0.729]

CAGI q01~07 템플릿 행 간격 상대 비율: [1, 1.042, 0.75, 0.75, 0.708, 0.792]
```

**템플릿은 "이 표의 행 간격이 1:1:0.73:0.73으로 들쭉날쭉하다"고 주장하고 있다.** 그런데 인쇄된 표의 같은 유형 응답 행(예/아니오 5행)은 거의 항상 **균등 간격**이다. 실제 폼의 행이 균등하다고 가정하고 계산하면:

```
실제(균등 [1,1,1,1]) vs 템플릿([1,1,0.729,0.729]) → 최대 편차 37%
실측 보고값: 40~48%
```

**거의 일치한다.** 즉 검출기는 실제 표의 행을 제대로 찾고 있는데, 그것을 **틀린 템플릿 패턴과 대조해서 "불일치"로 기각**하고 있는 것이다.

## 3. 근본 설계 결함

현재 구조:

```
1. 페이지 경계 추정
2. 템플릿의 고정 비율 좌표를 그 경계에 매핑
3. 이미지에서 실제 격자선 검출
4. 검출된 선의 간격 패턴을 ★템플릿의 간격 패턴과 대조★
5. 일치하면 검출 좌표 사용, 불일치하면 템플릿 좌표로 폴백
```

**4번이 자기모순이다.** 검출의 목적은 "템플릿 좌표가 못 미더우니 실제 이미지에서 찾자"인데, 그 검출 결과를 검증하는 기준이 다시 템플릿이다. 템플릿이 틀렸을 때:

- 검출이 **맞으면** → 템플릿과 안 맞으므로 **기각** → 틀린 템플릿 좌표로 폴백 (지금 상황)
- 검출이 **틀렸는데 우연히 템플릿과 비슷하면** → **채택** (CAGI 01~07이 "성공"으로 뜨지만 신뢰도가 계속 낮은 이유일 가능성)

즉 이 구조에서는 **템플릿이 정확할 때만 검출이 작동하는데, 템플릿이 정확하다면 애초에 검출이 필요 없다.** 지난 세 라운드에서 진단을 아무리 정교하게 만들어도 인식이 안 고쳐진 이유가 이것이다.

덧붙여 `roiTemplates.ts`의 좌표 출처를 git 이력으로 확인해보니 최초 커밋 이후 딱 두 번 손봤고, 주석에는 "공식 A4 양식의 인쇄 표 기하학에 맞춰 보정됨"이라고 적혀 있지만 **실제 빈 양식 파일을 측정한 기록은 이 저장소 어디에도 없다.** 참고 이미지 한 장을 보고 눈대중으로 넣은 값이 계속 "정답" 역할을 해온 셈이다.

## 4. 재설계 방향

핵심 원칙: **이미지가 진실이고, 템플릿은 스키마(개수)일 뿐 좌표가 아니다.**

템플릿이 제공해야 할 것과 제공하면 안 되는 것을 분리한다:

| 템플릿이 제공 (신뢰 가능) | 템플릿이 제공하면 안 됨 (지금 문제의 근원) |
|---|---|
| 이 표에 응답 행이 **몇 개**인가 (CAGI 1~7 = 7행) | 각 행이 페이지의 몇 % 지점인가 |
| 선택지가 **몇 개**인가 (4열) | 행 간 간격이 어떤 비율인가 |
| 대략 어느 **구역**을 볼 것인가 (넉넉한 검색 밴드) | 셀의 정확한 위치 |

검증 기준을 "템플릿 패턴과 일치하는가"에서 **"표 자체로서 말이 되는가"**로 바꾼다:

1. 검색 밴드 안에서 가로선·세로선을 검출한다.
2. **행 개수·열 개수가 스키마와 맞는지**만 본다(7행 4열).
3. 간격은 템플릿과 대조하지 않고, **검출된 행들끼리 서로 균등한지**(변동계수가 작은지)만 본다. 실제 인쇄된 표는 균등하다는 것이 신뢰할 수 있는 성질이고, 이건 이미지 내부에서 자기완결적으로 검증 가능하다.
4. 통과하면 검출된 실제 픽셀 셀을 사용한다. 실패하면 지금처럼 자동 확정 금지(폴백은 유지하되, 그건 "값을 채우지 않는다"는 뜻이지 "틀린 좌표로 채운다"가 아니어야 한다).

이렇게 하면 템플릿 좌표가 부정확해도 **검출이 옳으면 옳은 답이 나온다.** 템플릿은 "몇 행 몇 열짜리 표를 이 근처에서 찾아라"는 지시로만 쓰인다.

## 5. 병행할 별건: 폴백의 의미 재정의

현재 `'fixed'` 폴백은 **틀린 것으로 확인된 템플릿 좌표로 crop을 만들어 사용자에게 보여준다.** 사용자는 그 crop이 엉뚱한 곳을 가리키는 걸 보고 혼란스러워한다(§10.1부터 반복 지적된 증상). 격자 검출이 실패했다는 것은 "이 문항의 위치를 모른다"는 뜻이므로, 틀릴 수 있는 좁은 crop을 확신 있게 보여주는 대신 **해당 표 구역 전체를 넉넉히 보여주고 "위치 특정 실패"임을 명시**하는 편이 검수에 훨씬 유용하다.

## 6. 이번 라운드 범위 (§12까지의 실패를 반복하지 않기 위한 제한)

**진단 추가는 이번 라운드에 하지 않는다.** 실제 인식 로직을 바꾼다. 범위는 다음 두 가지로 한정한다:

1. 격자 검증 기준을 "템플릿 간격 패턴 대조" → "행/열 개수 일치 + 검출 행 간 균등성"으로 교체.
2. 격자 검출 실패 시 crop을 좁은 템플릿 좌표가 아니라 표 구역 전체로 넓히고 라벨을 명확히.

성공 판정 기준도 미리 정한다 — 다음 재테스트에서 **CAGI 08~09와 만족도 문항1~6의 배지가 "고정 좌표"에서 "격자 검출"로 바뀌어야 한다.** 안 바뀌면 이 재설계도 틀린 것이고, 그때는 임계값이 아니라 **실제 빈 양식 파일을 확보해 좌표를 실측하는 것**(§7)으로 넘어간다.

## 7. 이 방향도 실패할 경우의 Plan B

빈 CAGI/만족도 양식 원본(스캔이든 PDF든, 응답이 없는 깨끗한 1장)을 확보해 **좌표를 눈대중이 아니라 실측**한다. 지금까지 모든 문제의 뿌리가 "검증된 적 없는 템플릿 좌표"인데, 사용자가 실제 빈 양식을 한 장만 제공하면 이 불확실성 전체가 제거된다. 개인정보가 없는 빈 양식이므로 저장소에 넣어 회귀 테스트 고정 자산으로 쓸 수도 있다 — 지금까지 없었던, 가장 확실한 기준점이 된다.

## 8. 작업지시서 (Codex, Luna-Max)

**배경**: 위 §2~§3을 반드시 먼저 읽을 것. 요지는 "격자 검출이 실제 표를 제대로 찾고 있는데, 검증 기준인 템플릿 간격 패턴이 틀려서 정답을 기각하고 있다"는 것이다.

1. `src/lib/recognition/tableGridDetection.ts`의 검증 로직 교체:
   - 현재 `matchExpectedLines`(기대 좌표 근처에서 선을 찾음) + `hasConsistentGaps`(템플릿 간격 비율과 대조)로 검증한다. 이 중 **`hasConsistentGaps`의 "템플릿 간격 비율과 대조" 부분을 제거**하고, 대신 **검출된 행들끼리의 균등성 검사**로 대체한다: 인접 행 간격들의 변동계수(표준편차/평균)가 일정 값(예: 0.25) 이하이면 통과. 열도 동일하게 처리한다.
   - `matchExpectedLines`는 "대략 이 구역에서 찾는다"는 앵커 역할이므로 유지하되, 개수가 맞고 균등하면 채택하도록 한다. 기대 좌표에서 다소 벗어나도 개수·균등성이 맞으면 실제 검출 결과를 신뢰한다.
   - 스키마(행 수·열 수)는 기존 `TableGridSpec`의 `groups`에서 그대로 얻을 수 있다(그룹 수 = 행 수, `candidates.length` = 열 수).
2. `src/lib/recognition/tableRowDetection.ts`의 `matchRowPattern`도 같은 원칙으로: `expectedRelativeGaps`와의 대조 대신, 필요한 개수만큼의 연속된 선을 찾되 **그 선들이 서로 균등한지**로 판정하도록 교체한다.
3. **crop 폴백 개선**: 격자 검출이 실패해 `'fixed'`로 떨어진 필드는, 좁은 템플릿 ROI 대신 **해당 문항이 속한 표 구역 전체**(그 spec의 모든 group을 합친 범위 + 여유 패딩)를 crop으로 보여준다. 배지 문구도 `"고정 좌표"` → `"위치 특정 실패 (구역 전체 표시)"`로 바꾼다.
4. **자동 확정 안전장치는 그대로 유지한다** — 격자 검출 실패 시 값을 자동으로 채우지 않는 현재 동작(`allowAutoValue`)은 절대 완화하지 말 것. 이 재설계는 "더 많이 자동 확정하자"가 아니라 "위치를 제대로 찾자"이다.
5. 기존 테스트 중 템플릿 간격 패턴 대조에 의존하던 것들은 새 기준(개수+균등성)에 맞게 갱신하되, **"실패해야 하는 케이스는 여전히 실패하는지"**를 반드시 유지할 것(예: 빈 이미지, 선이 부족한 이미지, 명백히 균등하지 않은 무작위 선 배치). 균등성 검사가 아무거나 통과시키면 안 된다.
6. `npm test`, `npm run build` 통과 확인 후, `src/app/page.tsx`의 버전 마커를 규칙대로 갱신(README.md "작업 프로세스" 참고)하고 커밋·푸시.

보고 시: (a) 파일별 변경 내용, (b) 테스트/빌드 결과, (c) 균등성 임계값을 얼마로 정했고 왜 그 값인지, (d) 기존 테스트 중 기대값을 바꾼 것이 있다면 각각 왜 바꾸는 게 타당한지(단순히 통과시키려고 느슨하게 만든 것이 아님을 설명).

  즉 **§2에서 진단한 실제 프로덕션 실패 케이스가 이제 통과하면서, 노이즈는 여전히 거부된다** — 균등성 검사가 공허하지 않음을 실증했다. (검증 스크립트는 일회성이라 저장소에 남기지 않았다.)

## 10. 다음 작업을 위한 피드백

- **성공 기준은 §6에 미리 못박아둔 그대로다**: 같은 19쌍 배치로 재검수했을 때 **CAGI 08~09와 만족도 문항1~6의 배지가 "고정 좌표"에서 "격자 검출"로 바뀌어야 한다.** 위 합성 검증은 "로직이 의도대로 동작한다"까지만 증명하며, 실제 스캔 이미지에서 선이 충분히 검출되는지는 여전히 실측으로만 확인 가능하다.
- 바뀌지 않으면 이 재설계도 틀린 것이다. 그 경우 임계값을 만지지 말고 **§7의 Plan B(실제 빈 양식 확보 후 좌표 실측)로 즉시 이동한다.** 이번엔 그 판단 기준을 미리 정해뒀으므로 또 진단 라운드를 반복하지 않는다.
- 배지가 "격자 검출"로 바뀌었는데도 신뢰도가 계속 낮다면, 그건 위치 문제가 아니라 마킹 판별 문제이므로 [[COORDINATE_REGISTRATION_AND_RESPONSE_PRIOR_PLAN]] §4.2(인쇄 원문자와 수기 표시 분리)로 넘어간다 — 이건 좌표와 독립된 별개 과제다.
