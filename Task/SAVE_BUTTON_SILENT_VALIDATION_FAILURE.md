# "검수 완료 및 엑셀 반영" 무반응 + 높은 신뢰도 항목의 근거 은닉 (2026-08-10, v2026-08-10.6)

## 1. 증상

1. 모든 값을 채운 뒤 **"검수 완료 및 엑셀 반영" 버튼을 눌러도 아무 일도 일어나지 않는다.** 개발자도구 콘솔에는 `/api/students` **400** 이 두 번 기록돼 있다(버튼 두 번 클릭).
2. **CAGI 09가 크롭 이미지 없이 `높음`으로 판정**된다.

## 2. 원인 A — 저장은 실패하고 있고, 오류 메시지는 화면 밖에 그려진다

버튼은 정상 동작한다. `/api/students`가 **400 + 검증 오류 목록**을 반환하고, 클라이언트도 `setErrors(data.errors)`로 오류를 정상 수신한다. 문제는 **오류가 그려지는 위치**다.

`src/app/page.tsx`에서 `<ErrorSummary errors={errors} />`는 작업 영역 **맨 위**(검수 패널·안내문보다도 위)에 렌더링된다. 그런데 "검수 완료 및 엑셀 반영" 버튼은 22개 항목을 모두 지나온 **페이지 최하단**에 있다.

따라서 실제로 일어나는 일은:

1. 사용자가 최하단에서 저장 클릭
2. 서버 400 → 클라이언트가 오류 상태 설정
3. 오류 배너가 **한참 위 화면 밖에** 그려짐
4. 사용자 눈에는 **아무 반응 없음**

즉 "동작하지 않는" 게 아니라 **"실패했는데 실패했다고 말해주지 않는"** 것이다. 이번 세션에서 이미 한 번 겪은 유형이다 — [[CAMERA_UPLOAD_ROBUSTNESS_FIXES]]의 "촬영 버튼 무반응"도 예외가 조용히 삼켜져 피드백이 없던 사례였다.

### 무엇이 검증에 걸렸나

`validateStudent`는 기본정보 4개를 **모두 필수**로 요구한다:

| 필드 | 요구값 |
|---|---|
| `basic.age` | 1~20 정수 |
| `basic.gender` | 남 / 여 |
| `basic.schoolType` | 초등학교 / 중학교 / 고등학교 / 학교외기관 |
| `basic.grade` | 1~6학년 / 해당없음 |

스크린샷 기준 **연령대가 빈칸**이고(숫자 OCR이 채우지 못함), 학교유형·학년이 `선택 안 함` 상태였다. 이 항목들이 비어 있으면 100% 400이 난다. 사용자가 만족도 문항을 다 채워도, 기본정보가 비어 있으면 저장은 계속 막힌다.

## 3. 원인 B — 높은 신뢰도일수록 근거를 숨긴다

`RecognitionReview.tsx`의 `renderFieldCropPreview`는 첫 줄에서:

```ts
if (getConfidenceLevel(key) === 'high') return null;
```

즉 **`높음`으로 판정된 항목은 크롭 미리보기를 아예 표시하지 않는다.** CAGI 09에 이미지가 없는 이유다(점수 0/35%, 2/10%, 3/9% → best 0.35 ≥ 0.35, gap 0.25 ≥ 0.12 이므로 규칙상 `높음`이 맞다).

원래 의도는 "확실한 건 굳이 보여주지 않아 화면을 간결하게"였겠지만, **이 프로젝트 맥락에서는 정반대로 위험하다.** 이번 세션에서만 "높은 확신으로 엉뚱한 곳을 읽은" 사고가 두 번 있었다(만족도 q01이 다른 표를 가리킨 건, 두 줄짜리 항목이 한 줄로 붕괴된 건). **가장 확신할 때 검증 근거를 감추면 그 두 사고를 사용자가 발견할 방법이 없다.**

## 4. 작업지시서 (Codex, Luna-Max)

### A. 저장 실패를 사용자가 반드시 인지하게 (최우선)

1. 저장이 실패했을 때(`/api/students`가 `!res.ok`) **오류 배너로 화면을 스크롤**시킨다. `ErrorSummary`에 ref를 달고 `scrollIntoView({ behavior: 'smooth', block: 'center' })`를 호출하는 정도면 충분하다.
2. 그것만으로는 부족하므로, **저장 버튼 근처에도 실패 요약을 함께 표시**한다(예: 버튼 위에 "필수 항목 N개가 비어 있어 저장하지 못했습니다" + 해당 항목명 나열). 상단 배너는 그대로 두고 하단에 요약을 추가하는 형태.
3. 가능하면 **문제가 된 필드 카드 자체를 시각적으로 표시**한다. 서버 응답의 `errors[].field`(`basic.age` 등)가 이미 필드 키를 담고 있으므로, 해당 카드에 테두리 강조를 주면 된다.
4. **저장 전에 미리 막지는 말 것** — 버튼을 비활성화하면 "왜 안 눌리는지" 알 수 없어 지금과 같은 혼란이 반복된다. 누르면 반드시 명확한 피드백이 나오는 방향으로 할 것.

### B. 높은 신뢰도 항목도 근거를 보여주기

5. `renderFieldCropPreview`의 `if (getConfidenceLevel(key) === 'high') return null;` 조기 반환을 **제거**해, 신뢰도와 무관하게 모든 항목이 크롭과 `ROI 확인`을 갖도록 한다. 화면이 길어지는 건 감수한다 — 검증 가능성이 우선이다.
6. 자동 확정 로직(`allowAutoValue`, `requiresHighVisualConfidence`, 임계값)은 **변경 금지**. 이건 표시 문제이지 판정 문제가 아니다.

### 공통

7. `npm test`, `npm run build` 통과, `git status`에 `templates/` 변경 없음 확인, 버전 마커 갱신(현재 `v2026-08-10.6`) 후 커밋·푸시.

보고 시: (a) 파일별 변경, (b) 테스트/빌드 결과, (c) 필수 항목을 비운 채 저장했을 때 사용자에게 실제로 무엇이 보이는지(스크롤 동작·하단 요약 문구·필드 강조), (d) `높음` 항목에도 크롭이 나오는지 확인 결과.

## 6. 다음 작업을 위한 피드백

- **실사용 재검수 필요**: 위 검증은 API 응답과 배포 번들 수준까지다. 실제로 버튼을 눌렀을 때 스크롤·하단 요약·카드 강조가 기대대로 보이는지는 사용자 재테스트로 확인해야 한다.
- **근본 원인은 남아 있다**: 저장이 막힌 진짜 이유는 **기본정보 4개가 자동으로 채워지지 않는 것**이다. 이번 수정은 "왜 막혔는지 알려주는" 것이지 "안 막히게 하는" 것이 아니다. 특히 **연령대 숫자 OCR이 실사용 이미지에서 값을 못 채우고 있다** — 좌표는 맞으므로 인식 자체의 문제다. 학교유형·학년도 좌표는 잡히지만 신뢰도가 낮아 자동 입력되지 않는다.
- 즉 사용자는 여전히 학생마다 기본정보 4개를 수동 입력해야 한다. 다음 라운드에서 이 자동 입력률을 올리는 것이 실질적 사용성 개선의 핵심이다.
