# 촬영 유도와 원본 평가 — 설계

작성 2026-08-27. 근거는 [PHOTO_PATH_PLAN_2026-08-25.md](PHOTO_PATH_PLAN_2026-08-25.md)
§4의 19명 촬영본 측정이다. **아직 구현하지 않았다. 이 문서는 무엇을 왜 만들지와, 무엇을
아직 모르는지를 적는다.**

---

## 1. 왜 — 숫자 하나

19명(사진 38장)을 정답표와 대조한 결과를 보정 성공 여부로 갈랐다.

| 묶음 | 학생 수 | 학생당 정답 |
|---|---|---|
| 앞뒤 **둘 다** 보정 성공 | 8 | **1.63** |
| 한 장만 성공 | 10 | 0.10 |
| 둘 다 실패 | 1 | 0.00 |

**16배다.** 그리고 원본 사진의 오답 11건은 전부 보정되지 않은 장에서 나왔다.

찍고 나서 경고하는 것으로는 늦다. 검수자가 그 자리에 있고 종이도 그 자리에 있을 때
**다시 찍게 하는 것**이 24칸 수기 입력보다 싸다.

**주의: 보정 성공은 충분조건이 아니다.** 학생 14·15는 양면 모두 신뢰도 0.82~0.99로
보정됐는데 결과가 0/0, 0/1이었다. 그래서 이 문서는 기하 유도(§3~§5)와 **원본 평가**(§6)를
분리해서 다룬다.

## 2. 지금 화면에 있는 것

[ImageUploadPanel.tsx](../src/components/ImageUploadPanel.tsx)의 카메라 흐름은
`getUserMedia`(ideal 1600x1200) → `<video>` 미리보기 → 캡처 → 보정 → 확인 → 업로드다.

미리보기 위에 얹힌 것은 **단계 이름 하나와 정적인 안내 문구 셋**이 전부다.

```
종이의 네 모서리가 모두 보이게 촬영합니다.
그림자와 흔들림을 줄이고 정면에서 촬영합니다.
체크 표시가 작게 보이지 않도록 화면을 가득 채웁니다.
```

**맞는 말이고, 아무것도 재지 않는다.** 지켜졌는지 알려주지 않으므로 §1의 표에서 오른쪽
칸으로 가는 사람과 왼쪽 칸으로 가는 사람이 갈리지 않는다.

## 3. 무엇을 재서 무엇을 말할 것인가

전부 이미 계산되는 값이다. `detectDocumentQuadFromMat`이 돌려주는 `QuadQuality`와,
거절했을 때의 `QuadRejection`에 다 들어 있다.

| 신호 | 출처 | 화면에 할 말 |
|---|---|---|
| 사각형을 못 찾음 | `quality === null && rejection === null` | 종이가 배경과 구분되게 놓아주세요 |
| `cropped` | 여백 < 0.02 | 종이 전체가 화면 안에 들어오게 |
| `too-small` | 커버리지 < 0.6 | 조금 더 가까이 |
| `wrong-shape` | 종횡비 밴드 밖 | 정면에서, 종이 전체를 |
| 회전 | 아래 §5 | 화면과 나란히 돌려주세요 |
| 원근 기울기 | `edgeConsistency` | 어느 쪽을 눕힐지 (방향까지) |
| 종이가 어두움 | 아래 §6 | 밝은 곳에서, 그림자 없이 |

## 4. 테두리 표시

### 4.1 어디에 그릴 것인가 — 측정에서 나온 값

보정에 성공한 사각형 26개의 분포다.

| | min | p25 | 중앙 | max |
|---|---|---|---|---|
| 커버리지 가로 | 0.632 | 0.719 | 0.806 | 0.922 |
| 커버리지 세로 | 0.661 | 0.724 | 0.834 | 0.936 |
| 최소 여백 | 0.021 | 0.039 | 0.067 | 0.134 |
| 종횡비 | 1.251 | 1.407 | **1.410** | 1.725 |

가이드 테두리는 **게이트가 받아주는 영역의 한가운데**에 놓아야 한다. 게이트는 커버리지
0.6 이상, 네 변 여백 0.02 이상, 종횡비 1.384의 ±1.25배를 요구한다
([perspectiveCorrect.ts](../src/lib/documentScanner/perspectiveCorrect.ts)).

제안: **화면 짧은 변의 78%를 채우는 종횡비 1.384 직사각형**을 중앙에 그린다.

- 세로 커버리지 0.78 → 측정 중앙값 0.834보다 약간 여유. 여백은 각 변 0.11로 하한(0.02)의
  5배.
- 사용자가 테두리에 맞추면 게이트의 세 조건이 **동시에** 만족된다. 하한에 맞추게 하면
  한 조건만 흔들려도 떨어진다.
- 세로 화면과 가로 화면에서 같은 규칙을 쓰되, 짧은 변 기준이므로 세로 촬영을 전제한다.
  가로로 들면 종횡비가 뒤집혀 `wrong-shape`가 되므로, **가로 감지 시 세로로 돌리라는 안내를
  먼저** 띄운다.

### 4.2 어떻게 그릴 것인가

`<video>` 위에 절대 위치 `<div>` 하나. 캔버스가 필요 없다.

```
video wrapper (position: relative)
  video           (object-fit: cover)
  guide overlay   (position: absolute; inset: 0; pointer-events: none)
      어두운 마스크 4장 또는 box-shadow: 0 0 0 100vmax rgba(0,0,0,.45)
      테두리 사각형 + 네 모서리 기호
```

상태는 색으로만 말하지 않는다 — **회색(찾는 중) / 주황(조건 미달) / 초록(지금 찍으면 됨)**
에 더해 테두리 두께와 모서리 기호를 함께 바꾸고, 문구를 같이 띄운다. 색만 쓰면 색각
이상에서 구분되지 않는다.

`object-fit: cover`는 영상 일부를 잘라낸다. **테두리의 화면 좌표와 검출에 쓰는 프레임
좌표가 어긋나면 안 된다** — 이 프로젝트에서 렌더 해상도 불일치로 엉뚱한 단계를 잰 사례가
네 번 있다(CLAUDE.md §2). 검출 프레임은 `video.videoWidth/videoHeight`에서 직접 그리고,
오버레이 좌표는 그 프레임을 화면에 매핑한 변환을 **한 곳에서** 계산해 양쪽이 같은 수를
쓰게 한다.

## 5. 기울어짐 경고 — 구현 제안

### 5.1 두 가지 기울어짐을 구분해야 한다

같은 "기울었다"가 아니다. 사용자가 해야 할 행동이 다르다.

| | 뜻 | 고치는 법 |
|---|---|---|
| **회전(roll)** | 종이가 화면 안에서 돌아가 있음 | 폰이나 종이를 돌린다 |
| **원근 기울기** | 카메라가 종이와 나란하지 않음 | 폰을 종이 위로 눕힌다 |

원근 기울기는 워프가 펴주지만, **심하면 검출 자체가 실패한다.** §4의 실패 12건이 대체로
그랬다.

### 5.2 제안 — 이미 있는 사각형에서 뽑는다 (권장)

새 알고리즘이 필요 없다. `orderQuadPoints`가 정렬한 네 점에서 바로 나온다.

```ts
const [tl, tr, br, bl] = quality.points;

// 회전: 위/아래 변의 평균 각도. 0에 가까워야 한다.
const rollDeg = ((Math.atan2(tr.y - tl.y, tr.x - tl.x)
               + Math.atan2(br.y - bl.y, br.x - bl.x)) / 2) * (180 / Math.PI);

// 원근 기울기: 마주보는 변의 길이 차이. 부호가 방향을 말한다.
const topW = dist(tl, tr), bottomW = dist(bl, br);
const leftH = dist(tl, bl), rightH = dist(tr, br);
const keystoneV = (bottomW - topW) / Math.max(topW, bottomW); // +면 위쪽이 멀다
const keystoneH = (rightH - leftH) / Math.max(leftH, rightH); // +면 왼쪽이 멀다
```

**부호가 방향을 준다는 것이 핵심이다.** "기울었습니다"가 아니라 *"위쪽을 조금 낮춰
주세요"*라고 말할 수 있다.

`edgeConsistency`가 이미 이 둘을 하나로 합친 값이다(`(min/max 가로 + min/max 세로)/2`).
경고 문구에는 개별 `keystone`의 부호를, 최종 판정에는 `edgeConsistency`를 쓴다.

측정된 분포(성공한 26개): `edgeConsistency` min 0.814 · 중앙 0.978. 즉 성공 사례는 거의
정면이다. **경고 문턱 초안은 `edgeConsistency < 0.93`(키스톤 약 7%), 회전은 `|roll| > 4°`
로 두고 첫 라운드에서 재조정한다.** 이 두 숫자는 아직 검증되지 않았다.

### 5.3 대안과 왜 안 쓰는가

| 방법 | 판단 |
|---|---|
| `DeviceOrientationEvent` (중력 기준 자세) | **보조로만.** 종이가 수평면에 있을 때만 뜻이 있고, 데스크톱 웹캠에는 센서가 없다. CPU를 안 쓰므로 *사각형을 찾기 전* 단계에서 "폰을 눕히세요"를 미리 띄우는 데는 쓸 수 있다 |
| Hough 직선 검출 | 코드가 늘고 §5.2보다 나은 점이 없다. 사각형을 이미 찾았으면 변은 이미 안다 |
| 별도 ML 모델 | 이 문제에 과하다. 번들과 초기화 비용이 인식 이득보다 크다 |

**권장: §5.2 단독. `DeviceOrientation`은 모바일에서 선택적 사전 힌트.**

## 6. 어두움 감지와 "인식 가능한 원본인가" 평가

### 6.1 이것이 진짜 남은 문제다

워프된 선별검사 19장의 `pageInkRatio`:

```
빈 양식(스캔)   0.087
워프된 사진     0.345 ~ 0.613      격자 필드 1~11개
```

배경은 잘려나갔는데도 **종이 자체가 `pixel < 200`보다 어둡게 찍혔다.** 흰 종이에 자동
노출을 맞추면 그렇게 된다. 학생 14·15가 잘 보정되고도 아무 값을 못 낸 이유가 여기 있다고
본다 — **아직 증명되지 않았다.**

### 6.2 라이브에서 잴 것 (사각형 안쪽만)

검출된 사각형 내부를 재야 한다. 바깥(바닥·책상)은 노출과 무관한 잡음이다.

| 값 | 정의 | 쓰임 |
|---|---|---|
| `inkFraction` | 사각형 안에서 `gray < 200`인 비율 | `pageInkRatio`의 라이브 대응. 어두움 판정 |
| `paperLuma` | 사각형 안 평균 밝기 | 노출 안내 |
| `blownFraction` | `gray >= 250` 비율 | 반사광(글레어) 판정 |
| `backgroundContrast` | 안쪽 평균 − 바깥쪽 평균 | 검출 실패 예보 |
| 흐림 | 라플라시안 분산 | 손떨림 판정 |

**문턱은 아직 정하지 않는다.** 스캔이 0.087, 잘 안 읽힌 사진이 0.35~0.61이라는 두 점만
알고 있고, 그 사이 어디가 경계인지는 재지 않았다. §8에 그 측정을 적어둔다.

흐림도 마찬가지다. 서버의 `pageSharpness`(gradient 기반)가 있지만 라플라시안 분산과 다른
양이므로, **문턱을 추측해 넣지 않는다. 먼저 잰다.**

### 6.3 "유의미한 인식이 가능한가" — 클라이언트가 할 수 없는 부분

| 신호 | 어디서 | 라이브 가능? |
|---|---|---|
| 보정 성공 / 거절 이유 | OpenCV 워커 | 예 |
| 커버리지·여백·종횡비·기울기 | 같은 사각형 | 예 |
| `inkFraction`·글레어·흐림 | 같은 프레임 | 예 |
| **격자 필드 수** | `buildCagiGridDetection` | **아니오** |

격자 검출은 `markDensity`를 거치고 그것은 `sharp`(서버 전용)를 쓴다. 그런데 §4에서
**격자 필드 수가 1~11개로 갈리고 그것이 학생별 성패와 같이 움직였다.** 라이브 신호만으로는
이 축을 볼 수 없다.

**제안: 촬영 직후 서버에 한 번 물어본다.**

```
POST /api/uploads/quality   { imageId, type }
  -> { rectified, pageInkRatio, gridFields, verdict, hint }
```

- 종이가 아직 눈앞에 있을 때, 장당 즉시 판정한다. `/api/recognize`는 양면이 다 모인 뒤에
  돌므로 이 자리에 쓸 수 없다.
- **같은 평가기를 `/api/recognize`에서도 호출한다.** 두 경로가 다른 답을 내면 사용자는
  "괜찮다더니 왜"를 겪는다. 이 프로젝트에서 노드와 브라우저가 다른 답을 낸 사례가 이미
  있다(CLAUDE.md §5.1).
- 파일 업로드 경로에도 같은 판정을 붙인다. 카메라만 유도하고 업로드는 방치하면 사용자는
  더 조용한 경로로 도망간다.

### 6.4 판정 밴드는 측정으로 정한다

`verdict`를 세 단계로 두되(`good` / `retake-suggested` / `unusable`), **경계는 추측하지
않는다.** 19명 세트에 정답이 붙어 있으므로 이렇게 정할 수 있다.

> "정답을 한 칸이라도 낸 학생"과 "한 칸도 못 낸 학생"을 가장 잘 가르는
> `gridFields` / `pageInkRatio` 절단면을 찾는다.

표본이 19명이므로 **과적합을 경계해야 한다.** 절단면을 고른 뒤에는 라벨을 섞은 대조군에서
같은 탐색을 돌려, 우연히 얻어지는 분리 수준을 같이 적는다 — 선택 편향을 그렇게 쟀다
([WEAK_SIGNAL_STABILITY_PLAN_2026-08-24.md](WEAK_SIGNAL_STABILITY_PLAN_2026-08-24.md)).

## 7. 성능 예산

측정된 값: 1600px 긴 변에서 사각형 검출이 **241~1392 ms**(사진 10장).

라이브는 그것보다 훨씬 작아야 한다.

- 검출 프레임 **긴 변 480px** 제안. 1600px 대비 화소가 약 11분의 1이다.
- 목표 **4 fps 이상**, 한 프레임이 처리 중이면 다음 프레임은 **버린다**(큐에 쌓지 않는다).
- 검출은 **이미 있는 OpenCV 워커**에서 돈다. 메인 스레드에서 돌리면 미리보기가 끊긴다.
- 프레임 공급은 `requestVideoFrameCallback`, 없으면 `setTimeout`. **`requestAnimationFrame`을
  쓰지 않는다** — 숨은 탭에서 발화하지 않아 조용히 멈춘다(CLAUDE.md §4).
- **480px과 4 fps는 아직 재지 않은 목표치다.** 첫 구현에서 실측하고, 못 맞추면 프레임을
  더 줄이거나 검출 지도를 Otsu 하나로 줄인다.

### 7.1 §8-1 실측 (2026-08-27, `scripts/check-live-detect-cost.cjs`)

`detectDocumentQuadFromMat` **단독** 비용. 합성 프레임(빈 양식을 기울여 잡음 섞인 회색
배경에 합성), Node OpenCV 4.9.0 빌드.

```
긴 변 480  (368x480)   N=20   median 36.8 ms   min 36.1  max 56.9   쿼드 검출 20/20
긴 변 1600 (1225x1600) N=5    median 299.5 ms                       쿼드 검출 5/5
```

- 1600 쪽이 §7 서두의 실측 밴드(241~1392 ms) 안쪽 하단에 들어온다. 합성 프레임이 실제
  사진보다 쉬운 쪽이라는 뜻이고, **480의 36.8 ms도 같은 만큼 낙관적으로 읽어야 한다.**
- **이것은 fps가 아니다.** 비디오 grab, 캔버스 축소, 워커 전송, 리렌더가 전부 빠져 있다.
  브라우저 WASM 빌드도 Node 빌드와 다르다. 200 ms 주기와의 여유가 얼마나 남는지는
  브라우저에서 따로 재야 한다.
- 배율이 8.1x로 화소비 11.1x보다 작다 — 고정 비용이 있다는 뜻이므로, 프레임을 더 줄여
  얻을 이득은 화소비만큼 나오지 않는다.

2. **`inkFraction` 경계.** 워프된 19장의 사각형 내부 `inkFraction`과 학생별 성패를 대조해
   `good` / `retake` 경계를 찾는다. 섞은 라벨 대조군을 같이 돌린다.
3. **흐림 지표 보정.** 라플라시안 분산을 19장에서 재고 격자 필드 수와의 관계를 본다.
   관계가 없으면 흐림 경고를 넣지 않는다.
4. **§5.2 문턱 검증.** `edgeConsistency < 0.93`, `|roll| > 4°`가 실제로 실패를 예보하는가.
   성공한 26개의 분포(min 0.814)와 실패 12건을 나란히 놓고 확인한다.

## 11. M5 재정의 — 합격 기준이 측정 불가가 됐고, 안내가 푼 문제를 안내하고 있다 (2026-08-27)

### 11.1 §9 5단계의 합격 기준은 이제 잴 수 없다

원래 기준: *"실기기에서 초록 상태로 찍은 사진의 보정 성공률이 안내 없이 찍은 것보다 유의하게
높을 것."*

그 사이에 ORB 2경로가 들어가면서 **보정 성공률이 38/38로 포화됐다**
([FEATURE_SPEC §7](FEATURE_SPEC_CAPTURE_PIPELINE_2026-08-27.md)). 포화된 지표로는 어떤
개선도 보일 수 없다. 이 기준은 폐기한다.

**새 기준**: 안내를 받고 찍은 사진이 **자동 입력 칸을 더 많이 내는가.** 정답표가 있으므로
같은 하니스(`_probe-photo-accuracy`)로 바로 잴 수 있고, 이것이 검수자에게 실제로 남는 값이다.

### 11.2 안내가 재는 것과 남은 문제가 어긋나 있다

`captureGuidance.ts`가 재는 것: 사각형·회전·원근 기울기·커버리지·여백 — **전부 기하**다.
밝기·노출은 **한 줄도 재지 않는다**(exposure·bright·luma 관련 코드 0건).

그런데 기하는 §11.1대로 해결됐고, **열려 있는 문제는 톤이다** — 어두운 바닥 11명이 0칸인
이유이고([FEATURE_SPEC §12.2](FEATURE_SPEC_CAPTURE_PIPELINE_2026-08-27.md)), 미확정 392칸의
대부분이다.

**즉 라이브 안내는 풀린 문제를 안내하고 안 풀린 문제에는 침묵한다.** §6.2에 계획돼 있던
노출 측정이 구현에서 빠진 결과다.

### 11.3 무엇을 붙이면 되는가

`sheetExposure.ts`의 `dynamicRange = p95 − p05`는 **사진만의 속성**이라 템플릿 없이 프레임
하나로 계산된다. 라이브 루프가 이미 프레임을 캔버스로 받고 있으므로 추가 자산이 필요 없다.

측정된 분리(19명, 워프 후):

```
수확 학생   155 ~ 182
무수확 학생  61 ~ 108        최적 절단 17/19 · 섞은 라벨 p95 15
```

**단, 이 숫자는 워프된 최종 이미지의 것이고 라이브 프리뷰 프레임의 것이 아니다.** 라이브
문턱은 실기기 세션에서 보정해야 하며, 그때까지 PROVISIONAL로 표시한다.

판정용(`unusable`)이 아니라 **안내용**이라는 점이 중요하다 — 틀렸을 때의 비용이 재촬영 한
번이지 오답이 아니므로, 판정 밴드에 적용한 것보다 낮은 증거 기준으로 쓸 수 있다.

### 11.4 실기기 세션 준비 — HTTPS 없이 카메라를 여는 법

앱은 `window.isSecureContext`를 요구한다. 인증서를 만들 필요 없이, **Chrome의 USB 포트
포워딩**(`chrome://inspect` → Port forwarding)으로 폰이 `http://localhost:<포트>`를 보게 하면
보안 컨텍스트가 성립한다. 폰을 USB로 연결하는 것으로 끝난다.

## 12. M6에 필요한 것 — 정답표를 다시 만들지 않는다

가장 비싼 것은 사진이 아니라 **정답표**다. 그런데 **같은 19장을 다시 촬영하면 기존 정답표가
그대로 적용된다** — 학생과 순서가 같기 때문이다. 스캔에서 이미 3세트를 그렇게 만들었다.

**몇 세트인가 — 막힌 지점에서 역산한다.** 아핀 승격을 막는 것은 밴드 어긋남 **1건**이고
(자동 입력 88칸 중), 판별자를 찾으려면 5~10건이 필요하다 → **3~5세트 재촬영**.

같은 재촬영이 작은 표본에서 자른 상수들을 함께 재검한다.

| 상수 | 현재 n |
|---|---|
| `AGE_OCR_MIN_CONFIDENCE = 85` | **3** |
| `PHOTO_BINARY_FLOOR = 0.042` | **6** |
| `BAND_INK_ALL_MIN = 0.040` | 15행 |
| `dynamicRange` 문턱(미적용) | 19명 |

촬영 조건: **밝은 곳에서, 어두운 바닥을 피해서.** 나머지는 다양할수록 좋다 — 판별자는
변이에서 나온다. **불량 샘플은 버리지 말고 보관한다**(FEATURE_SPEC §10.3) — 게이트의 회귀
시험 대상이다.

## 13. 라이브 노출 안내 1회차 — 계측은 남기고 경고는 끈다 (2026-08-27)

§11.2가 지목한 공백(안내가 기하만 재고 밝기에는 침묵)을 메우는 라운드. 위임 결과는
`worktree-agent-a799b5327d00ae8c1` @ `c0b3a60`.

### 13.1 위임 대상이 잴 수 없었던 것

주문서에 문턱을 **잠정치로 표시하라**고 적어 보냈다. 위임 대상은 그대로 했고, 근거도
정직하게 남겼다 — *"§11.3의 숫자는 보정 최종본에서 나왔고, 프리뷰 프레임과의 관계는 측정된
적이 없다."* 워크트리에 사진이 없으니 그 이상은 할 수 없었다.

**그 관계는 여기서 잴 수 있다.** 이것이 CLAUDE.md §1이 말하는 중앙 측정 위치의 값이다.

`scratchpad/preview-exposure.cjs` — 19명의 **원본 사진**을 라이브와 같은 480px 장변으로
축소하고, **출하되는 검출기**로 사각형을 찾고, **출하되는 노출 코드**로 그 내부를 잰다.
재구현이 아니라 실제로 도는 코드를 채점한다.

### 13.2 결과: 문턱이 아니라 신호가 죽는다

```
프리뷰 - 최종 : 중앙값 -5, 범위 -58 .. +14
프리뷰 범위   :  65 .. 105        (최종  57 .. 139)

문턱 130을 프리뷰 값에 그대로 적용하면 → 19/19명 "어둡다" 경고
```

**19명 전원**이다. 자동 입력을 실제로 낸 p1–p5까지 포함해서. 항상 발화하는 안내는 안내가
아니라 잡음이고, 옆에 붙은 기하 안내의 신뢰까지 같이 깎는다.

문턱을 옮기면 되는 문제가 아니다. 판별력 자체를 §5.1과 같은 규율로 재보면:

| 신호 | 최적절단/19 | 섞은라벨 p95 | 판정 |
|---|---|---|---|
| **최종** dynamicRange | 17 | 15 | ★ 상회 — §11.3이 본 것 |
| **프리뷰** dynamicRange | **15** | **15** | **우연 수준** |

**§11.3이 최종본에서 찾은 신호는 프리뷰 해상도에 존재하지 않는다.** 문턱이 틀린 게 아니라
정직하게 고를 값이 없다.

기제는 표에 그대로 보인다. 축소는 **평균**이고 dynamicRange는 양 꼬리의 거리뿐이라, 잉크
디테일이 살아 있는 **좋은** 사진일수록 많이 깎인다(p1–p5: −34 ~ −58). 어두운 사진은 잃을
디테일이 없어서 거의 그대로다(−5 안팎). **축소가 좋은 사진을 나쁜 사진 쪽으로 끌어내린다.**

### 13.3 더 나쁜 것: 대체 영역이 반대로 읽는다

19명 중 **14명은 사각형이 안 잡혀 `guide` 대체 경로**로 측정됐다. 그 경로는 안내 사각형
내부를 재는데, 거기엔 어두운 바닥이 섞인다. 그런데 결과는 어두워지는 게 아니라 **범위가
넓어진다** — p6의 만족도 프리뷰는 143으로, 자동 입력을 낸 p1의 81보다 높다.

`guide` 값은 종이의 노출이 아니다. 그리고 그것이 **다수 상태**다.

### 13.4 대안 신호를 찾았다가 라벨 누출로 기각

p05(`≥110`)가 17/19로 대조군을 넘겼다. 그런데 그 절단이 고르는 집합은 정확히 p1–p5이고,
이는 **사각형이 검출된 학생 집합과 같다.** 노출이 아니라 검출 성공을 재고 있다 —
FEATURE_SPEC §14.1에서 이미 한 번 당한 누출과 같은 모양이다. 게다가 수확이 있는 p16·p17을
둘 다 놓친다. **기각.**

### 13.5 판정

| 대상 | 판정 |
|---|---|
| 계측 배관(히스토그램·영역 테스트·워커 배선·시험 22건) | **병합** — CLAUDE.md §1.4의 "환경변수로 가려진 중립 계측기" 예외 |
| 경고 발화 | **기본 끔.** 어떤 문턱값도 이 증거로는 정당화되지 않는다 |
| `guide` 대체 경로에서의 발화 | **금지.** 종이를 재고 있지 않음이 측정됐다 |

계측기는 실기기 세션이 쓸 도구다. 지금 켜면 전원에게 틀린 말을 한다.

### 13.6 이 측정이 재지 않은 것

축소본은 **촬영된 스틸의 축소**이지 진짜 카메라 프리뷰가 아니다. 폰의 프리뷰는 자체 게인과
화이트밸런스를 갖고, 뒤따르는 스틸과 노출이 다를 수 있다. 여기서 분리한 것은 **래스터 축소
항 하나**다.

다만 방향은 보수적이다. 이 측정은 sharp의 lanczos3로 축소했고, 실제 경로는 캔버스
`drawImage`(ImageUploadPanel.tsx:512)로 더 부드럽게 축소한다. **실제 프리뷰는 최소한 이만큼,
아마 더 압축된다.** 문턱을 무효화하는 방향으로는 하한이다.

### 13.7 함께 잡힌 회귀 — 셔터 강조가 도달 불가능해진다

노출 분기가 `ready` 반환 **바로 앞**에 있다(captureGuidance.ts:794). `nextReadyStreak`는
`level !== 'ready'`면 0을 돌려주므로, 발화하는 프레임은 연속 카운트를 쌓지 못한다 →
`shutterEmphasized`가 영원히 false → **`1595494`에서 출하한 "지금 촬영하세요"가 도달
불가능해진다.**

§13.2의 숫자와 합치면 이것은 문장 하나가 추가되는 문제가 아니다. **모든 시트에서 셔터 강조
기능이 영구히 사라진다.** 병합 불가의 실제 이유는 문턱이 아니라 이쪽이다.

### 13.8 합성이 또 틀렸다 — 이번엔 양쪽 다

검토 렌즈 둘이 각자 만든 **합성 이미지**로 같은 상황에 정반대 숫자를 냈다. 하나는 "가장자리
링이 지배하므로 1px만 안쪽으로 밀어도 119 → 163으로 뒤집힌다", 다른 하나는 "빈 양식 축소본이
111~125". 실제 사진으로 판정했다(`scripts/check-quad-inset-exposure.cjs`) — 검출된 사각형을
중심 쪽으로 0~12px 줄여가며 재측정:

```
사각형 검출 프레임 9개 · 변동폭 중앙값 4, 최대 5   (값 자체는 81~97)
어느 inset 에서든 문턱 130 을 넘는 프레임: 0/9
```

실제 사진에서 읽기는 **안정적**이다. 가장자리 링이 지배한다는 설명은 합성의 산물이었다 —
합성은 종이와 바닥 사이가 계단이지만 실제 사진은 부드럽고 잡음이 있으며, 꼬리는 시트 내부가
만든다. 그리고 다른 렌즈의 111~125도 실측(81~97)과 맞지 않았다.

**두 합성이 모두 틀렸고, 방향도 서로 반대였다.** CLAUDE.md §2가 말하는 그대로다. 이 라운드에서
값을 가진 숫자는 실제 사진에서 나온 것뿐이다.

부수적으로 얻은 것: inset 보정으로 문턱을 구제할 수 없다는 것도 이 표가 닫는다.

### 13.9 2회차 — 병합 (`cf39252` → `6a93b2c`)

발화만 끄고 계측은 전부 남겼다.

```
LIVE_EXPOSURE_HINT_ENABLED = false     실기기 세션이 뒤집을 불리언 하나
LIVE_EXPOSURE_MIN_SAMPLES  = 2000      p95가 읽을 상위 5%에 100개가 남는 수
LIVE_DYNAMIC_RANGE_WARN    = 130       지우지 않고 "프리뷰에서 미검증"으로 재기술
```

발화 조건이 `shouldWarnOnExposure` 한 곳에 모였다: `enabled` → `region === 'quad'` →
`sampleCount ≥ 2000` → `range < WARN`.

**최소 표본 수를 6,392와 7,600 사이에 두지 않은 것이 옳다.** 그 사이에 두면 두 번의 관측에
맞춘 값이 되고, 조용히 **두 번째 영역 테스트**로 굳는다 — 더 나쁜 쪽으로. 2,000은 p95가 무엇을
읽는지에서 나온 수이고, 실제 프레임 어디에도 걸리지 않는다.

`region === 'quad'` 강제에 대해 위임 대상이 스스로 정정한 것도 남겨둔다 — 처음엔 "미래의 호출
순서 변경에 대한 위생"으로 썼는데, §13.3을 읽고 **오늘의 정확성 관문**으로 바꿔 적었다. 가이드
경로는 미래에 틀릴 수 있는 게 아니라 지금 거꾸로 읽는다.

**판정은 실제 사진으로 했다**(`scripts/check-live-guidance-on-photos.cjs`). 단위 시험은 손으로
만든 입력을 검사하지만, 회귀를 발견한 것은 그 프레임들이다.

```
사각형 검출 프레임 9개
  "어둡습니다" 발화 : 0/9      기본 꺼짐
  ready 도달        : 9/9      §13.7의 회귀 복구
  streak 증가       : 9/9      level이 아니라 streak이 회귀한 것이므로 이쪽을 단언
```

전체 시험 376건 통과(`MARK_AFFINE_TONE=1` 포함), `tsc` 무오류, 빌드 통과.

**스캔 기준선은 잴 필요가 없다.** 인식·채점·`sheetQuality`는 한 줄도 바뀌지 않았고, 워커에서
지워진 줄은 `detectOnly`의 주석·시그니처·반환 세 줄뿐이다. 보정 경로는 그대로다.

### 13.10 실기기 세션이 이 라운드에서 받아가는 것

문턱이 아니라 **도구 세 개와 닫힌 설명 하나**다.

- `scripts/check-preview-exposure.cjs` — 프리뷰 축소에서 신호가 얼마나 남는지
- `scripts/check-quad-inset-exposure.cjs` — 영역 경계에 얼마나 민감한지
- `scripts/check-live-guidance-on-photos.cjs` — 판정기가 실제 프레임에서 무엇을 말하는지
- **닫힌 설명**: 프리뷰 dynamicRange는 노출 판별자가 아니다(15/19, 대조군 15). 다시 열려면
  새 증거가 필요하다 — 실기기 프리뷰의 래스터가 축소본과 다르게 동작한다는 측정이면 된다.

세션이 할 일은 문턱을 고르는 게 아니라 **프리뷰 래스터에서 신호가 존재하는지부터** 다시
확인하는 것이다. 존재하면 그때 불리언을 뒤집는다.

## 14. 실기기 세션 준비 — 진단 표시 (2026-08-28)

§13에서 계측기를 병합했는데, **화면 어디에도 표시되지 않았다.** `exposure`는 상태 객체까지
흘러오고 거기서 멈춘다. 세션의 목적이 "실기기 프리뷰에서 이 숫자가 뭘로 읽히는가"인데 폰으로
접속해도 읽을 방법이 없었다.

### 14.1 무엇을 붙였나

`?diag=1`. 없으면 DOM에 노드가 생기지 않는다(확인함). 읽기는 `useEffect` 안이라 SSR과 첫
클라이언트 렌더가 동일 — 하이드레이션 불일치가 없다.

프레임 아래 자기 행에 놓인다(덮지 않는다). `영역`이 숫자 앞에 온다 — §13.3 때문에 **어느
측정을 보고 있는지**를 먼저 알아야 그 아래 숫자를 믿을 수 있다.

`프레임`은 비디오 원본이 아니라 **검출 프레임**(480 축소본)을 보고한다. 래스터 배율 없는
판독값은 기기 간 비교가 안 된다.

### 14.2 핵심은 표시가 아니라 join

사람이 화면에서 읽는 숫자는 데이터가 아니다. 셔터에서 기록이 쓰이고, 업로드가 끝나면
**`imageId`(저장 키)**가 역으로 채워진다. 그래야 나중에 "이 프리뷰 판독값을 낸 사진이 실제로
자동 입력을 냈는가"를 정답표와 대조할 수 있다.

위임 대상이 제안된 두 경로를 모두 쓰지 않고 더 나은 것을 찾았다 — 업로드 라우트는 클라이언트
파일명을 버리고 재생성하므로 거기 찍은 도장은 저장소에 닿지 않고, `registration` 메타는 인식과
판정 경로가 읽으므로 이번 라운드가 건드리면 안 된다. `imageId`는 인식이 이미 그 키로 이미지를
연다. **파싱이 아니라 정확한 키다.**

### 14.3 브라우저에서 직접 확인했다

위임 대상은 "브라우저에서 못 봤다"고 명시했다. 그건 이쪽 일이다(§4). 카메라가 없어 캔버스
`captureStream`으로 합성 스트림을 물려 375×812에서 끝까지 돌렸다.

```
영역 quad · range 187 · p05/p95 55/242 · 표본 13267(stride 3) · 프레임 360x480 · streak 2
레이아웃  뷰포트 안, 가로 스크롤 없음, 비디오와 겹치지 않음, ui-monospace 12px tabular-nums
셔터 →   기록 1건
이대로 사용 → outcome "uploaded" · imageId ".../uploads/cagi/.../page-0001.jpg" · dynamicRange 187 보존
?diag 없음 → 노드 0개 · 콘솔 오류 없음
```

**join이 실기 브라우저에서 끝까지 동작한다.** 단위 시험이 아니라 실제 업로드까지 간 결과다.

확인된 잔가지 둘: 스타일시트는 꺼져 있어도 `.capture-diagnostics*` 규칙 ~60줄을 싣는다(무해).
판독부가 첫 화면 아래에 있어 촬영 중에는 보이지 않는다 — 자동 기록이라 문제는 아니지만,
기록 건수도 같이 안 보이므로 세션에서 한 번은 스크롤해 확인하는 편이 좋다.

### 14.4 이 준비가 바꾸는 것

M6 촬영(같은 19장 × 3~5세트)이 도는 동안 프리뷰 판독값이 자동으로 쌓인다. **M5 ③이 같은
촬영에서 나온다 — 세션을 따로 잡을 필요가 없다.**

세션 뒤 할 일: 내보낸 JSON을 §13의 하네스와 맞물려, **프리뷰 래스터에서 신호가 존재하는지부터**
재확인한다. 존재하면 그때 `LIVE_EXPOSURE_HINT_ENABLED`를 뒤집는다. 문턱을 고르는 것이 먼저가
아니다.

## 15. 촬영 3세트 평가 규약 — 데이터 도착 **전에** 못박는다 (2026-08-29)

사용자가 조건을 갈라 3세트를 촬영했다. 파일이 오기 전에 규약을 고정한다 — 측정 뒤에 기준을
고르면 맞추게 된다.

### 15.1 세트는 라벨이 아니라 조건이다

| 세트 | 의도한 조건 |
|---|---|
| 1 | 신경 써서 촬영 (적합 계열) |
| 2 | 햇볕, 페이지별·부분별 극단적 밝기 차 |
| 3 | 극단적 기울기, 모서리 프레임 아웃, 중앙 어긋남 |

**사용자가 명시: 2·3세트에도 비교적 양호한 표본이 섞여 있다.** 그러므로 세트를 그대로 정답으로
쓰면 안 된다. "세트2 = 부적합"으로 채점하면, 햇빛 아래서도 잘 읽히는 장을 통과시킨 게이트가
**오답으로 집계된다.** 계측기가 재는 대상이 뒤바뀐다(§2).

- **조건 = 세트 소속** (층화 변수)
- **라벨 = 결과**: 그 장이 정답표 대비 자동 입력을 내는가 (`_probe-photo-accuracy` 방식)

### 15.2 이 표본이 답할 수 있게 되는 질문

조건이 섞여 있어야만 갈리는 것이 있다:

> 게이트가 **조건**을 감지하는가, **쓸 수 없음**을 감지하는가?

햇빛을 감지하는 게이트는 쓸모없다 — 햇빛이 들어도 읽히면 통과시켜야 하고, 잘 찍었는데
안 읽히면 걸러야 한다. 그 구분은 **조건 안의 변이**에서만 측정된다. 세트별 통과율이 아니라
**세트 내부에서 수확 있는 장 vs 없는 장**을 가르는지를 본다.

판정 지표: 세트를 층으로 고정한 뒤의 판별력. 세트 소속만으로 얻는 정확도를 기준선으로 두고,
게이트가 그 위로 올라가야 값이 있다. (세트 소속이 이미 결과와 상관되므로, 층화 없이 재면
게이트가 세트를 알아맞힌 것을 판별력으로 착각한다 — FEATURE_SPEC §14.1의 누출과 같은 모양.)

### 15.3 순서

1. **게이트 채점** — 현 `sheetQuality` 판정을 114장에 돌려 결과 라벨과 대조. 세트 층화 필수
2. **재촬영 요구 발화** — 2·3세트의 부적합 장에서 실제로 안내가 뜨는가, 아니면 조용히 넘어가는가
3. **닫힌 설명 재개 여부** — §13은 프리뷰 dynamicRange를 "판별자 아님"으로 닫았다. 그것은
   **한 세트 안의 좁은 변이**로 잰 결과였다. 세트 2는 밝기 범위를 의도적으로 넓혔으므로
   **새 증거의 자격이 있다**. 다시 열되, 판정은 §15.2의 층화 규칙 아래에서
4. **M6 기준선** — 세트 1(적합 계열)의 인식률. "잘 찍으면 어디까지 가는가"의 답이자,
   회색조 재스캔이 보류인 동안 소프트웨어 천장의 대용 지표

### 15.4 미리 적어두는 사망 조건

- 게이트가 **세트 층 안에서** 결과를 예측하지 못하면(층화 후 대조군 수준), 현 판정 로직은
  조건 감지기일 뿐이며 재촬영 요구의 근거가 약하다 — 그렇게 보고한다
- 세트 1의 수확이 세트 2·3과 유의하게 다르지 않으면, "잘 찍으면 나아진다"는 전제 자체가
  이 표본에서 지지되지 않는다. 그 경우 촬영 안내(M5) 전체의 가치를 재평가해야 한다
