# 촬영 유도와 원본 평가 — 설계

작성 2026-08-27. 근거는 [PHOTO_PATH_PLAN_2026-08-25.md](PHOTO_PATH_PLAN_2026-08-25.md)
§4의 19명 촬영본 측정이다. **아직 구현하지 않았다. 이 문서는 무엇을 왜 만들지와, 무엇을
아직 모르는지를 적는다.**

---

## 1. 왜 — 숫자 하나

19명(사진 38장)을 정답표와 대조한 결과를 보정 성공 여부로 갈랐다.

| 묶음 | 학생 수 | 학생당 정답 |
|---|---|---|
| 앞뒤 **둘 다** 보정 성공 | 8 | **1.63** |
| 한 장만 성공 | 10 | 0.10 |
| 둘 다 실패 | 1 | 0.00 |

**16배다.** 그리고 원본 사진의 오답 11건은 전부 보정되지 않은 장에서 나왔다.

찍고 나서 경고하는 것으로는 늦다. 검수자가 그 자리에 있고 종이도 그 자리에 있을 때
**다시 찍게 하는 것**이 24칸 수기 입력보다 싸다.

**주의: 보정 성공은 충분조건이 아니다.** 학생 14·15는 양면 모두 신뢰도 0.82~0.99로
보정됐는데 결과가 0/0, 0/1이었다. 그래서 이 문서는 기하 유도(§3~§5)와 **원본 평가**(§6)를
분리해서 다룬다.

## 2. 지금 화면에 있는 것

[ImageUploadPanel.tsx](../src/components/ImageUploadPanel.tsx)의 카메라 흐름은
`getUserMedia`(ideal 1600x1200) → `<video>` 미리보기 → 캡처 → 보정 → 확인 → 업로드다.

미리보기 위에 얹힌 것은 **단계 이름 하나와 정적인 안내 문구 셋**이 전부다.

```
종이의 네 모서리가 모두 보이게 촬영합니다.
그림자와 흔들림을 줄이고 정면에서 촬영합니다.
체크 표시가 작게 보이지 않도록 화면을 가득 채웁니다.
```

**맞는 말이고, 아무것도 재지 않는다.** 지켜졌는지 알려주지 않으므로 §1의 표에서 오른쪽
칸으로 가는 사람과 왼쪽 칸으로 가는 사람이 갈리지 않는다.

## 3. 무엇을 재서 무엇을 말할 것인가

전부 이미 계산되는 값이다. `detectDocumentQuadFromMat`이 돌려주는 `QuadQuality`와,
거절했을 때의 `QuadRejection`에 다 들어 있다.

| 신호 | 출처 | 화면에 할 말 |
|---|---|---|
| 사각형을 못 찾음 | `quality === null && rejection === null` | 종이가 배경과 구분되게 놓아주세요 |
| `cropped` | 여백 < 0.02 | 종이 전체가 화면 안에 들어오게 |
| `too-small` | 커버리지 < 0.6 | 조금 더 가까이 |
| `wrong-shape` | 종횡비 밴드 밖 | 정면에서, 종이 전체를 |
| 회전 | 아래 §5 | 화면과 나란히 돌려주세요 |
| 원근 기울기 | `edgeConsistency` | 어느 쪽을 눕힐지 (방향까지) |
| 종이가 어두움 | 아래 §6 | 밝은 곳에서, 그림자 없이 |

## 4. 테두리 표시

### 4.1 어디에 그릴 것인가 — 측정에서 나온 값

보정에 성공한 사각형 26개의 분포다.

| | min | p25 | 중앙 | max |
|---|---|---|---|---|
| 커버리지 가로 | 0.632 | 0.719 | 0.806 | 0.922 |
| 커버리지 세로 | 0.661 | 0.724 | 0.834 | 0.936 |
| 최소 여백 | 0.021 | 0.039 | 0.067 | 0.134 |
| 종횡비 | 1.251 | 1.407 | **1.410** | 1.725 |

가이드 테두리는 **게이트가 받아주는 영역의 한가운데**에 놓아야 한다. 게이트는 커버리지
0.6 이상, 네 변 여백 0.02 이상, 종횡비 1.384의 ±1.25배를 요구한다
([perspectiveCorrect.ts](../src/lib/documentScanner/perspectiveCorrect.ts)).

제안: **화면 짧은 변의 78%를 채우는 종횡비 1.384 직사각형**을 중앙에 그린다.

- 세로 커버리지 0.78 → 측정 중앙값 0.834보다 약간 여유. 여백은 각 변 0.11로 하한(0.02)의
  5배.
- 사용자가 테두리에 맞추면 게이트의 세 조건이 **동시에** 만족된다. 하한에 맞추게 하면
  한 조건만 흔들려도 떨어진다.
- 세로 화면과 가로 화면에서 같은 규칙을 쓰되, 짧은 변 기준이므로 세로 촬영을 전제한다.
  가로로 들면 종횡비가 뒤집혀 `wrong-shape`가 되므로, **가로 감지 시 세로로 돌리라는 안내를
  먼저** 띄운다.

### 4.2 어떻게 그릴 것인가

`<video>` 위에 절대 위치 `<div>` 하나. 캔버스가 필요 없다.

```
video wrapper (position: relative)
  video           (object-fit: cover)
  guide overlay   (position: absolute; inset: 0; pointer-events: none)
      어두운 마스크 4장 또는 box-shadow: 0 0 0 100vmax rgba(0,0,0,.45)
      테두리 사각형 + 네 모서리 기호
```

상태는 색으로만 말하지 않는다 — **회색(찾는 중) / 주황(조건 미달) / 초록(지금 찍으면 됨)**
에 더해 테두리 두께와 모서리 기호를 함께 바꾸고, 문구를 같이 띄운다. 색만 쓰면 색각
이상에서 구분되지 않는다.

`object-fit: cover`는 영상 일부를 잘라낸다. **테두리의 화면 좌표와 검출에 쓰는 프레임
좌표가 어긋나면 안 된다** — 이 프로젝트에서 렌더 해상도 불일치로 엉뚱한 단계를 잰 사례가
네 번 있다(CLAUDE.md §2). 검출 프레임은 `video.videoWidth/videoHeight`에서 직접 그리고,
오버레이 좌표는 그 프레임을 화면에 매핑한 변환을 **한 곳에서** 계산해 양쪽이 같은 수를
쓰게 한다.

## 5. 기울어짐 경고 — 구현 제안

### 5.1 두 가지 기울어짐을 구분해야 한다

같은 "기울었다"가 아니다. 사용자가 해야 할 행동이 다르다.

| | 뜻 | 고치는 법 |
|---|---|---|
| **회전(roll)** | 종이가 화면 안에서 돌아가 있음 | 폰이나 종이를 돌린다 |
| **원근 기울기** | 카메라가 종이와 나란하지 않음 | 폰을 종이 위로 눕힌다 |

원근 기울기는 워프가 펴주지만, **심하면 검출 자체가 실패한다.** §4의 실패 12건이 대체로
그랬다.

### 5.2 제안 — 이미 있는 사각형에서 뽑는다 (권장)

새 알고리즘이 필요 없다. `orderQuadPoints`가 정렬한 네 점에서 바로 나온다.

```ts
const [tl, tr, br, bl] = quality.points;

// 회전: 위/아래 변의 평균 각도. 0에 가까워야 한다.
const rollDeg = ((Math.atan2(tr.y - tl.y, tr.x - tl.x)
               + Math.atan2(br.y - bl.y, br.x - bl.x)) / 2) * (180 / Math.PI);

// 원근 기울기: 마주보는 변의 길이 차이. 부호가 방향을 말한다.
const topW = dist(tl, tr), bottomW = dist(bl, br);
const leftH = dist(tl, bl), rightH = dist(tr, br);
const keystoneV = (bottomW - topW) / Math.max(topW, bottomW); // +면 위쪽이 멀다
const keystoneH = (rightH - leftH) / Math.max(leftH, rightH); // +면 왼쪽이 멀다
```

**부호가 방향을 준다는 것이 핵심이다.** "기울었습니다"가 아니라 *"위쪽을 조금 낮춰
주세요"*라고 말할 수 있다.

`edgeConsistency`가 이미 이 둘을 하나로 합친 값이다(`(min/max 가로 + min/max 세로)/2`).
경고 문구에는 개별 `keystone`의 부호를, 최종 판정에는 `edgeConsistency`를 쓴다.

측정된 분포(성공한 26개): `edgeConsistency` min 0.814 · 중앙 0.978. 즉 성공 사례는 거의
정면이다. **경고 문턱 초안은 `edgeConsistency < 0.93`(키스톤 약 7%), 회전은 `|roll| > 4°`
로 두고 첫 라운드에서 재조정한다.** 이 두 숫자는 아직 검증되지 않았다.

### 5.3 대안과 왜 안 쓰는가

| 방법 | 판단 |
|---|---|
| `DeviceOrientationEvent` (중력 기준 자세) | **보조로만.** 종이가 수평면에 있을 때만 뜻이 있고, 데스크톱 웹캠에는 센서가 없다. CPU를 안 쓰므로 *사각형을 찾기 전* 단계에서 "폰을 눕히세요"를 미리 띄우는 데는 쓸 수 있다 |
| Hough 직선 검출 | 코드가 늘고 §5.2보다 나은 점이 없다. 사각형을 이미 찾았으면 변은 이미 안다 |
| 별도 ML 모델 | 이 문제에 과하다. 번들과 초기화 비용이 인식 이득보다 크다 |

**권장: §5.2 단독. `DeviceOrientation`은 모바일에서 선택적 사전 힌트.**

## 6. 어두움 감지와 "인식 가능한 원본인가" 평가

### 6.1 이것이 진짜 남은 문제다

워프된 선별검사 19장의 `pageInkRatio`:

```
빈 양식(스캔)   0.087
워프된 사진     0.345 ~ 0.613      격자 필드 1~11개
```

배경은 잘려나갔는데도 **종이 자체가 `pixel < 200`보다 어둡게 찍혔다.** 흰 종이에 자동
노출을 맞추면 그렇게 된다. 학생 14·15가 잘 보정되고도 아무 값을 못 낸 이유가 여기 있다고
본다 — **아직 증명되지 않았다.**

### 6.2 라이브에서 잴 것 (사각형 안쪽만)

검출된 사각형 내부를 재야 한다. 바깥(바닥·책상)은 노출과 무관한 잡음이다.

| 값 | 정의 | 쓰임 |
|---|---|---|
| `inkFraction` | 사각형 안에서 `gray < 200`인 비율 | `pageInkRatio`의 라이브 대응. 어두움 판정 |
| `paperLuma` | 사각형 안 평균 밝기 | 노출 안내 |
| `blownFraction` | `gray >= 250` 비율 | 반사광(글레어) 판정 |
| `backgroundContrast` | 안쪽 평균 − 바깥쪽 평균 | 검출 실패 예보 |
| 흐림 | 라플라시안 분산 | 손떨림 판정 |

**문턱은 아직 정하지 않는다.** 스캔이 0.087, 잘 안 읽힌 사진이 0.35~0.61이라는 두 점만
알고 있고, 그 사이 어디가 경계인지는 재지 않았다. §8에 그 측정을 적어둔다.

흐림도 마찬가지다. 서버의 `pageSharpness`(gradient 기반)가 있지만 라플라시안 분산과 다른
양이므로, **문턱을 추측해 넣지 않는다. 먼저 잰다.**

### 6.3 "유의미한 인식이 가능한가" — 클라이언트가 할 수 없는 부분

| 신호 | 어디서 | 라이브 가능? |
|---|---|---|
| 보정 성공 / 거절 이유 | OpenCV 워커 | 예 |
| 커버리지·여백·종횡비·기울기 | 같은 사각형 | 예 |
| `inkFraction`·글레어·흐림 | 같은 프레임 | 예 |
| **격자 필드 수** | `buildCagiGridDetection` | **아니오** |

격자 검출은 `markDensity`를 거치고 그것은 `sharp`(서버 전용)를 쓴다. 그런데 §4에서
**격자 필드 수가 1~11개로 갈리고 그것이 학생별 성패와 같이 움직였다.** 라이브 신호만으로는
이 축을 볼 수 없다.

**제안: 촬영 직후 서버에 한 번 물어본다.**

```
POST /api/uploads/quality   { imageId, type }
  -> { rectified, pageInkRatio, gridFields, verdict, hint }
```

- 종이가 아직 눈앞에 있을 때, 장당 즉시 판정한다. `/api/recognize`는 양면이 다 모인 뒤에
  돌므로 이 자리에 쓸 수 없다.
- **같은 평가기를 `/api/recognize`에서도 호출한다.** 두 경로가 다른 답을 내면 사용자는
  "괜찮다더니 왜"를 겪는다. 이 프로젝트에서 노드와 브라우저가 다른 답을 낸 사례가 이미
  있다(CLAUDE.md §5.1).
- 파일 업로드 경로에도 같은 판정을 붙인다. 카메라만 유도하고 업로드는 방치하면 사용자는
  더 조용한 경로로 도망간다.

### 6.4 판정 밴드는 측정으로 정한다

`verdict`를 세 단계로 두되(`good` / `retake-suggested` / `unusable`), **경계는 추측하지
않는다.** 19명 세트에 정답이 붙어 있으므로 이렇게 정할 수 있다.

> "정답을 한 칸이라도 낸 학생"과 "한 칸도 못 낸 학생"을 가장 잘 가르는
> `gridFields` / `pageInkRatio` 절단면을 찾는다.

표본이 19명이므로 **과적합을 경계해야 한다.** 절단면을 고른 뒤에는 라벨을 섞은 대조군에서
같은 탐색을 돌려, 우연히 얻어지는 분리 수준을 같이 적는다 — 선택 편향을 그렇게 쟀다
([WEAK_SIGNAL_STABILITY_PLAN_2026-08-24.md](WEAK_SIGNAL_STABILITY_PLAN_2026-08-24.md)).

## 7. 성능 예산

측정된 값: 1600px 긴 변에서 사각형 검출이 **241~1392 ms**(사진 10장).

라이브는 그것보다 훨씬 작아야 한다.

- 검출 프레임 **긴 변 480px** 제안. 1600px 대비 화소가 약 11분의 1이다.
- 목표 **4 fps 이상**, 한 프레임이 처리 중이면 다음 프레임은 **버린다**(큐에 쌓지 않는다).
- 검출은 **이미 있는 OpenCV 워커**에서 돈다. 메인 스레드에서 돌리면 미리보기가 끊긴다.
- 프레임 공급은 `requestVideoFrameCallback`, 없으면 `setTimeout`. **`requestAnimationFrame`을
  쓰지 않는다** — 숨은 탭에서 발화하지 않아 조용히 멈춘다(CLAUDE.md §4).
- **480px과 4 fps는 아직 재지 않은 목표치다.** 첫 구현에서 실측하고, 못 맞추면 프레임을
  더 줄이거나 검출 지도를 Otsu 하나로 줄인다.

### 7.1 §8-1 실측 (2026-08-27, `scripts/check-live-detect-cost.cjs`)

`detectDocumentQuadFromMat` **단독** 비용. 합성 프레임(빈 양식을 기울여 잡음 섞인 회색
배경에 합성), Node OpenCV 4.9.0 빌드.

```
긴 변 480  (368x480)   N=20   median 36.8 ms   min 36.1  max 56.9   쿼드 검출 20/20
긴 변 1600 (1225x1600) N=5    median 299.5 ms                       쿼드 검출 5/5
```

- 1600 쪽이 §7 서두의 실측 밴드(241~1392 ms) 안쪽 하단에 들어온다. 합성 프레임이 실제
  사진보다 쉬운 쪽이라는 뜻이고, **480의 36.8 ms도 같은 만큼 낙관적으로 읽어야 한다.**
- **이것은 fps가 아니다.** 비디오 grab, 캔버스 축소, 워커 전송, 리렌더가 전부 빠져 있다.
  브라우저 WASM 빌드도 Node 빌드와 다르다. 200 ms 주기와의 여유가 얼마나 남는지는
  브라우저에서 따로 재야 한다.
- 배율이 8.1x로 화소비 11.1x보다 작다 — 고정 비용이 있다는 뜻이므로, 프레임을 더 줄여
  얻을 이득은 화소비만큼 나오지 않는다.

2. **`inkFraction` 경계.** 워프된 19장의 사각형 내부 `inkFraction`과 학생별 성패를 대조해
   `good` / `retake` 경계를 찾는다. 섞은 라벨 대조군을 같이 돌린다.
3. **흐림 지표 보정.** 라플라시안 분산을 19장에서 재고 격자 필드 수와의 관계를 본다.
   관계가 없으면 흐림 경고를 넣지 않는다.
4. **§5.2 문턱 검증.** `edgeConsistency < 0.93`, `|roll| > 4°`가 실제로 실패를 예보하는가.
   성공한 26개의 분포(min 0.814)와 실패 12건을 나란히 놓고 확인한다.

## 9. 만드는 순서

| 단계 | 내용 | 판정 기준 |
|---|---|---|
| 1 | 정적 가이드 테두리(§4) + 세로 촬영 안내 | 화면 좌표와 검출 좌표가 같은 변환을 쓰는가 |
| 2 | 라이브 사각형 검출 + 상태 색/문구(§3) | 4 fps, 미리보기 끊김 없음 |
| 3 | 기울어짐·거리 방향 안내(§5) | §8-4에서 문턱 검증 후 |
| 4 | 노출·글레어 안내(§6.2) | §8-2에서 경계 측정 후 |
| 5 | 촬영 직후 서버 판정(§6.3) + 파일 업로드 경로에도 적용 | §6.4 밴드 확정 후 |
| 6 | 거절 시 **원본을 조용히 올리지 않는다** | 지금의 조용한 폴백 제거 |

**6단계가 실제 안전 이득이다.** 1~5는 그 앞에서 재촬영을 유도하는 장치이고, 6이 없으면
못 쓸 사진이 여전히 통과한다.
