# KPGA_sacnner

도박예방교육 강사가 교육 후 수집하는 종이 응답지 2종(도박문제 선별검사지 CAGI, 예방교육 만족도조사)을 사진/PDF로 업로드하면, 이미지에서 응답값을 추출해 중앙 시스템 업로드용 엑셀 템플릿 2개에 학생별로 자동 입력해주는 Next.js 웹앱. 제품 요구사항은 [Docs/00_PRD.md](Docs/00_PRD.md) 참고.

## 문서 구성 규칙

작업이 반복될 때마다 `Docs/`에 번호를 매긴 파일이 끝없이 늘어나는 문제가 있어, 아래와 같이 역할별로 분리한다.

### `Docs/` — 상위 문서만

프로젝트 자체를 설명하는, 자주 바뀌지 않는 문서만 둔다.

- **README(이 문서)** — 프로젝트 개요와 문서 규칙.
- **PRD/스펙 문서** (`00_PRD.md`, `01_DATA_MAPPING.md`~`13_IMPLEMENTED_FEATURES_STATUS.md`) — 요구사항, 데이터 매핑, 검증 규칙, 테스트 계획, 구현 로드맵, 현재 구현 상태 등. 최초 기획 단계에 작성되었고 이후에도 그 자체로 유효한 "제품이 무엇인가"에 대한 문서라 이 폴더에 남긴다.
- **`DESIGN.md`** — 아키텍처/설계 문서.
- **[BUG_REPORTS.md](Docs/BUG_REPORTS.md)** — 실제 버그(정상적으로 동작해야 하는데 하지 못한 사례)만 모은 색인.

**상위 문서 공통 원칙**: 상위 문서에는 그 문서 자체가 필요로 하는 내용(예: 버그의 원인·대응, 스펙의 규칙)만 적고, 조사 과정·검토했던 대안·구현 히스토리 같은 전체 맥락은 적지 않는다. 대신 관련 `Task/` 문서로 가는 **색인(링크)만** 걸어둔다 — 세부사항이 필요할 때만 그 링크를 따라가 읽으면 되도록. 예를 들어 `BUG_REPORTS.md`는 원인과 대응을 3~6줄로 직접 적되, "어떤 작업을 하다가 발생했는지"는 서술하지 않고 관련 Task 문서 링크로만 남긴다. 같은 원리를 `00_PRD.md`, `04_OCR_FORM_RECOGNITION_SPEC.md`, `12_REAL_FEATURE_IMPLEMENTATION_ROADMAP.md`, `13_IMPLEMENTED_FEATURES_STATUS.md` 등 다른 상위 문서에도 적용한다 — 관련된 실제 작업이 있으면 해당 절 근처에 "관련 Task" 목록을 추가한다. 새 문서 파일을 만들지 않고 기존 파일 안에 항목/링크를 추가하는 방식으로 운영한다.

새로운 스펙/설계 문서가 필요하면 여기에 추가하되, 여러 문서가 사실상 같은 역할(예: 세부 스펙 여러 개)을 한다면 하나로 통합하는 것을 우선 고려한다.

### `Task/` — 작업 기록

기능 구현, 조사, 버그 수정처럼 **한 번 하고 끝나는 작업의 상세 기록**은 전부 `Task/` 아래에 작업 단위(하나의 기능/이슈 스레드)로 하나의 파일을 만들어 쌓아간다. 같은 작업이 여러 라운드(설계 → 구현 → 회귀 → 재수정)에 걸쳐 이어지면 새 파일을 만들지 말고 **기존 파일에 이어서 추가**한다.

Task 문서 안은 **사이클 단위**로 기입한다. 하나의 사이클은 다음 세 가지를 한 묶음으로 한다:

- **작업 내용(코드 작성)**: 원인 분석, 검토한 방식, 실제로 변경/작성한 코드.
- **테스트 결과**: 그 사이클에서 한 자동 테스트, 수동/실기기 검증 결과. 검증하지 못한 부분은 그렇다고 명시한다.
- **다음 작업을 위한 피드백**: 그 사이클이 끝난 시점에 남은 미해결 사항이나 다음에 확인해야 할 것. 다음 사이클은 이 피드백을 배경 삼아 시작된다.

작업이 여러 라운드에 걸치면(설계 → 구현 → 회귀 발견 → 재수정처럼) 새 파일을 만들지 않고 **사이클을 이어서 추가**한다 — "사이클 1", "사이클 2"처럼 시간순으로 쌓아 하나의 파일 안에서 전체 히스토리가 보이게 한다. 맨 앞에는 전체 배경(왜 이 작업 스레드가 시작됐는지)을 한 번만 적는다.

`Docs/BUG_REPORTS.md`에 실제 버그로 등재된 항목은 반드시 여기 어딘가에 대응하는 Task 문서(전체 맥락)가 있어야 한다.

### 예시

- `Docs/BUG_REPORTS.md`의 "Vercel 인스턴스 간 `/tmp` 미공유로 저장/다운로드 404" 항목(3~4줄) → 전체 조사 과정과 구현 히스토리는 [Task/STATELESS_ARCHITECTURE_MIGRATION.md](Task/STATELESS_ARCHITECTURE_MIGRATION.md)에.
- 아직 버그로 등재되지 않은 순수 기능 작업(예: 동적 표 행 검출 도입)은 Task 문서만 있고 BUG_REPORTS에는 없을 수 있다.
- `Docs/04_OCR_FORM_RECOGNITION_SPEC.md`는 인식 규칙 자체만 설명하고, 그 규칙이 실제로 왜/어떻게 바뀌었는지는 "관련 Task" 링크로만 연결한다.

## 작업 프로세스

이 프로젝트의 실제 코드 작업은 클로드 코드와 코덱스(Codex CLI)가 역할을 나눠 진행한다. 표준 흐름은 다음 5단계다.

1. **계획 수립 (클로드 코드)** — 무엇을, 왜 바꾸는지 정리한다.
2. **문서 작성 (클로드 코드)** — 필요하면 작업지시서·설계 문서를 먼저 쓴다(`Task/`에 새 사이클로, 또는 신규 스레드면 새 Task 파일로).
3. **코드 작성 및 배포 (코덱스)** — 실제 구현과 커밋·푸시(배포 트리거)까지 코덱스가 수행한다.
4. **테스트 (클로드 코드)** — 자동 테스트, 필요시 브라우저/실기기 검증을 클로드 코드가 직접 수행한다.
5. **테스트 결과 정리 및 피드백, 관련 문서 작성 & 필요에 따라 상위 문서 수정 (클로드 코드)** — `Task/` 문서에 사이클(작업 내용/테스트 결과/다음 작업 피드백)을 기록하고, 버그가 확정되면 `BUG_REPORTS.md`에, 상위 문서(PRD/스펙 등) 내용이 실제로 바뀌었으면 해당 문서에도 반영한다.

**코덱스가 작성한 코드를 매번 즉시 리뷰하지 않는다.** 4단계 테스트에서 실제로 문제가 발견됐을 때만 코드를 열어 리뷰한다 — 테스트를 통과하면 리뷰 없이 다음 단계로 넘어간다. 이는 이전에 매 변경마다 코드를 먼저 리뷰하던 방식에서 바뀐 것이다(2026-08-03 변경).

### 배포마다 테스트 버전 번호 갱신 (필수)

코드를 수정하고 새로 배포할 때마다, 화면 우측 상단의 "테스트 버전" 표시(`src/app/page.tsx`의 `BrandHeader` 컴포넌트)를 반드시 갱신한다. 사용자가 지금 보고 있는 화면이 정확히 몇 번째 배포분인지 한눈에 확인하기 위한 것이다(2026-08-10 도입).

- 형식: `v{배포일 YYYY-MM-DD}.{그날 몇 번째 배포인지, 1부터 시작}` — 예: 같은 날 두 번째 배포면 `v2026-08-10.2`. 날짜가 바뀌면 순번은 다시 1로 리셋.
- **코드를 수정해 커밋·배포하는 주체(3단계, 코덱스)가 매번 이 줄도 함께 갱신하고 커밋에 포함한다.** 코드만 바뀌고 이 버전 문자열이 그대로면 배포 자체를 빠뜨린 것으로 간주한다.
- 문서 전용 변경(코드가 바뀌지 않는 `Docs/`·`Task/` 커밋)은 갱신하지 않는다 — 실제 배포되는 코드가 바뀔 때만 올린다.

### 원인 격리 실험 브랜치 규칙

원인이 불확실한 문제(특히 인식 정확도)를 고칠 때는, 여러 가설을 한 번에 손대지 않고 **가설 하나당 브랜치 하나**로 나눠 수정·측정한다. 2026-08-11~12에 인식 계층에 2,121줄을 추가하고도 측정값이 전혀 움직이지 않은 일이 있었다 — 판정 기준이 되는 숫자가 없으면 어떤 라운드도 반증되지 않아 작업이 루프에 빠진다(2026-08-13 도입).

1. **착수 전에 합격 기준을 숫자로 정한다.** 무엇이 좋아지면 성공인지(예: `AUTO 34/46 → 40`)를 작업지시서에 먼저 적는다. 숫자가 없는 작업은 할당하지 않는다.
2. **기준선을 먼저 측정해 Task 문서에 기록한다.** 수정 후 같은 명령으로 재측정해 같은 지표를 비교한다.
3. **브랜치 하나는 원인 하나만 건드린다.** 이름은 `exp/cause-<식별자>-<요약>`. 두 원인을 한 브랜치에서 고치면 어느 쪽이 효과를 냈는지 판정할 수 없다.
4. **모든 실험 브랜치는 `main`에서 분기한다.** 실험 브랜치 위에 실험 브랜치를 쌓지 않는다.
5. **판정 후 정리한다.** 지표가 개선되고 다른 지표가 나빠지지 않은 브랜치만 `main`에 병합한다. 개선이 없으면 **가설 기각**으로 기록하고 브랜치를 삭제한다(`git branch -d` 실패 시 `-D`, 원격은 `git push origin --delete`). 기각도 유효한 결과이므로 숫자와 함께 Task 문서에 남긴다.
6. **되돌릴 수 있는 상태를 유지한다.** 실험 중에는 `main`을 건드리지 않는다. 미커밋 변경을 남긴 채 다른 작업으로 넘어가지 않는다 — 커밋되지 않은 실험 코드가 섞이면 측정값이 오염된다(실제로 2026-08-12에 이 문제로 배포본이 깨진 것으로 오진한 사례가 있다).
7. **실제 스캔 자료는 저장소에 커밋하지 않는다.** 학생 응답과 연락처 흔적이 포함되므로 경로는 환경변수로 주입한다. 저장소에는 빈 양식 픽스처만 둔다.
8. **표본에 코드를 맞추지 않는다.** 계측기나 정답표를 고치는 것은 물론 금지이고, **표본에서 실패한 특정 항목의 이름으로 분기하는 예외**(예: `field === 'satisfaction.q07'`)도 같은 성격의 반칙이다. 숫자는 올라가지만 메커니즘은 그대로여서 다음 자료에서 다시 실패한다. 수정은 판별 방식의 일반적 성질이어야 한다(2026-08-13, 사이클 3에서 실제로 발생).
9. **임계값 조정은 표본을 늘린 뒤에만 한다.** 2페이지로 맞춘 임계값은 과적합이다. 임계값을 건드리려면 정답표 표본을 먼저 확보한다.

## 개발

```bash
npm install
npm run dev
npm test
npm run build
```

실제 스캔으로 인식 정확도를 측정할 때(자료는 저장소 밖에 둔다):

```bash
REAL_SCAN_CAGI_PDF="<선별검사 PDF 경로>" REAL_SCAN_SAT_PDF="<만족도조사 PDF 경로>" REAL_SCAN_PAGES=2 npx vitest run tests/real-scan-measure.test.ts
```

이 계측기는 **배포본과 동일한 래스터**(`PDF_RENDER_OPTIONS[0]` = scale 1.5, JPEG q0.86)로 렌더한다. 상수는 `src/lib/pdf/pdfRenderConfig.ts`에서 앱과 함께 import하므로 둘이 어긋날 수 없다. 예전에는 계측기만 `scale 2.0` PNG 무손실로 렌더해, 같은 커밋에서 계측기는 `CORRECT 116/135 WRONG 0`, 배포본은 `92/135 WRONG 1`을 내는 상태였다(2026-08-19 발견, [Task/MEASUREMENT_RENDER_PARITY_2026-08-19.md](Task/MEASUREMENT_RENDER_PARITY_2026-08-19.md)).

업로드 해상도 변경안을 **측정할 때만** 스케일을 덮어쓴다. 덮어쓰면 보고서에 `OVERRIDDEN` 경고가 찍힌다.

```bash
REAL_SCAN_RENDER_SCALE=2.0 REAL_SCAN_RENDER_QUALITY=0.86 npx vitest run tests/real-scan-measure.test.ts
```
